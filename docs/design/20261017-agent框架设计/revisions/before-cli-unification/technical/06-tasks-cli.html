任务协议

TargetIntent = Direct | Project(projectId, workspaceId?)
    | Session(sessionId) | NewSession(label?, nodeId?, workdir?)
    | NewProject(name, nodeId?, baseDir?, template?)
TaskSpec = {
  taskId, revision, parentTaskId?, ownerId,
  originConversationId, originBranchId, originMessageId,
  targetIntent, resolvedTarget?, goal, acceptance,
  contextRefs, budget, idempotencyKey
}
ResolvedTarget = { nodeId?, projectId?, workspaceId?, sessionId?, workdir? }
RunHandle = { runId, launchId, taskId, revision, executor, sessionId? }
Result = { runId, taskId, revision, state, summary,
  artifactRefs, checks, blockers, exitCode?, usage? }

目标显式指定优先；其次引用任务 / 会话，再其次当前对话绑定，最后才是名称推断。projectId 可空。不能因为用户当前在 Roami 项目页，就把“新建一个记账项目”派进现有项目。

资源准备状态机

1. 接受 TaskIntent

任务 + task.prepare job + task.accepted 事件同事务保存。

2. preparing

解析目标、确定节点；建目录 / 项目 / 会话时记录资源回执。

3. queued / running

资源就绪再提交执行器；收到启动回执才宣告 running。

4. verifying / terminal

结果验证当前 revision；写终态并入 Main 回报邮箱。

创建资源按 taskId + revision + resourceKind 去重。项目同名冲突不得静默覆盖。资源写入结果不明时先按已记录 ID / 标签查回，不能直接再建一套。已有用户目录与会话不由失败清理顺手删除。

CLI 接入的真实边界

Python 使用独立 argv 调现有 CLI，不导入 Go internal 包。已有 roami ttmux swarm ...、send、capture、ls --json 支持会话与派活；长简报 file / stdin、启动结构化回执、退出状态与确认停止仍需补齐。

# 当前已有命令的示意；框架内部用 argv，不拼 shell 字符串
roami ttmux swarm new <group> --no-master
roami ttmux swarm add <group> <member> --type agent --kind codex --dir <workdir> '<brief>'
roami ttmux swarm status <group> --json
roami ttmux send <sessionId> '<follow-up>'
roami ttmux capture <sessionId>

# 拟新增统一任务回报 / 用户回复命令，尚未实现
roami agent report --task <taskId> --run <runId> --revision <n> --file result.json
roami agent reply --conversation <conversationId> --run <runId> --file reply.md

回报到原对话

  • 执行器启动时记录 task / run / revision / session / 编码 Agent conversationId；通过任务简报与 ROAMI_TASK_ID、ROAMI_RUN_ID 等专用环境变量提供回报上下文。
  • report 只保存 Result，重复相同 payload 返回同回执；同 run 相同终态却不同 payload 标记冲突，不重复唤醒 Main。
  • 旧 revision 的结果作为历史保留，不改最新任务终态。Result 的 artifact hash、目标 commit 与 checks 经独立验收后，才能标 succeeded。
  • Main 原生使用 ReplyService；外部 Worker 默认 report。reply 仅对明确允许代答的运行开放，conversationId 必须匹配任务记录的 origin，不由 Worker 任意指定收件人。
  • 本机 CLI 通过 agent.sock 连接私有回报入口，复用主机用户与运行绑定；不再签发一套用户登录 Token。该私有入口不通过 Go 公共代理暴露。
  • channel binding 保存最初 Web / IM 来源；执行会话改名、转项目或用户切页面，都不改变原对话回报位置。

租约、Fork 与预算

# 领取与终态写入使用 fencing；示意条件
UPDATE jobs SET state='running', lease_owner=:worker,
    lease_until_ms=:deadline, lease_epoch=lease_epoch+1
WHERE id=:job AND state='queued';

UPDATE task_attempts SET state=:terminal, result_json=:result
WHERE id=:run AND lease_epoch=:claimed_epoch
  AND task_revision=:expected_revision;

作业租约、资源租约和任务状态是不同事实。对 CLI 启动先持久化 launchId，再调用外部命令；崩溃后 outcome=unknown 时按 launchId / sessionId 对账，不能靠再跑命令获得“至少一次执行”。有副作用的 Shell / HTTP 也不承诺 exactly-once。租约过期不能作为重复启动的依据；旧执行器未确认停止时资源保持隔离，由 supervisor 对账后再决定是否重新领取。

原生 Fork 从已完成检查点分支；默认只传简报。首版建议父树并发 3、深度 2，可配置；每个 child 消耗祖先总预算，模型用量未知时用 deadline / 工具轮次 / 并发兜底。同 worktree 单写；并行编码用独立 worktree，集成验收另做任务。

取消与重启

取消先记 cancelling，通知当前工具 / 子树停止，再确认任务对应工具进程与资源动作已停止。复用的 TUI 会话可以保持空闲；取消任务不等于必须销毁会话。不能证明停止时保留 interrupted / unknown，而不是仅因 CLI 进程返回就宣告 cancelled。

中断点恢复行为
目录创建后、登记前按 provisioning 记录查回；不覆盖同名现有用户目录
CLI 启动后、会话 ID 回写前按 launchId 对账；不明时等待处理，防重复派活
Worker 完成后、Main 回复前持久化 completion job 重放；只生成一条幂等回报
取消和完成同时到达按 task revision 与状态转换规则决议；迟到结果留历史
Go 或网页断开Python 和 tmux 后台工作继续；连接恢复后收事件
