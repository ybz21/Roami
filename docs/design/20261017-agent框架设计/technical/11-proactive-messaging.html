大总管主动联系你的时机

来源消息内容触发方式
任务完成 / 失败一句结果、证据入口或下一步任务终态事件，不逐 token 通知
等待用户卡在哪里，需要你做哪个决定waiting_user 事件，回答后续接原任务
时间 / 日程到点提醒、每日简报、目标跟进明确配置的调度器，按时区执行并补偿漏跑
主动建议与你的目标相关的新发现或建议事件驱动、有预算的后台评估；可关闭

Main 默认随时可聊，不通过无限模型轮询来维持“主动”。主动生成与普通问答用不同队列和额度，不能抢占 Main 的低延迟槽位。

统一的方法与投递链路

trigger → proactive policy → durable job → Main mailbox / notify_user
        → ReplyService: assistant message + message.completed + delivery outbox
        → Web SSE / unread badge / existing App notification adapter

Python 内部提供 notify_user 服务，任务完成复用 report → Main 回报流程。外部执行器仍使用拟新增 roami agent report / reply，并验证 run 与原始对话绑定；定时触发器也先建立可追溯 job，不任意指定外部用户收件人。无需第二套用户鉴权，公开请求一律经过 Go。

来源 source + dedupeKey 在 owner / conversation 范围内去重；同键不同内容报冲突。消息、完成事件、渠道 outbox 同事务提交，提交后才推送；发送失败可以重试，不重新生成一条消息。Web、App 与外部渠道沿用同一个 messageId / eventId。

右上角未读红圈

桌面和手机的右上角都提供“大总管消息”入口，按钮右上显示红色数字圆角角标；0 隐藏，超过 99 显示 99+。历史对话列表标出有未读消息的会话。未读按一条已提交的 assistant 消息计数，不按流片段、重复事件、任务进度或通知渠道计数。

打开消息列表不自动全部已读；点消息回到对应对话并滚到消息位置，真正呈现后提交 readThroughEventId。只有当前对话、页面可见且消息进入可见区域时才自动标已读，后台标签页不清红圈。多端同步使用服务端持久水位，客户端只做乐观更新；较旧设备提交不能倒退水位，浏览期间新来的消息不会被旧游标误清。

原型可演示红圈计数、消息列表、主动联系和历史对话定位；生产应使用交叉观察 / 可见性信号，不能把打开 App 等同于读完全部消息。操作系统桌面 App 图标角标与通知权限属于平台适配，不能由网页中的红圈冒充已完成。

免打扰、节奏与隐私

用户可分别控制任务结果、待决定事项、定时提醒和主动建议。普通提醒遵守免打扰时间与时区；只延后通知，不丢弃聊天记录。高优先级是否绕过免打扰必须由用户设置，不能由模型自行升级。

同一任务频繁变化合并通知；按用户配置限制单位时间主动建议数量，延后项目可以汇成一条简报。可选锁屏内容隐藏，仅提示“大总管有新消息”。权限被拒时仍保留 App 内未读与聊天消息，提示投递实际状态。

持久化与代码落点

原始消息在 messages，事件在 events；conversation_reads(owner_id, conversation_id, event_cursor) 保存单调已读水位，按 owner / conversation 校验。计数从所有符合条件的未读事件计算，列表可分页，不能只数最近 200 条。投递沿用 deliveries；后续通知偏好与调度配置进入版本化迁移。

Python Notifications 服务已开始实现事务性主动消息、去重、outbox 与已读水位；Go 仍需接统一代理 / 通知适配。当前 Go InboxStore 只对 session.waiting 计算 badge，不能直接当作 Agent 聊天未读数；不得双写两套未读真相。系统 Push 沿用现有后端通道，通过 Agent 事件 ID 关联和去重。

验收

同一事件重发只有一条消息；断线 / 重启后未读仍存在；查看其他对话不误清；旧设备游标不倒退；进入消息前新到的消息不被旧游标清掉；多端同步；超过 200 条未读仍计数准确；普通提醒在免打扰内延后；无权限时不伪报送达；任务回报仍回原对话；App 通知点击定位消息；移动端红圈不挤压标题与触控入口。
