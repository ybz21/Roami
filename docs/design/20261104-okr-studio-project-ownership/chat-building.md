# 边聊天边搭建 OKR

2026-11-16，延续[项目内创建流程](project-creation-flow.md)，以此稿澄清搭建 Agent 与运行 Main 的区别。[可交互原型](chat-building.html)。设计与模拟验收，不代表产品能力已上线；原宣传 Swarm、成员及日程继续停止。

## 交互主线

用户从项目的 OKR Tab 创建草稿，直接进入聊天。输入框下方先选搭建 Agent：Codex、Claude Code、OpenCode、Pi 或 Roami，沿用全局输入框的选择方式，展示真实安装/登录/工具可用状态。首条发送前可改，首次提交原子绑定本草稿的唯一开发会话；首页对话不参与。不先填配置表，不先创建运营团队。

用户说“提高产品曝光，内容用 Codex，数据用 Claude”，搭建 Agent 阅读当前项目约定和完整 okr-development 模板，再在隔离草稿建立目标、实施手段、看板、Connector Skill、角色、记忆和日程定义。缺少会改变方案的必要信息时，在聊天里只问最关键的一个问题；其他内容先留可修改草稿，不编目标数字、账号或权限。

聊天始终是主区域。右侧预览默认展开，只有目标、看板、团队、文件四个内容入口；无额外规划仪表盘、进度大卡或永久配置面板。文件树与源代码属于“文件”，不再把配置目录做单独产品页。桌面可收起预览释放空间；手机“查看方案”进入全屏预览，“返回聊天”保留原草稿和滚动位置。项目导航与当前 OKR 身份保留。

## 每轮怎样反馈

1. 发出原文后，在原搭建对话显示真实流式正文和工具过程，复用首页或所选原生 Agent 的组件，不只显示最后答案。
2. 构建中显示“正在更新草稿”和可用的“停止构建”。预览仍看上一份完整快照，不展示写到一半的文件为完整方案。离开页面不等于停止；回来先查询原请求，不能重发。
3. 这一轮完成后，聊天给一句结果：“已新增评论运营，数据分析改用 Claude”，附一条可点击的变更摘要和版本。工具细节按需展开；失败指出具体文件或缺口，保留上一版与用户输入。
4. 点击“查看这一版”定位右侧对应快照；版本选择和预览中的角色 Agent 修改都生成新草稿版本并回到同一聊天记录。页面控件与聊天共同写一个版本模型，不能各存一套互相覆盖。
5. 用户继续说“加评论运营”“每周复盘”“改成按周查看”，在当前选定版本上增量修改，只改相关文件与依赖，不重建整个包，不注册同名成员、不启动运行。

聊天上的变更摘要是理解入口；文件差异与完整工具回执是依据。预览明确标注“草稿 vN”；看板没有真实观测时显示“待取数”，不能把布局样例当成实测数据。

## 搭建 Agent 与运行团队

| 项目 | 搭建 Agent | 运行 Main / 成员 |
|---|---|---|
| 用途 | 讨论、写草稿、校验与预览 | Main 指挥、成员执行、取数与验收 |
| 何时选择 | 第一次发需求前 | 搭建过程或开始运行前 |
| 身份 | 本 OKR 的独立开发会话 | 本 OKR 的固定 Main 和长期成员 |
| Agent | Codex、Claude Code、OpenCode、Pi、Roami | Main 为 Roami；各角色独立选择 executor |
| 关联 | 保存 draftId、provider 会话、轮次和产物 | 明确接收确认版本与目标来源，不复制成新的用户授权 |

更改搭建 Agent 不应静默替换当前 provider。第一次发送后保留当前选择；需要更换时显式进入“更换搭建 Agent”，先确认本轮停止，再保留旧会话，建立新的开发会话关联和可读交接（目标、当前文件快照、约束、未完成项）。旧历史仍可看，不能声称跨 provider 原生记忆相同。原型暂不模拟这段迁移，不把禁用选择器当产品最终方案。

“团队”默认平面职责行，展示名称、Agent、未启动/真实状态。展开一行才看职责、Agent选择、Skill和记忆位置。模板只提出建议，不固定要几个角色。未安装的 Agent 可以在提案里标成待配置，但不能通过运行检查。选择执行器不改全局模型、路由或费用。

## 编辑、版本与恢复

- 每轮绑定 baseVersion、requestKey 和真实开发会话；同键重试查询原轮次。流式事件须带 buildRunId/sequence/version，重连补齐，旧事件不得覆盖新版本。
- 原生 Agent 在独立 draft workspace 写文件；宿主收集文件 manifest、内容 hash 与校验结果，在轮次结束时发布完整快照。文件监听可提示“正在修改”，不自动确认上线。构建不能写运行观测或动真实发布。
- 角色表单是对草稿的结构化变更；使用 expectedVersion，正在构建时禁用或排队。冲突保留两份和原输入，提示重新合并，不直接覆盖后写者。
- 查看旧版本只改变预览，不改变当前编辑基线。另设“以此版继续”才提交基线变更；旧版不替代已确认运行版。原型也将历史预览与当前编辑分离；只有“以此版继续”改变后续构建基线。
- 撤回某轮先展示会被撤回的文件和后续依赖，生成恢复快照，不删除对话与版本。原型已有历史查看，撤回动作属于后续生产实施。
- 刷新恢复对话、输入、预览选择和真实构建状态；本地镜像服务首帧，服务器版本为准。无权限、网络断开、工具拒绝和校验失败分别显示具体下一步，不用统一“失败重试”遮掩未知结果。

## 从搭建到运行

主动作“检查并运行”打开同工作区的检查内容，保留聊天：查看选定草稿版本、目标、成员 Agent 与工具能力、真实账号、可执行动作范围、日程。用户确认后才保存/应用文件包、绑定运行 Main/成员和持续目标，并开始首批任务；开发 Agent 写了文件不等于已激活，安装不等于已验证可执行。

停运后仍可聊天搭建新草稿。应用新版本和恢复运行是不同动作；用户未点“恢复运行”就不得续派、发布、取数或自动唤醒。调度默认关闭，只有明确授权时间/时区和业务范围后才启用。原型的运行检查明确不能启动真实团队。

## 技术实施分批

1. 项目 OKR Tab 和 OkrDraftWorkspace，复用全局输入组件、executor catalog 和渲染/原生两种会话；新增开发会话绑定，不复用首页或直接把构建话发给运行 Main。
2. DraftBuildRuns 管理请求、事件重连、停止与未知对账；DraftSnapshots 管理 manifest、expectedVersion、历史读取和差异；OkrPreview 从一个快照投影四个视图。名称是建议，落地先对照现有领域模块。
3. 让 okr-development Skill 输出标准文件包与构建清单，完整 assets 初始化、增量组合 parts、结构校验和引用核对。沿用现有 Connector/HTML 数据桥协议，不新增 HTML 直读宿主 SQLite 权限。
4. OkrReadiness/Activation 绑定确认草稿、真实用户目标与范围、原项目/OKR身份；停止与恢复形成宿主硬门，而不是提示词。支持多个 OKR 前先完成前稿的独立作用域迁移。

## 原型的可操作范围与验收

原型可在首条消息前选择搭建 Agent、发送示例需求、查看模拟构建过程、停止、失败/重试、新增运营、调整数据角色、查看目标/看板/团队/文件、版本切换、刷新恢复草稿、手机聊天/预览切换及运行检查。只识别示例关键词，不是自然语言模型，不实际写项目文件或派工。localStorage 仅用于这个原型的本机草稿，不是生产持久化。

验收记录写入 chat-building-acceptance.md；必须分清原型交互、真实 Agent 构建和真实运行三个层级。
