# Agent 框架与 OKR 业务边界

## 产品原则

同一个 Agent 框架应当支撑宣传、软件交付、成本管理等不同 OKR。创建者和 Main 会通过对话定目标和工作方式，Studio 将确认后的规则写入项目文件。以后调整内容口径、角色分工或运行频率，交付物是项目变更。

| 归属 | 职责 | 宣传 OKR 的例子 |
| --- | --- | --- |
| Agent 框架 | 维护项目和会话隔离、稳定成员、任务轮次、租约、调度、重试、权限、幂等及可信回执。按已确认的要求校验版本、证据和实际结果。 | 模型 503 后，原 Main 按退避机制接回同一任务和成员回执。 |
| 项目定义与 `AGENTS.md` | 记录用户确认的目标、分工、交接、验收、停止与升级规则。指标、来源、时区、周期、角色配置和看板布局写入对应的结构化定义，供运行时读取。 | 确认 X、B 站、数据分析和评论运营怎么交接。定义发布工作量、统计口径、取数时间及独立验收要求。 |
| 项目 Skill、Connector 或平台适配器 | 实现可重复工作，声明输入、输出、证据和错误处理。可复用的平台协议放登记的适配器。项目 Skill 决定如何组合工具。 | 媒体制作、X/B 站操作和评论处理用各自的 Skill。取数用项目 Connector 的 Python 或 MCP。 |
| Main 和成员 | Main 规划、派工、根据项目规则独立验收并决定下一轮。成员按职责执行并提交实际证据、阻塞和回执。 | Main 根据当日数据决定做哪条内容、给谁处理、何时可以进入发布，以及下一轮实验。 |

## 创建时生成什么

1. 从用户需求整理目标、业务角色、交接与验收、运行节奏和失败处理。把团队共用的规则写进项目根 `AGENTS.md`，详细步骤放在手册或对应 Skill。
2. 将需要程序读取的数值和绑定写进 `okr.json`、`agents/team.json`、`dashboard.json`、`schedules/` 和 Connector 定义。调度状态、确认观测与实际完成以宿主回执为准。
3. 保留用户授权及范围的来源。外部动作由宿主核验当前权限、任务、账号和已确认版本。模板、说明文件及群聊均不授予额外权限。
4. 预览并确认项目配置后再应用。后续业务迭代继续用项目文件、Skill 和受管续派，保留原 Main、原成员和历史。

## 现有实现的归属

- `swarm_model_wait.py`、`swarm_settled_route_recovery.py` 的队列恢复、原生会话绑定和轮次证据属于框架。模型路由选择来自已保存的项目绑定。
- `publication/post_journal.py` 与 `storage/publication_reviews.py` 中的动作意图、不可变版本、独立决策、执行回执应抽出通用机制。目标状态、需要的材料和审核标准由已确认项目约定提供。模型输入证据采集按通用工具调用工作。
- `publication/x_channel.py`、`publication/x_public.py` 与 `publication/bilibili_public.py` 对应各自平台适配。平台对象身份和回执核验保留在适配器。发什么、多少条、谁发布、什么时候取数及如何复盘回到宣传项目。
- `publication/media_decode.py` 等解码和转写能力可作为独立、可选的媒体工具。是否需要画面抽样、何种字幕与转写、怎样验收由项目和 Skill 约定。

迁移时保留旧工具契约和在途回执，先明确独立接口，再迁移平台实现和项目策略。已完成的历史不重写。

## 验收方式

- 创建一个软件交付 OKR，仅修改项目规则、角色、Skill 与数据定义即可运行。宣传角色、渠道、频率或发布步骤不会成为它的默认工作流。
- 修改宣传项目的取数窗口或验收口径时，项目确认后由原 Main 在下一轮使用。无需修改框架或重建团队。
- 同一份项目规则无法绕过宿主的授权、隔离、实际结果和幂等检查。停服、模型故障或外部结果未知后，仍沿用原任务与回执。
