一个周期如何完成

  1. Main 选择今天要验证的改进。
  2. 原成员执行，Connector 取数并保存证据。
  3. Main 核验，发布确认数据。
  4. 看板更新，独立验收任务。
  5. 写周期复盘，更新记忆与 Skill。

原子性与迁移

证据/页面资源先按摘要归档，SQLite 在一个事务中提交确认数据、修订和回执。JSONL 与 current.json 是可修复导出，最终态只认数据库确认版本。

现有项目先冻结同一确认修订、备份并逐项对比，再切换存储模式。过渡阶段仍使用原文件权威，不能静默双写两套“当前数据”。

共享群聊，Main 负责协调

收到、读取、回复与任务独立验收是不同状态。Main 自己的回复不会唤醒自己。

检查同一轮次的交付与完成回报

先交付后完成、先完成后交付，都只进入一次 Main 处理。只有交付尚无执行结果时，先保留待处理。

本地同一轮次演示，不代表真实任务已完成。

成员之间如何互通

成员按同群稳定身份定向提问、回复与交付依赖，Main 看到需要协调的内容。成员读各自收件箱；忙碌 TUI 保持待处理，Main 在受管边界续派原成员，不并发注入终端输入。

身份与授权

作者由真实 Main 或当前成员 task/revision/run 绑定。协调回合继承有效的原目标委托，普通 completion 不开放续派权限；团队事件不是新的用户授权。旧实例引用、跨项目目标、过期运行不得覆盖当前路由。人的 say 与 Agent post 保持不同署名。

先定机制，再分阶段落地

模板与宣传项目采用同一套约定；各阶段分别证明交付与真实运行。

阶段交付验收重点
0 · 设计本设计、数据模型、通信状态机权威数据源、确认边界与恢复路径明确
1 · 协作基础原委托、完成回报与持久收件箱交付与完成共用入口；协调不冒充新用户
2 · 通用源库初始化 / schema / 读写 / 备份 Skill真实创建入口取得完整模板；重试与回滚
3 · 确认发布SQLite 修订、迁移和兼容导出故障时原子性；旧事实与去重语义保留
4 · 看板读取标签、表格 SDK、筛选与更新实际 DB 经只读宿主层到 HTML
5 · 日常闭环原团队取数、发布、复盘与 Skill 改进真实本轮证据、独立验收和定时回执

模板与真实项目

模板含完整目录、空库初始化资源、schema 和操作手册；实际运行才创建数据库。

宣传项目按真实来源迁移全部现有数据、页面和回执，保留原 Main、原成员、原任务与历史。

本设计稿不建真实库、不启用调度，也不假称新增通信协议已运行。
