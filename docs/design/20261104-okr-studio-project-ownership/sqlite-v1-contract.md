# SQLite 源库、发布与读取契约 v1（提案）

补充 [数据设计](sqlite-data-design.md)。先把数据版本、文件草稿和 API 兼容定义清楚，再编写通用脚本。

## 源行采用不可变版本

业务 schema 声明表名、逻辑主键、字段类型、可空、单位与来源口径。实际源行由稳定业务键和行版本共同识别；同一 BVID/账号再次取数不能覆盖正在核验或已经批准的旧版本。

| 字段/身份 | 来源 | 用途 |
| --- | --- | --- |
| sourceTable / schemaDigest | 已读取的 schema 版本 | 固定字段与口径 |
| recordKey | 声明的业务键 | 识别同一业务对象/统计窗口 |
| rowVersion | 写入层分配 | 新采集或更正保留新版本，旧版仍可读取 |
| ingestKey / payloadDigest | 调用方持久键及规范化内容 | 重试对账；同键改内容冲突 |
| capturedAt / asOf / sourceIdentity | 当前来源与证据 | 区分取数时间、平台截至时间与账号 |
| evidence | 日期目录的原始文件摘要 | Main 读取实际证据 |

源库读回执明确标为 source/candidate；它不含“Main 已批准”的自声明。受管发布固定 sourceTable/schemaDigest/recordKey/rowVersion，事务开始后仍复核。候选冻结后即使出现新采集，也不会更换被验收的数据。

默认写入采用追加版本。schema apply 可新增表或可空字段，不能自动删列、改单位、换业务键或解释旧行；结构迁移保留原版及校验记录。SQLite 事务不替代已有 Go workspace 准入、账号占用和原任务停止检查。

## save、sync 与数据发布分别处理

当前 `backend/okr/project-files.go` 以文件快照为权威；data-only 发布保留确认的页面摘要。SQLite 模式必须保留这些用户行为：

| 操作 | 读什么 | 提交什么 | 文件后续处理 |
| --- | --- | --- | --- |
| save | 未编辑状态下的提案和当前确认修订 | 验证后的配置/资源摘要与新修订 | 仅在基线未变时生成工作文件，不覆盖后来输入 |
| sync | 捕获的完整工作文件及摘要 | 同一份捕获内容、来源定义与新修订 | 捕获后内容改变则冲突，保留草稿 |
| record / 数据集发布 | 确认配置、固定候选与证据 | 观测/批准行、去重回执与新修订 | 使用既有确认页面，不应用未发布的 HTML 草稿 |
| 导出修复 | 数据库已提交修订 | 修复进度 | 重建兼容导出；不触发第二次发布，不覆盖有冲突的工作草稿 |

资源先内容寻址归档，后进入 SQLite 确认事务。原始证据与页面资源引用不可变字节；事务失败不切换修订。事务已成功但导出失败，原 key 仍返回已提交回执，API 读取正确数据；导出故障是可恢复状态。

SQLite 的 active 标记与确认修订在同一事务提交。新宿主只采用有效 active 库；prepared 候选不接管读取。切换持有项目发布边界，防止旧文件发布与新数据库发布交错。回退必须从最新确认库导出并校验，不能恢复旧备份丢掉新事实。

## 旧数据的“最新”语义必须保持

现有 `dashboard-datasets.ts` 对同一来源按确认追加顺序取最后一条；同一天修正也保留历史。迁移记录每条观测原 ID、sourceKey、原顺序及首次接受修订/序号，不按 capturedAt 最大值重新排序，也不把重复累计快照相加为增长。

当前 metric sourceKey 变更后，旧来源仍留历史，但不会进入新来源卡片。未知继续为 null，证据给出的 0 保持 0；单位不同的数据不得通过重命名历史指标混用。

## 读取层与状态版本

现有指标 SDK 的 id/name/unit/latest/points/source/asOf 语义保持；quality 仍为 observed/unknown，不通过改变旧枚举破坏用户 HTML。

来源健康作为独立可选 freshness 信息：最近尝试、最近成功、错误与状态。一次失败可以改变健康状态，但不把未确认候选变成数值，也不删除最后已发布值。健康事件与数据修订分开，让界面知道“旧值仍有效，但来源本轮失败”。

表格由 datasetId 选择确认定义，返回定义中的 label/columns/unit 与已批准源行版本。请求只接受白名单字段的筛选、排序和分页，绑定 node/project/确认修订；页面不传任意 SQL 或数据库路径。

游标绑定 dataset、查询、项目和修订。修订变化后，旧游标返回明确的版本冲突，页面保留筛选并重读第一页；晚回结果仅在当前页面请求代次仍一致时应用。指标与表格共用项目更新通道和查询缓存，不为每卡新增轮询。

## 模板必须接通实际创建入口

当前 `seedWorkflow` / `seedProjectCapabilities` 使用 Go 中的内置常量，并不会自动复制完整 assets。仅新增模板文件不等于“从聊天创建的新项目”会带上它们。

实施时统一使用 `skills/okr-development/assets` 的规范资源：native Skill、Python 运行包与宿主初始化都从同一份版本化资源生成，不另养手写规则副本。开发 Skill 仍先复制完整 assets 到空草稿，再组合；宿主创建入口用同版本的通用规范/手册/项目 Skill 补齐缺失文件，受管定义由当前确认配置生成，不把占位目标或示例事实写进项目。

现有项目只合并新增部分，保留定制 AGENTS、Connector、页面、成员和历史；不因模板升级覆写或重派。项目根 AGENTS 与宿主 workflow 同步来源，两个入口都能取得完整约定。

## 实现前的验收矩阵

| 场景 | 应有结果 |
| --- | --- |
| 空模板初始化与再次初始化 | 空数据；资源齐全；不生成示例事实或启用日程 |
| 同一 ingestKey 重试、同键改内容 | 原回执；冲突；不增加第二个行版本 |
| 源行更正与 Main 并发核验旧版 | 旧候选仍指向旧版，不静默换数 |
| sync 捕获后文件变化 | 保留用户草稿并冲突，不覆盖后来修改 |
| record 时 HTML 尚有草稿 | 更新确认数据，继续使用旧确认页面 |
| 提交前失败、提交后导出失败 | 前者不发布；后者沿用提交回执并可修复导出 |
| 原观测迁移、sourceKey 变化、同日修正 | ID/顺序/旧事实保留，显示与原接口一致 |
| 分页时换项目/修订 | 不混入旧项目或不同修订数据，保留查询选择 |
| 模板安装后用真实创建入口建项目 | 完整规则和资源实际存在，不以打包清单代替创建验收 |

本契约仍是提案；最终完成需要源库、发布迁移、读取层以及原宣传项目的实际运行证据。
