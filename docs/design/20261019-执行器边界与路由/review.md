## 两轮设计复核

第一轮按常用场景检查分工，第二轮按矛盾输入和副作用恢复检查。已修正：

- 将“先已有会话”改为“先解析显式约束与身份”；用户指定 Claude 但给了 Codex 会话时先选择，不悄悄违背其中一项。
- 将偏好顺序放在能力 / 目标硬约束之后；未知额度不等于不可用，安装成功不等于可登录或可追踪。
- 区分“知道工具名可以直接调用”和“无论耗时都在 Main 做”；长调查、等待、循环轮询均转后台。
- 原 v1 按通用工作 / 工程交付划分；v2 根据用户补充改为按复杂度与能力路由，专业智能体承接复杂研究、原型、PPT、剪辑及工程工作。不能用文件扩展名、工具数量、改动行数或关键词单独决定。
- 不将同项目视为应复用任意旧专业会话；只在用户指向 / 原任务绑定明确时续接，否则新工程任务使用独立工作区。
- 混合任务保留用户原始意图、阶段验收和产物引用；不能把“网页研究完成”当作“代码实现完成”。未知或未验收回报不得自动进入有写副作用的下一阶段。
- 原生 Worker 无法完成任务时先报告缺口，不靠专业智能体替代来逃避权限、账号或资源缺失；跨执行器切换首版不做自动重放。
- 浏览器登录态与文件引用不等于可以转移凭据；记忆提取归原运行时，专业报告作为有来源的外部证据。

## 仍待实施，不是本轮已通过

`cases.json` 当前扩展为 48 条路由与链路验收预期。应先用可控模型 / 执行器验证路由和状态，再用隔离的真实专业执行器验证 cwd、分支、产物与回报。禁止向生产工作会话注入验收任务。

本轮只检查设计内容、链接、页面布局和真机阅读操作，不运行这些路由任务、不发起真实网页研究、不消耗专业执行器额度。验证结果单独记入 `validation.json`，不复用先前派活协议的通过记录来宣称新路由实现通过。
