1. 三层职责，两类后台执行器

Main

普通问答、短且有界的已知 CLI 操作；接收新意图、解析目标和组织回报。

native 后台

自研 Agent Loop：简单查询、有界的文件整理、脚本和数据处理；按能力进行浏览器与电脑操作。

专业智能体

Codex / Claude Code 等自有工具循环、会话、权限与账号；复杂调研、原型、PPT、剪辑等工作中的自主规划、探索、协调和迭代交付。

统一宿主

Python 任务和证据；Go 项目、工作区与会话；Roami CLI 提交与回报。

native 不是模型名称。Main 模型、原生后台模型与专业智能体供应商配置分开；给 native 选一个 Codex 系列模型不会自动变成 Codex CLI。项目、散任务、新项目是去向，不是执行器类型。

任务对象默认路径划分依据
解释概念、简单推理Main 回答无需外部执行；不强制分类、检索和建任务。
列项目、查进度、发消息Main 已知 CLI短且有界；不做长调查、等待任务完成或循环轮询。
天气、单项事实核对、少量公开资料native research简单且有界；纯公开导航与观察可用 resourceOnly，无需代码目录。
简单资料整理、附件转换、已知步骤的小脚本native worker任务路径明确、验证有界；产物写入绑定目录。
需要持续自主执行的复杂任务，如调研、原型、PPT、剪辑等专业智能体按实际规划、探索、协同与验证负担综合判断；任务种类开放，不先由 native 试做。
已有任务或专业会话的继续工作原绑定执行器保留上下文与目标；新增复杂范围按交接规则处理，不因名称或复杂度标签直接重建任务。
用户指定执行器或既有会话按显式约束解析通用研究也可明确交给 Codex；约束冲突时先选择。

当前受管 executor 枚举只有 native / codex / claude。OpenCode / Pi 的会话启动支持不能等同于受管任务、恢复、取消与回报支持；须补适配器契约和隔离验收后才能加入自动路由。

“复杂”到底指什么

复杂任务：目标可以描述清楚，但执行路径不能靠一个已知、有界的流程可靠完成，需要执行者持续自主规划、探索未知、协调依赖，或根据结果反复检查与调整。调研、原型、PPT、剪辑等都是举例，范围不限于这些工作；同类任务也可有不同复杂度。

观察维度简单、有界的表现需要专业执行的表现
规划负担步骤与交付方式已知，可以沿明确流程完成。要自行拆解目标、决定先后与分工，并按中间结果调整计划。
未知与探索输入、规则和来源明确，缺少开放式调查。要找线索、核验冲突证据、定位根因或比较方案，路径尚不确定。
依赖与协同工具调用虽可多次，但接口和依赖固定，能局部完成。多个阶段、素材、工具或环境相互影响，需要保持上下文和产物一致。
验证与迭代结果可以按明确规则直接核对。要持续运行、渲染、试用或对照证据，再反馈修改直至满足交付要求。

判断边界：需要后台工具执行且能用已知流程直接完成并验证，走 native；需要持续自主解决上述执行负担，默认交适配的专业智能体。综合目标、输入、已有上下文和验收要求判断，不用固定分数、步数、时长、Token 数或“满足几项”作门槛。几个串联工具不必然复杂，长文件或耗时批处理也可能有界；一句简短需求也可能包含复杂交付。

同一种工作，为什么有时简单、有时复杂
  • PPT 等文档制作：按给定模板替换几处文字，流程与检查都明确，可用 native；从零组织论证、图表和视觉表达，并渲染后反复修改，适合专业智能体。
  • 调研等信息工作：核对一个已知来源的事实可用 native；多源冲突核验、形成可论证建议并补充证据，适合专业智能体。
  • 剪辑等媒体工作：按已知起止时间截取已知文件，可用具备对应工具的 native；自行选素材、组织叙事、匹配字幕声画并反复预览，适合专业智能体。
  • 其他未列举工作：使用同一组维度判断；没有出现在示例里不能成为拒绝派活或强制走 native 的理由。

Main 在同一轮已有意图判断中给出简短依据，例如“需要自行组织多源证据并随核验结果补查”，而不只写“很复杂”或“因为是 PPT”。判断有充分依据就直接派活；确有关键需求或约束缺失才问选择题。不预先让 native 试做来证明复杂，也不为分类额外调用一个模型。显式指定、既有目标、能力与授权约束继续有效。

2. 先校验约束，再在候选中排序

  1. 解析本次意图和身份：区分新问题、任务进度、已有会话消息、受管任务补充、全新任务。沿用真实 taskId / sessionId，不互相转换。
  2. 收集显式约束：本次用户指定执行器、原任务绑定、会话身份、项目 / 目录、节点、权限与交付要求。明确建新任务才创建；同项目不等于应该续接任意旧会话。
  3. 校验硬约束：目标身份一致、能力匹配、路径可用、来源未遗忘、资源租约、任务预算和授权范围有效。指定 Claude 与 Codex 会话矛盾时，不用优先级静默覆盖；提出选择题。
  4. 确定是否需要后台：普通问答与短 CLI 操作走 Main；需要工具执行、探索、交付或等待的工作进入后台，再按实际复杂度选择执行器。
  5. 选择执行器：显式指定可行时采用；明确的既有任务保持原绑定。新任务按实际执行负担判断，复杂任务默认交给专业智能体，简单工具任务使用 native；不以领域名称单独分流。在满足所需能力的专业候选中，按明确绑定项目的默认、用户有效偏好、节点专业默认排序。复杂任务不要求必须属于项目。
  6. 无合适候选：列出真实缺口及 2–4 个可用选项，不暗中换服务、复制 Key 或创建新项目。候选只有一个且没有冲突时直接执行。
默认配置只负责选择，不扩张授权。记忆中的偏好可参与排序，但不能从网页、工具输出或历史执行器报告获得新的操作授权。额度未知保持未知；安装、登录、权限、额度和生命周期可跟踪性分别记录。

能力匹配覆盖实际可调用的浏览器、文档 / 幻灯片生成与渲染、视频 / 音频处理、素材读取、产物预览和验收；不根据 Codex / Claude 名称臆测能力，也不因为 native 目录有某 Skill 就认定专业执行器自动具备它。缺工具时优先查已有能力、Skill 与 CLI，再按授权补齐或回报缺口；不能静默把复杂任务降级给 native。现有任务中途变复杂时保留绑定，按交接规则处理，不能并发换人重做。

不额外调用一个分类模型再调用 Main。Main 同一轮给出任务类别 / 意图与约束；Python 策略层验证可信元数据并形成决定。不能用关键词路由代替语义理解，也不能让模型自报“已安装 / 已登录”。候选目录按需读取或复用有版本、有过期时间的快照；启动失败以真实回执为准。

3. 调度契约与代码落点

以下为拟新增内部契约，不是当前 CLI / HTTP API。不把 auto 塞入现有 executor 枚举，不改旧调用省略 executor 时默认 native 的兼容行为。新协调入口必须显式给出经过策略层校验的 executor。

RoutingIntent {
  originMessageId, action: answer | cli | send | continue | new_task,
  taskDescription: string,                开放描述，非固定领域枚举
  complexity: bounded | complex,
  complexityBasis: { planning?, uncertainty?, coordination?, verification? },
  explicitExecutor?, targetRef?, requiredCapabilities[], deliverables[]
}
RoutingDecision {
  version: 1, policyVersion, sourceMessageId,
  action, executor?: native | codex | claude,
  targetRef?, complexity, complexityBasis, routingExplanation,
  reasonCode, decisionSource,
  metadataRefs[], constraints[], stageKey?
}

宿主提供来源与标识，模型不能覆写 owner / 原对话。reasonCode 是可本地化的简短事实说明，如 explicit_executor、existing_session、project_default、bounded_native、complex_professional、target_conflict；只保留决策依据，不记录模型私有思维。complexityBasis 保存与本次请求有关的简短事实依据，不保存打分或“命中类别”；routingExplanation 说明所需自主执行负担。上述维度是说明框架，可随新任务扩展，不能变成必须填满的固定清单。任务描述与所需能力开放，能力标识来自实际目录；不能形成“类别名映射执行器”的硬编码表。字段是提案，需以实际契约测试锁定。

dispatch/routing.py             拟新增：纯策略校验、候选过滤与原因
executors/targets.py            补齐 Go 返回的 executor / 项目偏好投影
server/configuration.py        同步 Main 路由指令，不另建分类服务
tools/main_catalog.py          delegate 入口校验；旧协议保持兼容
dispatch/tasks.py              接收已验证决定；继续校验目标和预算
conversation/session_dispatches.py  保留旧会话投递 / reply 语义
conversation/activity.py       兼容投影路由原因与既有执行事实
frontend/src/components/agent/ 在现有过程条目展示原因与回报边界

决定与任务意图 / 派活记录在执行前持久化，绑定稳定来源与幂等键。优先在既有版本化 JSON 中增加可选 decision；若实际需要表结构变更再做正式迁移，本稿不修改候选 schema 或生产库。CLI 回执与模型目录分别由既有服务提供，不直接读写 Go 的 meta.db。

复杂度选择不自动提高预算或权限。当前任务默认 deadline / maxTurns 仍可能不足以覆盖长调研或视频制作；实施时沿既有预算契约配置、检查剩余预算和阶段范围，超出时报告实际原因，不把超时当成功，也不在旧任务仍运行时重派。

非代码专业任务可使用 target={kind:new_session,directory:已知绝对工作目录}；不因调用专业智能体就创建项目、初始化 Git 或创建 worktree。现有 Go createWorkspace 对无 projectId 的普通目录已支持；任务专属产物目录的创建、素材物化、能力探测和验收仍须由各自正式接口与授权落实。复杂 PPT / 视频并不意味着现有执行器已验证能生成它们。

策略校验失败时只返回可恢复的原因，不先发消息再补校验。新受管任务继续沿 task / run / revision；已有会话消息继续沿 dispatchId。已有 native 任务用 steer / revision 续接，不能把原生 branchId 填入 tmux sessionId。

记忆原运行时按用户 / 项目 / 对话范围召回；保留版本与来源。派发相关且允许分享的片段；报告回原运行时后按既有提取规则处理，不直接写记忆表。

附件与产物引用跨阶段传递时，必须确认接收端可访问对应实例、路径和格式。只传一个原生附件 ID 不保证 Codex 能读到；需要受控物化文件或明确支持的读取入口，保留来源、哈希与删除 / 遗忘约束。

native 的 bash 能力不是 OS 安全沙箱。禁止绕过 delegate 私自启动 Codex / Claude 是编排契约，不宣称已经安全阻断所有进程启动路径。若要更强隔离，应单独评审权限和进程运行环境。

5. 复杂任务负责制、分阶段与失败

默认：一个专业智能体端到端负责复杂交付
  1. Main 简短接收，将原始目标、素材 / 证据引用、交付格式、验收要求交给适配的专业智能体。
  2. 专业智能体自行组织调查、制作、工具使用、预览和迭代；按原任务报告进展、阻塞和产物，不让 Main 逐条转发每个工具动作。
  3. 只在确有独立分工价值且宿主已支持时委派辅助任务；不得通过 bash 绕开受管委派，也不假定第三方内部子 Agent 已纳入 Roami 追踪。
  4. Main 继续接收其他问题，展示原任务链路及可信结果。PPT 要核对可打开的文件和渲染页，原型要实际运行并验证交互，视频要核对播放、时长和用户指定的声画要求；不只凭执行器一句“完成”。
显式分阶段：用户要求“先出调研结论，确认后再做 PPT”

将用户要求的阶段作为边界，分别定义验收与稳定阶段键。复杂调研阶段本身也交专业智能体；只有独立简单事实查询才可由 native 完成。前序结果与产物引用满足阶段条件，且用户要求的确认已经获得，才继续后续制作。未验收或 unknown 回报不得自动触发有写副作用的下一阶段；不强制 native 起步，也不把前一阶段完成当作整体完成。

情况要求
派发前明确不可用尚无副作用才能考虑其他候选；显式指定冲突、收费 / 账号变化或范围变化时先给选项。首版不做自动跨执行器降级。
写入 / 启动结果 unknown先查原回执；不重发，不换执行器重跑，不创建第二份工作区。
已有会话 delivered，无回报显示已投递 / 等待回报；不把静止、超时和会话退出解释为成功。
受管任务失败保留 task / attempt 与证据；恢复按现有状态机处理。不能把更换 executor 当作已支持的 steer 功能。
必须换执行器首版通过明确交接：停止 / 对账、保留产物、核实单写资源，再用有前序引用的新任务和稳定阶段键派发。未确认停止禁止接管同 worktree。
停止与新问题停止 Main 回复、取消受管任务、取消旧会话工作是不同动作。旧会话只有投递协议时，不承诺 task_cancel 能停止其进程。

专业执行器的 CLI completed 是执行器报告，verified=false；受管任务 report / lifecycle 和独立验收保持原语义。不把内部工具不可见的专业执行器日志伪造成 Roami 的原生工具事件。

7. 审查结论与实施顺序

已对照源码审查两轮，并按用户补充复核复杂度与产物能力，记录 13 项缺口与处理。执行链已有；以下为原实施顺序；当前已接入复杂度路由、目标身份、项目偏好和路由原因。跨执行器自动切换仍不支持。无需改变既有 Python / Go 分层。

  1. 先补可信目录：统一目标的实际 executor / 节点 / 项目偏好来源，保留未知状态，不阻断合法旧会话续派。
  2. 再接路由：新增纯策略层与 Main 指令，保持七个工具、旧 executor 参数和历史消息兼容；决定先持久化再产生副作用。
  3. 复用执行和回报：明确三种 action 的回执及取消边界，补冲突、未知和重复请求回归。
  4. 补展示与组合：过程条目显示原因，设置使用既有入口；验证复杂调研、原型、PPT 与剪辑的完整交付及必要阶段交接。真实专业执行器仅在隔离会话验收。

功能验收同时核对真实工具 / CLI 调用、目录、工作区、来源与去重，不以最终回复含“Codex”判通过。性能分别记录 Main 接收至首个流式片段、接收至队列接受、后台启动和完成耗时；本稿不写未经测量的延迟承诺。
