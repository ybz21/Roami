第一阶段：真实团队如何运作

一个受管团队有一个协调Main，成员按任务启动；核验与关闭会话分开，完成且无需续作后回收。不重新留下六个长期空闲终端。先做一个材料核验成员，验证现有MP4、字幕、文案和图片，并出实际核验文件。核验后再分配手机发布、浏览器投稿和独立检查，设备动作串行执行。

每项任务写清目的、范围、执行器、目录、输入产物、允许的账号动作、验收条件与前置依赖。制作、上传、提交、审核和公开分别记录。负责人能调整任务，操作者能停止当前执行；暂停派发不冒充暂停已经开始的动作。Main 需要显式核验入口：独立读取本团队当前 run 的产物，再记录核验，不从执行器成功直接跳到完成；有外部发布或用户决定时保留相应边界。上游修订会使旧下游成果失效，必须明确重绑并重做。写操作结果未知时先观察恢复，不换请求ID重复发帖或投稿。

节点模型、路由、参数和费用约束沿用保存的配置。先通过真实模型和执行器验证工具发现、执行、回报、验收和下一轮动作，再扩大并发。当前实现：浏览器有受管资源、观察、动作和本机文件选择能力；手机使用具备完整 CLI 环境的受管专业成员，通过 roami adb 操作明确序列号。两者都保存真实操作与结果，不能把主会话手工操作算作 Swarm 发布通过。

开始时不修改旧历史团队；新建一个明确属于Roami宣传项目的受管团队，保存其真实ID。B站仍需账号登录，等待登录期间继续不依赖授权的核验与开发。所有验收使用实际回执，测试样本单独标记。

Main 如何核验，哪些决定留给人

完成钩子只报告执行结束。Main 通过发现入口取得 roami swarm verify --input JSON，读取本团队当前任务状态和当前 run 的实际产物；完整读取发生在同一 Main turn，且早于核验所在的 assistant 消息，不能在同批调用中假装已经看过结果。

核验请求明确携带 swarmId、taskId、revision、runId、accepted、checks 和 artifactIds。宿主核对真实读取回执、完整文本摘要、文件完整性、声明的 MIME、当前运行与依赖门槛后，复用已有任务确认逻辑；记录 Main 身份及检查内容，区别于用户手工确认。旧上下文、其他 Main、成员自验、只读元数据、缺页或缺件不能放行。

这个窄入口支持文本报告的通过或退回；二进制仅有元数据不算看过媒体。声明 external_action 的任务由该入口拒绝，保留既有宿主回执和用户决策路径。需要用户登录、确认具体发布内容或决定实验方向时，明确提出这一项；普通成员交付无需让用户替 Main 做每一次技术核验。

第二阶段：面板是不是低代码HTML

当前面板是React按JSON定义渲染的HTML与图表，可视为配置驱动的展示层。展示协议应独立于对话：无论定义来自手写代码、脚本还是未来的模型，都能展示同一组运行结果。

优先复用已经生成的dashboard.json、日期指标、任务事件、产物和发布回执，注册组件负责目标、趋势、任务状态与媒体预览。现有 dashboard.json 使用 keyResults、metricTrend、nextAction 等注册组件；当前状态读取同一 Swarm 的任务与本轮产物，文件页直接看项目目录。生成的 HTML 报告可以作为产物预览，产物预览是静态隔离展示，不等于已开放任意脚本看板。需要更自由的展示时，可扩展为有清单的HTML展示包，声明版本、入口、数据绑定与允许的动作；这是第二阶段的扩展设计，不代表当前已经执行任意HTML。

HTML扩展由隔离容器展示，通过受约束的数据通道获取本项目的只读快照；控制意图交给宿主调用已有受管任务接口。展示页面不取得账号凭据、宿主Shell或任意数据库权限。宿主保留状态、来源、暂停和验收的最终控制。由此先解决“已有东西如何看”，再解决“如何生成东西”。

第三阶段：模型只生成可验证的定义

对话先确认目标与指标口径，再确认来源，最后生成绑定真实数据的配置。模型可以动态决定KR数量、方法组合和看板组成；保存仍走现有项目作用域、revision和记忆hash校验。输出必须落入已经验证过的执行和展示能力，没有工具成功回执不称已保存，没有平台回执不称已发布。
