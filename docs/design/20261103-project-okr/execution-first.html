第一阶段：真实团队如何运作

一个受管团队有一个协调Main，成员按任务启动并在结束后释放；不重新留下六个长期空闲终端。先做一个材料核验成员，验证现有MP4、字幕、文案和图片，并出实际核验文件。核验后再分配手机发布、浏览器投稿和独立检查，设备动作串行执行。

每项任务写清目的、范围、执行器、目录、输入产物、允许的账号动作、验收条件与前置依赖。制作、上传、提交、审核和公开分别记录。负责人能调整任务，操作者能停止当前执行；暂停派发不冒充暂停已经开始的动作。写操作结果未知时先观察恢复，不换请求ID重复发帖或投稿。

节点模型、路由、参数和费用约束沿用保存的配置。先通过真实模型和执行器验证工具发现、执行、回报、验收和下一轮动作，再扩大并发。当前已知：浏览器有受管资源、观察和动作能力；手机CLI可用，但原生运行时中的发现、任务绑定、设备控制和回执链路需要核对并补齐，不能把主会话手工ADB操作当作Swarm已经能操作。

第二阶段：面板是不是低代码HTML

当前面板是React按JSON定义渲染的HTML与图表，可视为配置驱动的展示层。展示协议应独立于对话：无论定义来自手写代码、脚本还是未来的模型，都能展示同一组运行结果。

优先复用已经生成的dashboard.json、日期指标、任务事件、产物和发布回执，注册组件负责目标、趋势、任务状态与媒体预览。需要更自由的展示时，可扩展为有清单的HTML展示包，声明版本、入口、数据绑定与允许的动作；这是第二阶段的扩展设计，不代表当前已经执行任意HTML。

HTML扩展由隔离容器展示，通过受约束的数据通道获取本项目的只读快照；控制意图交给宿主调用已有受管任务接口。展示页面不取得账号凭据、宿主Shell或任意数据库权限。宿主保留状态、来源、暂停和验收的最终控制。由此先解决“已有东西如何看”，再解决“如何生成东西”。

第三阶段：模型只生成可验证的定义

对话先确认目标与指标口径，再确认来源，最后生成绑定真实数据的配置。模型可以动态决定KR数量、方法组合和看板组成；保存仍走现有项目作用域、revision和记忆hash校验。输出必须落入已经验证过的执行和展示能力，没有工具成功回执不称已保存，没有平台回执不称已发布。
