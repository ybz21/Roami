产品与交互

外层仍是「OKR 与看板 / 具体活动 / 文件」。工作台内改为「OKR / 数据看板 / 当前状态」。OKR 讲清目标、长期与短期KR、达成手段和交付标准；数据看板展示真实日期、增量、采集来源和缺口；当前状态回答谁在做、产出了什么、哪些已验证、下一步由谁决策。具体活动打开同一蜂群、任务板和群聊；文件打开同一项目目录。

搭建态：口述目标→Main提出KR、方法与指标→用户确认→配置真实来源→保存一个有效修订。运行态：方法分配给真实成员→执行→产物/采集回填→独立验收→复盘→修改下一轮方法。成果不只看自述，状态必须由证据更新；短期实验与长期KR分开，失败、缺数和待确认均可见。

贯穿故事：宣传Roami

目标是让更多开发者了解和使用 Roami，已确认的长期KR为八周 star 净增100、fork净增20；历史首日基线11/5，只说明当时采集值，不伪造后续增量。现有短期KR是两渠道文案与制作计划验收2/2，达成只表示文本已验收，不能据此称视频已经制作或账号已发布。

手段一：在X发布图文；交付是最终文案、真实产品截图和待发/已发回执。手段二：每天一个带配音的Roami技巧；交付是录屏原片、配音、校时字幕、封面、可播放MP4，以及B站草稿/提交/发布确认。两个方法都关联增长KR，但发布数量是过程指标，star/fork是结果指标，曝光、点击、完播率、平均观看时长为诊断指标，不能互相冒充。

今天没有成片时，当前状态必须显示制作未完成；成片通过后显示已产出、待平台操作；打开上传页不算发布成功；草稿、提交审核、公开可访问分别记录。发布前用户查看具体成片和文案，最终账号动作以明确授权为准。明天采集真实反馈，团队保留哪种主题、风格、开头有效的依据，再设计下个实验。

其他故事与复用

科技博主可把增粉、点赞率、完播率、平均观看时长作为不同层次的指标；方法是选题、脚本、制作、发布、复盘。仓库维护可把可用功能、p95延迟、错误率和采用情况作为KR或诊断指标；方法是实现、测试、提交代码与AB实验。两者均使用同一套定义、证据、共享记忆和修订，不把发帖/提交代码的动作本身当成业务结果。

项目目录与数据职责

<project>/.roami/okr/
  okr.json                    目标、周期、KR、指标、方法、团队绑定
  dashboard.json              声明式组件、指标绑定、顺序与展示定义
  connectors/<id>/           来源清单、实现代码、权限与配置说明
  agents/                     按需Main与团队配置、指令；模型继承节点设置
  memory/team.md              团队共同知识与已核实结论
  memory/decisions.jsonl       预留决策记录文件；当前团队知识以team.md为准
  data/observations.jsonl      带日期、来源、采集时间的原始观测及更正
  data/reviews.jsonl           复盘及引用的证据修订
  evidence/                   不可变复盘快照；交付文件另由任务产物库保管
  state/                      已确认修订快照与原子当前指针

定义文件是可编辑工作稿，确认后的修订快照是运行和展示依据；通过同步入口按 revision 校验后生效。页面保存也走同一提交机制。SQLite承担索引、查询加速和旧数据迁移，不与项目文件形成双重真相。只为已启用OKR的项目生成文件包；首次迁移保留原数据与历史，文件已迁移后缺失或损坏必须提示，不能偷偷回退旧缓存覆盖新事实。

connector按来源类型声明实现、输入与输出；现有manual没有自动取数代码，GitHub内置来源导出准确实现及说明，不能假称修改本地源码就已执行任意脚本。扩展浏览器connector要声明账号/页面/字段/单位/日期与最小能力，经确认后绑定真实来源；登录凭据仅以节点凭据引用，不写进项目目录或版本库。

团队组织、记忆与验收

Main负责理解目标、分解和调度，执行成员负责具体产出，数据成员负责真实采样，复盘成员基于已验证证据提出下一轮方法。成员共用任务板、群聊和团队记忆。记忆保留事实、约定、教训、实验结果和待验证假设；群聊保留讨论过程，原始证据保留不可变来源，三者不混用。

@leader投递给绑定的Main对话，不创建另一个冒名指挥。成员进入任务时获得相关目标、方法、来源与记忆，不能靠读取未知宿主路径绕过权限。产物要求使用结构化声明：artifact需要真实文件与完整性校验，external_action需要具体外部动作与确认，纯只读研究不无端要求媒体文件。任务执行、产物生成、验收、外部提交和业务效果分别计量。

技术架构与落地边界

Go项目OKR层负责文件包、修订提交、旧库迁移和CLI同步；前端从同一workspace契约读取目标、方法、声明式widget与文件状态；Python managed Swarm负责指挥投递、成员任务、共享记忆与证据门禁。复用既有认证、任务回报和模型路由，不重新造任务台账，不把用户项目文件当成可绕过工具准入的系统指令。

实施拆为项目存储、运行时团队、工作台前端三个可并行职责，最终由主会话做集成、迁移、真机与真实宣传产物验收。设计中的接口字段以随代码验证的最终契约为准；实现和限制将在本页末尾记录，未完成的外部操作保持真实状态。

按顺序看一次完整交互

故事线一：聊目标，先确认想改变什么

我说：“宣传Roami，先做X图文，再每天在B站讲一个带配音的技巧，希望star和fork增长。”目标对话按需创建新的Main实例，并绑定本项目。它提出长期KR、短期验证、渠道方法和候选指标；粉丝、完播率、平均观看时长等是需要确认口径与来源的候选值。没有后台数据时只显示未知，不替用户编基线。

故事线二：从KR生成方法和看板

我确认长期star/fork目标，Main为两条方法分别写交付标准：X是正文、真实图和发布回执；B站是脚本、录屏、配音、字幕、MP4和平台回执。模型生成definitions和dashboard的受约束JSON，KR与指标数量由本次讨论决定；界面用已注册组件渲染。先预览与确认，才通过项目受管工具保存一个新修订；没有工具回执就不显示已保存。

故事线三：接上实际数据

Main先分析每个KR需要什么指标，再询问或检查来源。GitHub可用已内置的公开仓库采集，账号后台则先检查登录与可取字段。来源说明、口径和代码位于connectors目录；尚未绑定的后台不标已连接。浏览器或手机读到数据后可由授权成员显式回填，并附采集窗口和证据说明；这不等于任意本地脚本已自动运行。

故事线四：执行、验收、复盘、继续执行

运行团队共用一个任务板、群聊和记忆。Main按方法安排执行、取数和复盘成员，集成项依赖已验收的上游修订。写同一工作区受现有租约协调；没有必要为每个目标留一批空闲终端。产物生成先进入待验收；媒体必须有实际文件，发布还需要检查具体回执。复盘将事实、假设、下一步区分写入共享记忆，下一轮从相同来源和日期继续观察。

长期运转依赖持久化任务、事件与已配置的每日触发；没有每日计划就不宣称会自动日更。模型按事件或计划唤醒，搭建对话关闭只停止自己的实例。用户随时按看板的真实结果调整方向。

确认后的写入如何真正发生

入口边界与产物
按需目标对话创建对话时传projectId，服务端先通过已有项目CLI校验注册项目，再把项目与conversation原子绑定。模型不能在工具参数中替换项目ID，不创建额外Swarm来获得写权限。
project_okr_context / project_okr_update仅绑定的Main对话可用；读取真实扁平Workspace，按现有revision或记忆hash调用save / collect / record / review / sync / memory。未设OKR返回saved=false，首次保存才生成文件包。
运行团队swarm_project_context / swarm_project_update绑定团队的已注册项目；归档团队不能再借此修改目标。@leader投到原Main，成员建议进入同一群聊；仅Main写团队记忆，用户也可在界面显式编辑。
版本与并发配置提交采用revision和原子快照指针；记忆采用expectedSha256。草稿和原始hash一起保存在本机，重新打开仍保留原版本，冲突时先比较当前内容再明确合并，不能用新hash悄悄覆盖旧草稿。
数据与执行KR、方法和widget在项目文件中；原始日期观测和复盘快照可追溯。任务、群聊、调度和产物验收继续使用现有运行时账本。agents/main.json是角色声明，main.md是指令；swarm.json绑定团队，不复制另一套成员任务库。

Python新增schema16团队记忆/交付声明、schema17目标对话项目绑定；Go备份兼容上界同步为17并拒绝18等未来版本。模型、路由、费用、限额和历史账目均沿用节点原设置。
