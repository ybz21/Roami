依赖更新后，旧验收不能充当新结果

保留原任务、执行器、目录和旧证据；依赖真正变更后，要求这个任务的新版本重新执行并验收。重绑只改变输入关系，不自动开任务、不自动重跑，也不直接宣布完成。

用户故事

宣传团队的素材成员已把视频推进到版本 3。复核成员的版本 2 虽然验收过，但当时读的是素材版本 1。Main 把复核依赖绑定到素材版本 3 后，工作台仍应显示“依赖待复核”。只有沿用原复核任务继续到版本 3、读新素材并完成验收，团队才可能完成。

产品行为

  • 同一依赖集合再次保存、同一请求重试，不增加复核门槛。
  • 更换依赖成员、版本、产物或删除依赖，都会改变已有任务的输入。门槛为原门槛与“当前任务版本加一”中的较大值。
  • 待验收的旧结果不能靠点击接受绕过门槛。拒绝旧结果仍可记录，旧报告和文件可以继续追溯。
  • A 已更新而 B 尚未重绑时，C 即使依赖已验收的旧 B，也必须阻塞。传递依赖不能只看中间任务的原始成功状态。
  • 保留现有 blocked 状态及 SWARM_DEPENDENCY_NOT_VERIFIED 原因，不新增布局，不把原始任务的历史成功误写为新的当前成功。

持久结构

schema 18 在 swarm_work_items 新增 required_task_revision INTEGER NOT NULL DEFAULT 1 CHECK(required_task_revision >= 1)。它是工作项对本身任务版本的门槛，与依赖边绑定的上游版本分别保存。门槛不放进错误字符串、日志或易丢失的内存。

任务版本低于门槛时，工作项及所有传递下游均不能视为就绪。已有成功记录、attempt、artifact、任务 ID、执行器和目标目录均不重写。恢复进程只重新读取门槛，不创建新任务。迁移保留既有数据并默认门槛为 1；无法凭迁移推断历史版本缺失的依赖来源。

事务与并发

  1. SwarmPlans.dependencies 在一个 BEGIN IMMEDIATE 事务内检查当前任务停止证据、变更依赖、检查环、比较规范依赖集合、提高门槛并记录回执和事件。
  2. TaskDispatcher.complete 在实际写结果的同一事务内复查当前任务版本、等待验收状态、当前 run、待执行 steer，以及工作门槛和完整传递依赖。验收前的异步文件检查不承担并发裁决。
  3. 如果验收先提交，随后重绑会把门槛提高并阻塞旧成功；如果重绑先提交，旧结果的接受请求会被拒绝。两种顺序都不能把团队留在伪完成状态。
  4. 仍在等待的 verifier 返回成功时也必须经过同一护栏。依赖已变则保留待验收状态，不能覆盖新门槛；旧证据不被删掉。
