# 会话关闭阻塞修复

2026-11-10。修复原生会话长期关闭中，以及 detached HEAD worktree 无法提交关闭。分支 `fix/session-close-stall`。

## Product Design

关闭原生会话是归档会话，不是确认任务成功或确认历史动作结果。任务及其后代已停止、没有运行回合／工具且没有占用或隔离资源时，允许保留未知历史结果并归档。关闭后原任务、执行、工具记录及交付物仍可核对，原输入围栏转为已关闭，不释放工作区保护，也不重放动作。

真实执行、活动资源租约、隔离资源或明确未停止的输入仍阻止关闭。CLI 关闭仍需原执行回执，未知 CLI 执行不能借原生归档路径绕过身份和停止校验。

分离 HEAD 是合法工作区状态。关闭预检和清理使用实际 HEAD、仓库身份及文件快照；没有分支时不尝试删除任何原分支。真实变更仍要求重新确认。

## User Stories

- 旧原生任务已结束而浏览器回执缺失时，我可以关闭会话，历史不确定结果继续保留。
- 会话仍有真实执行、未确认停止的输入或资源占用时，关闭等待停止，不提前清理。
- worktree 在合入后分离 HEAD 时，我仍能关闭会话并删除已确认的 worktree。
- 我确认后又出现文件变更时，新内容保留；删除 detached worktree 不会误删原分支。

## Technical Design

### 原生归档

`dispatch/task_sessions.py` 原来先判断 `finished_ms`；未知历史执行常没有完成时间，提前落入每秒重排的 `TASK_SESSION_BUSY`。历史未知工具也被与计划／运行工具一起重试。

归档保留同一个 `TaskSessions` 所有者、任务版本校验、父子顺序、资源检查、执行中检查、关闭事务与事件：

1. 非稳定任务继续等待停止；`inputStopped=false` 明确阻止关闭。
2. 原生会话不要求历史执行已确认结果或补造完成时间；CLI 继续要求这些回执。
3. 原生根会话自身的历史未知调用保留原样；活动回合和计划／运行工具仍阻止关闭。
4. 后台按后代优先归档原生子会话，父会话只跳过已关闭后代的未知历史；未关闭后代、CLI 未知执行及待续派工作仍受原校验保护。
5. 成功只写关闭记录及关闭事件，不改任务验收、执行结果、工具状态或资源围栏。

### 分离 HEAD

`backend/worktree/lifecycle-snapshot.go` 的确认快照与 `LifecycleDetails` 都要求 `symbolic-ref HEAD` 成功，导致 detached worktree 的预检缺少 `snapshot`；提交时被错误归为 `LIFECYCLE_CONFIRM_AGAIN`。

统一用 `symbolic-ref --quiet HEAD`：只有明确退出码 1 代表分离 HEAD，以空分支保存；其他 Git 错误照常返回。HEAD、Git 目录身份与全量文件内容摘要仍参与快照。已有分支摘要不变，已有空分支删除保护继续生效。

### 生产排查

只读接口与一致性数据库快照确认三条旧原生会话：两条最新执行未知且无完成时间，另一条最新执行已结束但旧回合有未知浏览器调用。没有属于这三个任务的资源租约或运行回合，关闭作业却每秒重排。当前安装模块与修复前源码哈希相同。

另一条关闭失败会话的工作区是干净的 detached HEAD；生产预检返回工作区身份但没有确认快照。修复代码对该真实路径只读探测后成功返回快照、空分支和受管工作区身份。

原始生产快照仅在受限本机目录回放；公开记录不含用户提示词、原始参数或整库。

## 追加排查：Main 派发排队

这是另一组 CLI 执行，不能用上述原生关闭修复宣称已恢复。

默认与生产调试接口返回值均为 Main 对话并发 2、Worker 并发 3；同一会话分支仍串行。CLI 的全局名额按 `preparing/running/cancelling` 任务计数，与用户是否关闭已完成会话无关。排查时恰有两个取消中任务、一个运行中任务，三个最新执行都为 `unknown` 且没有结果，因此新的调研任务持续排队。

只读核对执行器状态与会话身份：

- 两条旧会话严格解析返回不存在，回执为 `SESSION_BINDING_UNAVAILABLE`；捕获的进程启动身份均已不匹配，原 cgroup 也已不存在。
- 另一条会话仍在，回执为 `SESSION_START_UNTRACKED`；保留的进程与 cgroup 仍存在，屏幕显示任务在等待用户处理。不能为释放旧记录而直接杀掉该会话。
- 调度器仍将这三条记录计入 `external_running`，外部执行观察没有把它们归入可结束的任务状态。单个任务的未知结果因此阻塞了全局新任务。

后续修复应由 Go 执行器提供绑定原执行身份的停止证据，Python 接收后将已停但结果未知的任务转为需要处理，释放执行并发；工作区保护与未知动作结果继续保留。只有真实执行占执行名额，关闭、清理及用户验收不应继续占用。观察失败本身不能作为停止证据，也不能直接忽略所有 `unknown` 执行，否则会漏算仍在运行的进程。本次没有改动该准入策略或伪造执行回执。

## 追加修复：失联执行释放全局名额

### Product Design 与 User Stories

- 收尾入口只列仍在准备、清理或需要恢复的事项。已清理、创建就绪及已归档的记录保留在原始台账，用户已打开的详情和未发送草稿继续可用。
- 原执行在本机已不存在时，其结果仍然未知，转为需要处理；不要求用户先关闭它才能派发无关的新任务。
- 活着的旧会话、捕获进程、无法观察的进程组或不同主机绑定继续保守等待，不能靠忽略全部 unknown 记录放开并发。

### Technical Design 与模块架构

Go `agentexecution/session-execution-loss.go` 只在原会话精确查询确实不存在、记录的专用 cgroup 已空或消失、所有捕获 PID 与启动标识都不再匹配时，返回 `SESSION_EXECUTION_MISSING`。校验当前主机绑定（旧记录缺少绑定时仍只报告未知），重复观察会话和 cgroup，并复核原回执未变；并发到达的真实结果优先。

这是一份只用于恢复本机准入的未知观察，不是停止或副作用确认：`inputStopped=false`、`outcomeKnown=false`、无完成时间。不写 Go `result.json`，不改原绑定，不释放工作区 writer，不自动重放。Go 回归显式验证其他任务仍得到 `WORKSPACE_OUTCOME_UNKNOWN`。

Python `Tasks.report` 将含未确认标志的执行保持为 `unknown`；既有验证流程将任务转为 `interrupted`，因此既有调度器自然释放执行名额。原任务、原版本、原 launch key 和工作区保护继续保留，迟到的真实结果仍能补回。Main 默认并发 2、Worker 默认并发 3 不变，不通过提高并发掩盖旧记录。

前端 `SessionLifecycleInbox` 使用现有未结束操作集合渲染列表，并过滤已关闭的原生记录。完整操作集合不删减，仍为已选详情与草稿通知提供数据；中英文空态改为“暂无待处理事项”。
