# 旧会话记录分批加载

## 产品设计

打开会话先显示最新 50 条。点击“加载更早的消息”时，每次向前取 50 条并追加到顶部，保留已读内容和输入草稿。新消息仍沿最新位置增量读取。沿用现有对话界面，不新增工具栏。

空记录只显示“暂无对话记录”，不推断 Agent 刚启动。执行状态不确定时，身份校验通过的历史仍可只读展示。

## 用户故事

- 旧会话已有大量记录时，直接查看最近内容，不等待整卷加载。
- 按需逐批回看历史，保留当前阅读位置，读到开头后隐藏入口。
- 较早记录加载失败时，已加载消息与草稿保留，并能重试相同位置。
- 任务执行处于未知状态时，仍能阅读已有历史；读取不改变执行状态。

## 技术设计

| 模块 | 行为 |
| --- | --- |
| `backend/api/transcript-read.go` | 从尾部或 `before` 字节游标之前向后读取，避免重新读取较新的记录 |
| `backend/api/transcript-window.go` | 默认批次 50 条，根据实际保留消息的行首生成下一批游标 |
| `backend/api/claude.go`、`codex.go` | 首屏和文件截断重置均使用有限窗口；返回独立的 `before` 与 `nextOffset` |
| `frontend/src/components/chat/useTranscript.ts` | 首次响应直接渲染；较早消息前插，最新游标保持不变；文件切换后忽略过期请求 |
| `internal/agentlifecycle/session-provider.go` | 历史读取复用会话、目录、主机和进程身份校验；执行准入继续要求原有生命周期状态 |

Claude/Codex 历史分页不再通过扩大尾部窗口重取所有已加载消息。Pi/OpenCode 和较旧服务端保留既有窗口协议兼容路径，首屏同样为 50 条。

排查发现两个独立问题：首次找到文件的响应被前端丢弃，等待下一轮；执行状态为 `unknown` 的受管会话被历史读取接口拒绝，即使转录文件存在。本机确实存在后一种状态，但用户截图未包含会话身份，不能断言截图仅由这一原因导致。

## 验收

- Claude/Codex 各 275 条真实格式的合成转录：默认首屏恰为最新 50 条，逐批回到开头，无遗漏、无重复；过期增量游标重置仍受批次限制。
- HTTP 接口回归：未知执行状态仍返回身份匹配的 Claude 历史，生命周期文件逐字节保持不变。
- 身份回归：执行准入继续拒绝未知状态；执行器、PID、目录、主机、进程启动标识或身份凭据不匹配时，只读入口同样拒绝。
- 前端回归覆盖首次响应、独立的前后游标、轮询后分页入口保留、失败重试和文件替换。全部 237 个测试文件、1752 个测试通过。
- 完整质量门通过：Go 全包测试、前端 typecheck / i18n / hover / 生产构建。按影响范围未运行 Python runtime / Skill 检查。
- 组件验收夹具挂载实际 `ChatShell`、消息渲染器和转录 Hook，使用合成 API 响应；不是线上原会话的部署验收。桌面 1280/1920/2560/3440 CSS px：首轮 1 个转录请求、50 条消息，无文档滚动或横向溢出。
- Redmi Note 8 真机：compact/coarse，触摸滚动生效；真实点按较早消息入口后 50 条增加到 100 条；输入框命中、聚焦和输入通过。
