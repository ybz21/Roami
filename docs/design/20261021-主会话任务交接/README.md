# 主会话任务交接

对应 #405。主模型省略可选的 `requestComplete` 后继续推理，既拖延响应，也可能反复查状态、重启任务或把旧结果当成本轮成果。

## 产品与用户故事

- 单项查询交给任务后立即结束本轮，由任务卡展示进度，完成事件负责回报。
- 多项请求显式保留未处理部分；不能遇到第一次派发就结束。
- 用户另发进度问题时允许读状态；另发查询时需要本次取证。
- 保留用户要求的详细结果和原始内容，不靠截字或固定答复缩短回复。

## 技术方案与审查

1. `delegate` 和 `task_steer` 要求布尔字段 `requestComplete`：未完成的多部分请求填 false，最后交接填 true。漏填在任何写入前拒绝，返回纠正说明，不能默认为 true 丢失后续工作。HTTP 任务 API 不变，模型与 CLI 使用同一 schema。
2. 同一 turn 中已成功接受的任务回执是持久交接证据。后续查状态和再次续作均拒绝并返回交接提示，不再读取成果，也不取消正在执行的任务。无指定 ID 的列表排除已交接任务，仍能发现其他请求涉及的任务；新用户 turn 不受此限制，失败或未接受的调用不算交接。按任务 ID 判断，不做自然语言关键词分类。
3. 最后交接成功且声明完成时结束 Main；允许同批先读资料再派发。批内失败、非任务写入、尚有未处理部分均不能意外结束。
4. 状态读取默认只作进度回答；显式取详细结果使用 `includeResult=true`，返回当前 revision 的完整执行器报告。进度读取只向下一次模型请求提供本轮消息与状态，不注入历史助手报告；本轮多项请求仍完整保留。`includeResult=true` 同时恢复历史引用，不能靠截断最终答复缩短文字。状态读取后重新声明回答范围，新查询仍须派发取证。
5. 新查询与回顾仍由模型根据原始用户意思判断，现有取证时间与来源校验保持独立；完成回调不能自行重新派发。

审查重点：分批/并行多任务不能漏项；停机恢复不能丢交接；跨轮用户干预不被拦；忘记的上下文不重新暴露；任何失败不伪装为接受。自动化覆盖这些边界，Chrome 端到端用真实配置模型、保留原失败对话复测，不替换模型或添加题目暗示。
