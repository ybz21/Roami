# 会话刷新负载：先消掉逐会话轮询

## 问题与证据

2026-10-20 在 Roami 托管 Chrome 的正式构建中观察到持续请求。静置设置页、首页、会话列表
各 30 秒，分别发出 31、41、543 次请求；没有发生整页导航。14 个会话的列表中，420 次请求
来自逐会话的 Claude / Codex 检测与抓屏。

`Sessions.tsx` 每 3 秒创建新的 `list`，依赖 `[list]` 的两个 effect 随即重新启动并立即请求，
原定 4 秒和 5 秒的周期因此提前重跑。后端探测还会启动 tmux、扫描进程；worktree 查询会
执行多条 git 命令。这是数据更新方式的开销，不能仅凭请求体小就判定成本低。

## 本轮走通的路线

1. **复用批量事实源。** 列表的 Agent 种类取 `/sessions/agents`，等待状态取
   `/sessions/overview` 中后台探测循环已汇总的 `waiting`；删除列表内逐会话检测和抓屏。
   详情页用于交互的 PromptPanel 不变。
2. **共享订阅。** `createSessionPoll` 让同一页面的消费者共享一次请求和一份快照；未变化的
   数据保留引用。App 与列表共用 `useAgentKinds` / `useSessionOverview`，按当前机器隔离，
   不累计保留已访问机器的快照。登录确认前不开启 App 的会话探测。
3. **管理生命周期。** `pollWhileVisible` 在文档隐藏、最后一个消费者卸载时中止请求并停止
   定时器，回前台立即刷新。请求完成后才安排下一次，15 秒超时，失败指数退避至最多 60 秒。
   会话页的列表、注解、竞赛、编队与仓库计数采用同一机制。App 的几处全局轮询也跳过隐藏页。
4. **分配刷新预算。** 会话列表仍为 3 秒；批量种类为 6 秒；批量活动为 5 秒。仓库计数依赖
   稳定的仓库集合，30 秒刷新，不再被每次注解更新重新触发。编队归属保留 8 秒周期。
5. **用同一方法复测。** 对生产构建、相同 14 个会话、无终端标签的页面，等待首屏 5 秒后
   采集 30 秒的 CDP 网络与 Performance 指标。优化前后共用同一批后端数据，不使用开发包
   的内存作为正式版结论。

## 结果

| 30 秒样本 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 请求总数 | 543 | 111 |
| 逐会话 Agent 检测与抓屏 | 420 | 0 |
| `/sessions/agents` | 10 | 5 |
| worktree 查询 | 16 | 4 |
| 整页导航 | 0 | 0 |

请求减少约 80%。后端在复测期间更新了版本；已核对相关刷新与状态接口源码未变化。
采样包含 DevTools 开销，且服务还有其他客户端；不把这个结果写成整机 CPU、Chrome 总内存
下降 80%，也不据短时堆采样判断内存泄漏。

## 验证与边界

- 自动测试覆盖共享请求、未登录禁用、隐藏中止及恢复、慢请求不重叠、切换机器隔离、失败
  保留快照与退避。前端全量测试、类型检查、i18n、hover、生产构建及仓库 quick 门禁通过。
- 浏览器用隔离响应验证等待状态出现、筛选、解除；正式数据用于资源采样。桌面无横向溢出。
- Android 真机验证 compact / coarse、顶栏、四个底部导航、设置与项目间真实触摸切换；
  真实滑动使内容滚动位置从 0 变为约 349px，页面没有横向溢出。
- 后台状态依赖服务端已有的探测周期，再叠加最多一个正常批量轮询周期；详情交互仍走原来的
  低延迟检测。失败时保留最近快照，不把网络失败展示成状态清零。
- 本轮在独立 HTTPS 预览验证，未部署工作区改动，也未重启正式服务。

## 后续顺序

先把项目详情、手机已有的独立状态轮询接入同一订阅，再处理编队详情的批量归属数据，最后
测量并优化隐藏终端的 PTY 处理与渲染。每一步都保留请求量与行为对照。事件推送可以进一步
减少轮询，但需要补齐断线追赶与低频恢复机制；不把全站一次改成 SSE 作为本轮前提。
