# 计费明细保留与日账归并

## Product Design

逐笔明细保留结算完成后的 48 小时，超期后按原账期日期、时区、模型、角色、智能体和 RSI/其他来源合并。费用、输入/输出/缓存 Token、请求数、失败数、费用未知数与用量未知数保留，逐笔请求 ID、响应元数据与核账理由到期清理。处理中请求不清理；延迟结算从结算时重新计时。未知费用不补零，仍只提示而不阻断调用。

历史日期已有归并数据时显示日汇总，明确不再提供完整的逐笔/小时明细；不会把缺失小时数据显示成零。来源、智能体、模型及多币种统计保持一致。超过保留期的未知费用只保留日汇总异常数，不再支持逐笔核账。

## User Stories

1. 我能查近两天的 Token、请求 ID 和错误详情。
2. 我能长期按天查看费用和 Token，不因清理而少账或重复计费。
3. 旧记录不会按每次模型请求持续累积，且异常或晚到回执不会被误删。

## Technical Design

Go 网关 schema v5 增加 `gateway_daily_usage`。归并每批最多 1000 笔，在同一 SQLite 事务内累加日账并删除对应明细；失败整批回滚，并发归并与重复执行保持幂等。费用保持整数纳单位，溢出拒绝写入，不转浮点数。索引覆盖已结束记录的保留期扫描。

网关持有服务 socket 锁后，恢复中断请求，再执行一次归并；常驻服务每小时继续归并，停服时停止定时器。维护错误记录日志并等待重试，不额外阻断模型服务。没有在 Python 中加入限额或清理逻辑。

统计联合读取未过期明细与日账，所有可加指标再次按既有维度分组；全部历史的起始日同时查两张表。历史单日已有归并数据时返回 `dailyAggregated`，前端以日数据呈现。配置保护仍计入日账中的未核清费用，归并不绕过既有币种/时区约束。每日额度仍按当天逐笔已知费用执行，当天记录不进入 48 小时清理窗口。

删除后的 SQLite 空闲页由后续请求复用，不做每小时全库 VACUUM；磁盘不再随每笔历史请求线性增长，日账随日期和统计维度缓慢增加。已有备份仍按存储备份策略保留。

## 48 小时保留期调整

按用户要求将保留期从 72 小时缩短为 48 小时。每小时归并、原账期日汇总、处理中保护、迟到回执重新计时、费用与 Token 计数均沿用已有规则。界面通过 API 的 `detailRetentionHours` 自动显示“两天”，无需改前端代码。48 小时边界与迟到回执回归同步调整。

48 小时版本验收：全量 Go 与仓库 full 门禁通过；独立实例自动将 49 小时前的请求归入日账，保留 47 小时前与当天请求。汇总仍为 3 次、198 Token、3 笔未知，界面自动显示“2 天”。部署以前一版 OKR 重设计树 `36b932262c755cf7c1c5d842415002e3d6d74dd1` 为基底，前端源码与构建产物保持一致。
