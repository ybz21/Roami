2.1 KR、指标提案、用户确认与来源绑定

领域链改为 Objective、KeyResult、MetricProposal、ConfirmedMetric、SourceBinding、Observation、Board。KR 与 Metric 不是一对一：增长 KR 可关联粉丝总量和净增；诊断指标不作为额外 KR 计分。模型只生成候选、理由与口径建议，用户确认所选指标修订后，才允许针对这些指标创建发现/取样任务。

拟新增 okr_metric_proposals（KR 关联、候选角色、理由、单位、窗口、计算依赖、proposal_revision）、okr_metric_confirmations（用户、确认时间、accepted metric ids、revision）、okr_metrics（稳定身份、口径、目标、有效基线、基线日期）和 okr_source_bindings（指标字段映射、节点、owner、平台、稳定账号 ID、适配器、能力范围、授权引用、验证样本、观测时间、水位与状态）。原始凭据使用现有安全存储引用，不存入提案、消息或看板 JSON。

状态分开保存：指标 proposed / confirmed；来源 unbound / discovering / needs_login / sampling / verified / bound / degraded / unavailable。某字段读到不表示所有指标都能接上。比率须具备兼容分母，净增须有有效起点；首次读到当前总量，不能反推过去的周期基线。用户修改指标选择或口径会使相关提案确认与绑定校验失效，不静默扩大采集字段。

取样任务依次发现已安装能力、复用已有授权、定位后台/接口/文件、核对登录态与账号、读取最小所需字段、保存日期和证据、验证指标契约，最后提交绑定。已授权且账号身份确定时可以自动绑定；需登录或存在歧义时才询问用户。登录结果需重新检查，不以“用户说已登录”直接转 bound。

绑定与读数均按 owner/node/platform/account/metric contract 隔离。API 适配器先检查实际权限、账号与日期能力；网页适配器复用 roami chrome 和对应可信浏览器会话，不凭模型生成的字段路径确认成功；导入适配器校验文件与统计口径。登录过期、页面变化或验证失败时旧值附时间保留，对应指标标记待处理，不盲重试副作用。更换账号不把旧事实重贴新来源：保留历史来源作用域，重新确认新的基线与窗口。

绑定提交幂等键覆盖 owner、metric confirmation revision、source account、capability revision 与 sample evidence；只接受与当前确认修订匹配的结果。先前已取消的发现任务晚到，不能覆盖新选择。Board 只引用已确认指标与版本化来源，不重复保存其当前数值；可包含明确待接入的指标组件。

拟议入口：POST /objectives/:id/metric-proposals、POST /metric-proposals/:id/confirm、POST /objectives/:id/source-discoveries、GET /source-discoveries/:id、POST /source-discoveries/:id/bind。API 真实路径通过既有 /api/agent 网关，读写检查归属、确认修订与幂等键。看板生成事务可保存待接入项，只有已验证且当前授权有效的绑定进入每日采集队列。

2.2 让模型分析目标，动态生成指标与看板

当前原型没有调用模型。原六步向导的 okr-setup-model.ts 的 starter() 和 analyze() 返回两组预设，字段依赖和看板也按示例指标编写。这验证了流程，但不能证明后台具备通用分析能力。生产实现必须替换这条语义决策链，不能只把固定文案改成模型润色。

目标架构：对话与目标上下文进入分析器，模型提出 MeasurementPlan；用户确认衡量方案后，来源智能体通过实际工具发现和取样；领域服务验证绑定，模型据此提出 BoardSpec；前端按组件目录渲染。结构化是双方的通信协议，指标内容、数量、依赖、提问与组件组合由本次推理决定。

决策模型负责领域服务负责
理解目标区分用户明确要求、合理假设和未知项；提出 O、KR 与最影响决策的问题保存原话、回答与提案修订；没有周期、方向或可衡量口径时保留草稿
推导指标提出任意领域的指标、角色、理由、窗口、公式依赖、备选和所需字段校验单位、窗口、引用、循环依赖、目标与基线状态；用户确认具体修订
发现来源从实际可用工具中选择访问路径、定位字段、解释口径差异执行受授权工具，记录账号、日期、样本与回执；凭证引用和字段校验通过后才绑定
组织看板选择指标卡、趋势、分组比较或明细；给出每块内容的用途与引用只接收组件目录内的配置；查询层计算数值，渲染层执行设计系统和可访问性规则
每日行动结合历史观测提出解释、优先行动和验证方法区分事实与因果假设；按日期写观测、派发已有任务并保留结果证据

2.3 分析器输入、输出与修订

输入包含用户原话与回答、已确认目标、当前提案修订、已授权的能力摘要、实际样本的字段/单位/日期/来源引用，以及允许的公式运算和组件目录。未验证的网页文字作为外部数据处理，不能改变执行权限。能力摘要不存在某连接器时，不向模型暗示它已经可用。

分析指令要求：先识别要改变的结果，再提出最小充分的衡量集合。仅说涨粉时，候选可以只有粉丝总量与周期净增；不能默认追加点赞和完播 KR。无法判断商业转化还是内容影响力时，只问会改变指标选择的问题。每个建议提供简短依据、待验证假设和所需证据；不索要或保存模型的内部思考过程。

type MeasurementPlan = {
  schemaVersion: 1;
  proposalId: string;
  revision: number;
  basedOnRevision: number;
  objective: { title: string; cycle: string | null };
  keyResults: Array<{ id: string; outcome: string; metricIds: string[] }>;
  metrics: Array<{
    id: string; krId: string; name: string; unit: string;
    role: 'outcome' | 'diagnostic' | 'guardrail';
    valueKind: 'snapshot' | 'flow' | 'ratio' | 'duration';
    direction: 'increase' | 'decrease' | 'range';
    window: { basis: 'calendar' | 'rolling' | 'cycle'; days?: number };
    definition: string; expression: FormulaNode | null;
    requiredFields: FieldRequirement[];
    target: number | null; baseline: number | null;
    rationale: string; assumptionIds: string[];
  }>;
  assumptions: Array<{ id: string; statement: string; evidenceIds: string[] }>;
  questions: Array<{ id: string; text: string; blocks: string[] }>;
};
type BoardSpec = {
  schemaVersion: 1; revision: number; metricConfirmationRevision: number;
  widgets: Array<{
    id: string; type: 'metric' | 'trend' | 'comparison' | 'records';
    metricIds: string[]; groupBy?: string; title: string;
  }>;
};

上述是契约轮廓，正式 JSON Schema 必须关闭额外属性并限制规模；具体指标 ID 是动态身份，不枚举 followers、likes、p95。FormulaNode 是有类型的运算树，FieldRequirement 描述单位、粒度、聚合语义与所需维度。允许引用、差值、窗口求和、比率和百分位等经过验证的运算；禁止 eval、任意 SQL 或模型生成的脚本。百分位需要分布或同口径平台统计，不能平均每天的 p95。数据来源、单位与分母不兼容的表达式拒绝执行。

用户补充“我更看重咨询，粉丝只是辅助”时，把原提案、修订号与新增要求送回分析器，生成差异：新增有效咨询指标，降级粉丝角色，移除不相关组件。界面显示变更及原因，保留未受影响的选择。目标、口径或采集范围变化后需确认对应修订；单纯调整展示顺序无需重新授权。旧推理晚到不能覆盖新回答，失败则保留原稿并提供重试。

2.4 接入现有后台智能体

新增 goals/measurement_analysis.py 组织上下文和模型调用，measurement_schema.py 校验提案，source_discovery.py 管工具回执与发现状态，board_specs.py 校验组件引用与版本；前端增加 MetricProposalReview.tsx、BoardRenderer.tsx 与 board-catalog.ts。不是为两个故事各写一个页面分支，而是让同一份分析协议和渲染器处理新的领域。

模型通过现有 protocol/model_routes.py、providers/factory.py 使用节点保存的路由与 Go 网关。优先复用已支持的工具调用提交 propose_measurement_plan 参数，经 tools/registry.py 的 JSON Schema 校验和领域语义校验后才保存为提案。未支持工具调用的路由可采用严格解析的 JSON 文本提案；不假定所有路由都支持 response_format，也不向能力声明中临时加入未知配置。校验失败把具体错误送回模型有限修正；仍失败显示未生成成功，不降级成假装由模型推导的默认方案。

来源发现是模型选择工具、工具返回事实、模型解释字段、领域服务验证绑定的闭环。截图识别可提供候选映射；账号身份、观测日期和统计口径无法核实时不能升级为可信绑定。找不到登录态、工具或字段时明确待接入，并给出登录、文件导入或手动记录的下一步。确认指标不代表已取得数据。

BoardSpec 不包含真实数值、凭据、任意 HTML/JavaScript 或可执行事件代码。组件通过已确认的指标 ID 查询同一个按日期的数据层，模型不算账、不直接写 KR 达成状态。模型可以建议新组件类型，但当前目录不支持时使用合适的明细回退并说明限制。首次生成后保存看板；每日只刷新事实与分析，不重新排列用户已熟悉的界面。新布局作为可预览的修订。

推理记录保存输入上下文版本、实际调用/路由引用、工具回执、结构校验结果与最终提案；密钥和不必要的原始个人信息不进入日志。以这些记录证明真实模型参与，而不是依靠动画、延迟或“AI 已分析”的文案。

2.5 动态构建机理：目标、KR、看板和 connector 同时演化

用户确认的是方案，智能体负责生成草稿。不能要求用户手工填完 KR、指标和来源才说“生成完成”。每一轮分析的输入是原话、已确认约束、实际可用能力和工具证据；输出包含新增、修改、移除和待核实项。用户补充后，受影响的下游配置重新生成，未改变的定义和历史保留。

用户目标 / 补充
  目标分析：提出 KR 及简短依据
  KR 提案：数值结果、阶段验收、检查清单等不同形式
  衡量分析：指标、公式、时间窗口、诊断关系与所需证据
  看板草稿：由组件目录、指标引用与数据形态组合
  用户确认衡量方案
  来源发现：可用工具 / API 文档 / 浏览器页面 / 文件
  connector 候选：读取步骤、字段映射、身份与日期约束
  受控试运行：采样、校验、登记连接
  每日复用：读取、验证、按日期写入、确定性计算
  失效恢复：保留旧事实，重新发现、生成修订、复验

KR 的表达形式由它要证明的结果决定。数值型可以引用目标指标；阶段型引用验收节点；清单型引用必须具备的交付条件。模型选择呈现类型与内容；前端组件目录提供稳定实现。未支持的类型先回退成可读描述与证据明细，不能让未知 schema 使整页崩溃，也不把所有 KR 强行压成一个百分比。

connector 是持久、可复验的执行产物，不是一句“去后台看看”。最小产物包括 transport、受授权 origin/path、账号身份约束、字段和单位、日期提取方式、契约版本、验证样本及运行记录。API 模式绑定接口和权限；浏览器模式绑定页面定位与读取步骤；代码模式可生成适配模块，但必须在隔离执行环境中运行并经同样的账号、字段、日期验证。生成代码本身没有资格把状态置为 connected。

浏览器场景的真实循环：发现已安装的浏览器能力，打开或复用获授权页面，观察 DOM/可访问树或截图，定位“粉丝总量”，核对稳定账号和日期，再提出选择器/字段映射。没有固定选择器可先用受控浏览器行动读取，定位稳定后再固化成 connector。页面结构变化时，模型根据新观察生成候选 v2，试读成功后替换当前绑定，v1 的历史回执继续可追溯。登录、验证码等由用户在原后台完成，不能把 cookie、密码或临时页面内容放进生成代码或看板配置。

连接注册流程拟分为 proposed、sampling、validated、active、degraded、retired。生成器不能直接写 active；注册服务只接受匹配当前 metric confirmation revision 的验证结果。字段范围、账号、来源、日期口径或执行步骤变更提升 connector revision，并触发相关校验；布局排序不触发重新采集。重复调度和迟到回执按 connector revision、账号、日期、口径版本去重。常规只读采集在已授权范围内自动执行；遇到账号歧义、需登录或新增授权范围时才向用户提问。

2.6 本次可运行的机理原型

动态构建原型使用 okr-generation-contract.ts 定义 GeneratedPlan 和观测契约，okr-generation.tsx 按配置渲染 KR、指标映射、connector 与看板。okr-generation-replays.ts 提供明确标注的响应回放：内容目标由四条 KR 修订为五条，呈现数值、阶段、清单三种形式；v1 读取粉丝、完整播放、有效播放、总观看秒数，v2 再增加点赞字段。项目维护复用同一渲染器。

原型允许粘贴和导入其他 GeneratedPlan，未知领域不按关键词套用两个故事。已验证“减少文档检索耗时”的单 KR 方案由同一组件渲染。自由输入但没有模型响应时明确提示需要接入或导入，不伪造推理。前述 MeasurementPlan / BoardSpec 是完整实施契约轮廓；GeneratedPlan 是本次原型的简化协议，不等同于已实现的后端服务。

browser-metric-connector.mjs 是真实可执行的浏览器 runner，使用 roami chrome eval --target 读取 本地创作者后台夹具。模型候选的 JSON 描述指定选择器、身份、日期和字段，runner 用固定读取与校验实现执行；没有 eval 任意模型生成脚本。夹具数据是虚构数据，runner 只允许 loopback 的这个夹具路径，不能拿它声称已接入抖音、视频号或真实监控。

# 从原型的连接详情下载 creator-console.json，使用本任务专用浏览器标签。
roami chrome new https://127.0.0.1:18684/fixtures/creator-console.html
node browser-metric-connector.mjs --spec creator-console.json --target <标签ID> --out sample.json
# 在“验证取数”导入 sample.json；切换夹具日期后再运行，输出另一个文件。

夹具通过本机隔离的 HTTPS 静态服务提供；生产实施应接入现有安全存储与任务执行器，不增加一套临时服务。样本包含 connector ID/revision、稳定账号、观测日期、采集时间、来源 URL、原始字段与单位。导入前按当前协议校验；原型导入 JSON 不能单独证明文件真实性，生产回执必须由受信执行器保存并通过服务端关联。基线确认独立保存，缺少周期前一日快照时净增仍未知；不会根据当前粉丝数倒造历史。

本轮验证范围：浏览器 runner 实读夹具的两天数据并导入原型，校验净增与比率；账号切换、字段消失时停止且不输出新样本。模型推理为回放；真实第三方账号采集、生产 connector 注册、调度与自动修复尚未实施。

2.7 如何证明没有把两套模板包装成智能

  • 用未写入示例的目标测试，例如“减少文档检索耗时”：应提出任务成功率、检索耗时等有依据的候选，或询问场景，不能出现粉丝或固定 repo 指标。
  • 同一句“提升账号”分别补充“扩大影响力”与“获得有效咨询”：结果指标和看板组件应随意图变化；澄清前保持假设可见。
  • 只有涨粉要求时不自动增加三个 KR；用户明确要求点赞率、完播率时再纳入，且区分结果与诊断。
  • 真实取样缺少分母、账号不符或日期未知时，模型输出“已绑定”也会被服务拒绝；缺数据不填零。
  • 对口径改变、取消发现、并发修订、无效公式和未知组件做校验；两种目标共用渲染器，无按故事枚举的组件分支。
  • 接入保存的模型路由跑真实调用并记录提案差异；样例回放、模型推理、真实工具采集三种验证结果分开标注。本次尚未进行真实调用验收。

补充调研（2026-10-31）：Vercel json-render 使用组件目录、JSON 规格与渲染器；AI SDK Generative UI 将模型选择的工具调用结果映射到 React 组件。这些是实现模式参考，不代表 Roami 已接入这些库。此处选择沿用仓库组件与现有模型基础设施。

2.8 交互形式设计书的实现边界

interaction-design.html 是可离线打开的设计书，不是新注册的产品页面。okr-dialogue-scenes.ts 定义输入、响应、字幕、输出视图和时长；interaction-book.tsx 用同一组场景支持章节播放与主动推进。KR 和趋势复用配置驱动组件，数据与复盘复用 okr-execution-cycle.ts；播放跳转从纯状态快照重建，不重放真实任务。

故事按四条线顺序组织：先聊 OKR，再拆 KR 与看板，再完成来源/样本/建板，最后执行与复盘。sceneSnapshot() 显式区分派发、交付、观测、复盘、次日计划，避免前期场景提前包含执行后的数据。两个场景在交付幕只有交付事件，到观测幕才加入当日数据，复盘幕才加入分析；第二轮任务来自前次有效 Review。决策幕支持本地继续、暂停和恢复，既有事实保持。

叙事状态与交互输入分别保存。自定义输入没有对应的响应时仅保留并明确说明，不改变 KR 或生成虚构事实；切回故事不插入用户的临时输入。播放支持暂停、拖动和倍速，页面隐藏后暂停；移动端不缩小桌面画布，而是切换对话、结果和设计说明。没有模型或账号请求，也不会因播放产生文件、任务、PR 或发布。未来真实接口应接入前述提案与执行协议，不能拿这段回放当运行时实现。

3. 数据模型与不变量

以下为逻辑结构，实施时需写正式迁移、索引与约束，不直接作为生产 DDL。所有时间戳存 UTC 毫秒，业务日期另存本地 local_date，所有读写按 owner 和来源节点校验。

对象 / 拟议表 主要字段与约束
Objective / okr_objectives id, owner_id, node_id, title, cycle_start, cycle_end, timezone, state, revision, policy_revision, source_conversation_id；个人目标允许无项目，多个项目通过独立关联表绑定；归档保留周期快照
KR / okr_key_results 稳定 KR 身份、结果陈述、目标边界、关联指标和达成规则；数值口径迁移到独立 Metric 与其 contract revision，允许一条 KR 关联多个指标。
MetricContractRevision / okr_metric_contracts 指标每版基线、目标、单位、环境、来源、有效时间和修改原因；旧观测始终绑定原口径，不能因修改目标而重算旧周期结论
Milestone / okr_milestones id, objective_id, title, target_date, exit_criteria, pinned, revision；依赖边单独存，入库检查无环；通过关联表支持多个 KR
Action / okr_actions id, objective_id, primary_kr_id, milestone_id?, title, acceptance, artifact_spec, actor, human_minutes, dependencies, state, revision, task_id?；已执行任务状态由任务域提供，不能被行动表反向覆盖
Plan / okr_daily_plans id, objective_id, local_date, revision, state, input_revision, observed_watermark, policy_revision, created_ms；同一目标日期只有一个生效版本，历史版本保留
PlanItem / okr_plan_items plan_id, action_id, order, reason, reserved_human_minutes, disposition；引用原行动，变更计划不复制执行任务
ExecutionLink / okr_execution_links action_id, action_revision, task_id, request_key；同一行动修订最多一个初始 task，后续 run 由原任务系统管理
Observation / okr_observations id, kr_id, contract_revision, source_id, source_record_key, observed_at, received_at, window, value, unit, environment?, release_commit?, evidence_refs, verification, supersedes?；追加记录，更正引用原记录
Review / okr_reviews objective_id, period_kind, period_key, evidence_watermark, facts, hypotheses, next_actions, proposed_changes；重复生成形成修订，不重复投递
Event / okr_events id, owner_id, objective_id, sequence, kind, revision, payload, created_ms；与对象更新同事务持久化，供 SSE 重放与通知去重

策略包括用户参与时段、每日总可用时间、各目标优先级、免打扰、执行与发布范围。用户总容量放在 owner/node 对应的工作约定；目标只保存分配和优先级，不能各自复制一份全部容量。跨节点的同一用户时间分配先要求显式配额分配或统一协调，P0 不宣称多个独立服务已能原子抢占同一时段。

事务不变量：目标、KR、行动、项目和 task 的 owner/node 归属一致；主要 KR 必须属于目标；依赖无环；来源能回到有权限的记录；current_value 只由有效观测投影更新；修改已关闭周期不覆盖快照。备份时连同产物证据保留，引用不可读时显示不可用，不继续宣称有完整验证证据。

3.0 生效定义与长期 Swarm 的生命周期

拟新增 ObjectiveSwarmBinding，关联 objective_id、active_design_revision、swarm_id、member_role_revisions、schedule_policy_revision、state、next_wakeup 与事件水位。搭建草稿和运行实例分别持久化：draft、validated、published 属于定义；active、waiting、blocked、paused、reviewing、archived 属于 Swarm 工作生命周期。发布启动用目标与定义修订作为幂等键，重试不能重复建群或成员。

复用现有 Swarm 成员、任务看板与广场能力：backend/api/swarm.go 通过现有会话 CLI 转发建群、成员与协作操作。新方案需要一个受控的目标/任务桥接器，把 OKR 行动、真实 task/run、Swarm task 和成员回报关联起来；成员自报完成不覆盖任务验证。规划、数据与复盘继续走已有 jobs 和 Go 网关，Swarm 的角色与共享状态持续存在，不依赖浏览器页面或一个不能恢复的模型调用。

Leader 持有目标与策略，执行、数据、复盘成员按职责接收任务并在共享事件/看板上报告；没有当前工作时标为待命并显示唤醒条件。相邻业务日使用同一 swarm_id，保留上一轮 Review、未结束任务、来源连接和计划修订。重启后按持久 jobs、lease 与回执恢复，只补当前有效工作，不重发已交付 PR、视频或过期发布动作。

运行态的战术调整生成 PlanRevision，继续执行现有目标；战略或口径变更创建新的 DesignRevision 草稿，校验后原子切换 active_design_revision，任务继续引用其启动时的修订。暂停阻止新派发，运行中的任务不被显示为已取消。周期结束进入目标回顾，归档保留事实；Swarm 整体完成必须有目标与集成验收，不能因为一个成员交付就结束整个持续循环。

设计书用 sceneLifecycle() 明确搭建/运行切换；okr-swarm-state.ts 从当前阶段快照投影稳定 Swarm 身份、成员和任务；okr-swarm-runtime.tsx 展示全宽运行工作台，并提供主责对话、配置查看和派发控制。它们是本地回放，未接入真实 Swarm API 或常驻调度。

3.1 长短 KR、project 与执行资源

KR 增加 parent_kr_id?, horizon, start_date, end_date, evaluation_policy_revision。horizon 支持长期周期、短期检查点，以及确有业务需要的日结果；每天的执行清单仍属于计划，不强制变成日 KR。父子关联检查同一 owner/目标、无环和时间边界；允许短期使用独立诊断指标，不能把子目标达成率相加冒充父 KR 的业务结果。周期滚动产生新记录，旧合同、观测和结论保持可追溯。

新增 okr_project_links：objective_id, kr_id?, project_id, node_id, contribution, execution_scope_ref, revision, state，支持多对多。一个行动引用一个主要执行项目及当前绑定修订，辅助产物引用其他任务，不把多个可写目录塞进一次未经校验的执行范围。对同一项目下多个目标的行动统一排队、去重和资源协调，避免每个目标独立重复派发。

现有 backend/project/service.go 的项目 ID 是稳定身份，Dir 是可变工作根；backend/api/project.go 已聚合 Git 与非 Git 项目。创建目录可复用 backend/project/provision.go，执行目标复用 dispatch/tasks.py 的 project/new_project/new_session/session 路径。不能从 API 文件开头的历史注释推断所有项目必须是 Git，也不能用目录 hash 作为新的 OKR 身份。

目标与观测存 runtime 领域库，不依赖用户目标目录存在。仅跟踪的目标可没有 project；需要写脚本、生成素材或改代码时，先解析可信项目和授权目录，再创建工作空间。素材使用明确的日期/实验产物目录，Git 写任务使用已有隔离工作区链路。任务的 run/workspace/session 与 project 分别有身份；会话重建不创建新目标。浏览器账号与 connector 属于受授权数据来源，不因关联 project 自动获得其他账号的访问权限。

项目移动保留稳定关联；项目删除、明确停用或不可访问时保留 OKR 和历史，新写任务标记阻塞并允许重新关联。自动归档表示空闲展示状态，不应阻止已有授权范围内的任务重新激活项目。取消关联不隐式停止已在运行的任务，已有停止链单独控制。P0 继续在同一 owner/runtime 节点内原子协调；跨节点绑定显式记录节点并走既有授权和派发协议，不宣称多节点目录锁或计划事务已统一。

3.2 实验、数据成熟度与独立复盘

新增 okr_experiments 与修订记录：长期/短期 KR 引用、假设、改动因素、比较方式、对象/版本、主要指标与约束指标、观察窗口、数据质量条件、预先约定的评估/停止规则及状态。方式至少区分随机实验、探索性比较和固定环境基准；方式未知时不得输出因果胜出结论。正式统计检验必须引用实际随机化单位、分流配置与分析策略，不能让模型临时拼一个 p 值或样本阈值。

观测补充 experiment_id?, variant_id?, subject_id?, published_at?, exposure_window?, observation_age?, maturity, quality_flags。账号自然日快照与单视频发布后固定观察龄属于不同事实；日增量只在相邻日期和同口径下计算，滚动窗口变化不替代当日新增。项目基准必须带候选/发布环境与 commit。无法取得精确 T+24h 的来源保留实际观察龄，不能从 T+27h 快照虚构 T+24h。

主责身份关联目标，连续记忆保存在目标修订、实验日志、已核验交付和 Review 中，不依赖常驻的长对话。执行、取数、复盘可以使用同一保存的模型路由，通过不同任务上下文、工具与写权限运行。复盘任务读取 ReviewInputSnapshot：目标/短周期合同修订、计划、执行和发布状态、观测水位、质量/成熟度、上次判断；不能只读取执行者的自然语言总结。

数据角色只能提交带回执的观测，由领域服务验证入库；复盘角色不能修改原始数据，只提交 facts/evidence_refs、hypotheses、missing_evidence、decision、next_actions。facts 里的数值来自投影，解释保持为可验证假设。主责把建议转成 PlanRevision，记录 source_review_id/revision 与 input_watermark，继续沿用 task 派发与验证；Review 本身不自动创建无版本、无归属的任务。

建议新增 goals/project_links.py、experiments.py、review_snapshots.py、role_dispatch.py。调度与验证仍走既有任务服务和 Go 网关，不增加一套 Token/调用/花费限额。角色分离本身不保证独立性或客观性，事实可信度来自工具回执、固定合同和领域校验。

4. 每日调度与规划

4.1 触发、幂等与时间

逻辑 key 使用 objective_id + local_date + trigger_kind；job key 再包含计划输入修订，以区分同日的合法重排。主计划日期沿用 schedule_clock.py 的本地日期计算：夏令时缺失分钟用第一个有效时刻，重复时段同一业务日期只生成一次主计划。

每日窗口到达，事务插入 job 并推进下次触发时间。服务重启只为当前有效日期补一次计划；漏掉的历史日期记录未运行，不追补几十份过期发布任务。当天结果回顾在约定窗口生成，迟到观测触发原回顾修订，不产生另一个“今天”。时区修改从下一个计划窗口生效，保留原日期计划的时区快照。

目标暂停或到期后不创建新派发。恢复先核对既有任务，重新计算当前日期的余量和依赖。周期截止后允许接收“观测窗口在周期内、补录在截止后”的证据；已归档快照只能追加有标记的更正，不静默重写结论。

4.2 规划步骤

  1. 读取目标、口径、策略和观测水位；读取原任务的最新状态与待决事项。
  2. 先保留用户固定安排，扣除正在执行和已承诺的用户时间；多个目标共同分配剩余容量。
  3. 确定性过滤无权执行、依赖未满足、重复、过期或护栏禁止的行动；已运行未知结果进入核对队列。
  4. 模型在有效集合内给出选择与理由，必要时提出细化行动；结果必须符合结构 schema，不直接执行任意命令。
  5. 校验依赖、时间、人机职责、关联 KR、验收标准、资源和版本。默认预留 20% 用户时间，用户可改；Agent 并发由既有 scheduler 管理。
  6. 比较 input_revision 和观测水位，未变化则复用原计划；有实质变化才保存新版本及差异，事务写派发意图。
  7. 同步到今日视图。网关准入通过后，通过任务服务推进已授权行动；失败或未知保持可恢复状态。

首版用可解释的规则排序加受约束的模型建议，不训练无基线的收益打分。预算/Token/请求数/花费准入继续由 Go 网关负责；Python 记录并传播决定，不新增一套额度上限。模型调用使用节点已保存的模型路由、参数和能力，验收也不临时硬编码模型。

4.3 计划与任务之间的崩溃恢复

计划提交事务写 okr.dispatch 意图；派发 job 使用稳定 request_key=action_id:action_revision 调用已有任务创建路径。创建 task、记录关联与意图完成在同一受控写事务实现，或通过任务服务幂等回查收敛，不能在数据库事务中等待模型/网络。

如果创建已成功、进程在保存关联前崩溃，重试以同一个 key 找到原 task；不会再开会话或 PR。修改验收要求优先走原 task 的 revision/steer，计划重排只调整关联。只有用户明确改变工作范围且原任务已妥善处理，才允许新行动修订绑定新任务。

专业执行器工作目录和会话复用现有可信目标、隔离 worktree 与持久 session。发送提示通过既有可靠提交路径；不新增原生 tmux 清理命令，不把用户活跃会话当测试资源。

4.4 规划、执行、取数、复盘与次日计划

同一目标在一个业务日期的流转由持久状态和事件驱动，不用主智能体不断自我唤醒。每个阶段以目标、日期、阶段、输入修订建立稳定 job 身份；调度 lease 防止重复协调。角色任务必须带 objective/KR/experiment、project link revision、plan revision、actor role、输入证据与验收要求。并行仅用于可独立验收的任务，项目写冲突交给现有工作区和执行调度协调。

阶段触发与输入持久输出
规划日期窗口、上次有效复盘、未结束任务、短周期假设与用户固定安排PlanRevision 与任务创建意图；主责按实际能力决定制作视频、提交 PR 或先建立测量
执行与验证任务服务派发至已解析项目/工作空间产物、验证与发布状态；task 完成事件不能直接更新业务 KR
取数账号每日读取 job，以及单个发布对象达到观察龄的独立 job带账号、对象、日期、契约版本和回执的观测；失败原因、数据水位和下次可读时间
复盘约定回顾窗口与数据到达事件；冻结 ReviewInputSnapshot事实、缺项、候选解释、继续/调整/停止/补测决定与行动建议；依赖输入水位
次日计划当前有效 Review 与既有策略关联 source_review_revision 的新计划；例行范围内自动采用，改变目标、口径或授权范围时按相应变更流程处理

数据未齐时允许形成“先补测”的回顾和次日测量任务，不能把未知填成 0。新数据或交付晚到使旧 Review 标记 superseded 并按同一业务日期重算，旧文本保留。如果次日还未执行，按新 Review 形成计划修订；如果任务已经运行或交付，保留其身份，形成增量调整，不能删除已发生的事实或重发同一 PR/视频。

每日观察、短周期评估与长期记分分开。没有随机化或可比样本时，复盘只提出探索性方向；数据质量不合格时优先修 connector。诊断信号好转不能直接抬高长期 KR。策略可以按护栏停止明显有害实验，但停止规则和统计方法必须来自实验合同，不由一次模型回复临时决定。

本轮可运行示例：okr-execution-cycle.ts 保存项目关联、日计划修订、回放交付、日期观测、Review 输入键与次日计划来源；okr-cycle.tsx 展示“目标与项目 / 今日行动 / 取数与复盘 / 明日计划”。关联不足阻止执行，数据晚到使复盘过期，旧复盘不能被采用，同日采集和重复采用幂等；次日可以出现负增量。这个状态机是设计原型，不是已实现的生产调度器或智能体运行系统。

领域 状态或展示 约束

任务执行状态 复用现有 task/run/verification 状态 不新增第二套 succeeded 或用规划状态覆盖任务终态

计划调度与用户干预必须带期望 revision；执行控制沿用 task_revision、run 和 controlFence。双端修改冲突返回当前版本与差异，保留用户草稿，不静默覆盖。

6. KR 观测、进展和证据

6.1 数值投影

增长型示意：progress = clamp((v - b) / (t - b), 0, 1)；降低型：progress = clamp((b - v) / (b - t), 0, 1)。b 是已确认基线，t 是目标，v 是有效当前值；要求目标方向正确、分母非零。无基线不算百分比。阈值类是否达标直接比较 v <= t 或配置的方向；固定验收项按固定集合内通过的项计数，不能随意加任务扩大分母。

百分比只是详情中的辅助解释，主界面优先原单位与差距；原始超额或负向变化保留。O 不默认平均 KR 得出总分；只有全部必要 KR 达标、证据有效且护栏通过，才可标为结果已达成。周期关闭也允许未达成。

R2 示例：基线 900ms，发布值 720ms，目标 300ms，改善进度为 30%；候选分支 280ms 不覆盖正式值。发布版 290ms 经同条件复验后才达到阈值。缺采样或环境变化，保留记录但不与原口径混算。

6.2 八个示例指标的口径

指标示例 投影规则 去重与证据
M1，视频号粉丝周期起点 300；同一视频号最新有效快照，目标 500；差值为净增，可下降来源账号、观测日期和快照键去重，不跨平台相加
M2，视频号近七日点赞量周期起点的七日窗口 80 次，目标 300；保留每日新增原始数，按窗口求和来源账号、自然日、事实类型和来源记录去重；窗口差不等于当日新增
M3，视频号点赞率基线 3%，目标 5%；同窗口点赞总量除以有效播放总量保留分子分母、样本量与口径版本，七天不足或分母为零时未知
M4，视频号完播率基线 25%，目标 40%；同窗口完整播放总量除以有效播放总量同口径事实先求和再相除，不平均日比例；变化显示百分点
M5，视频号平均观看时长建议基线 14 秒、目标 18 秒；同窗口总观看秒数除以对应有效播放量，具体以核对后的口径为准保留总时长、播放量、窗口和账号；视频片长单列，先合计权重再计算，变化以秒显示
R1，4 条用户旅程 固定旅程集合在当前发布版本通过的项数；起点 0 发布 commit、journey_id 与复验记录；候选测试保留在交付层；回归失败可减少当前通过数
R2，看板 API p95 固定环境、数据集、并发、预热/采样口径下，当前发布 commit 的有效基准；基线待测，故事示例 900ms 脚本与数据摘要、原始样本、环境指纹、测试区间、commit、样本充分性规则；不同发布和环境不混为同一结果
R3，连续四周有效使用 五位固定入组试用者中，在本周期完成四个连续自然周、每周至少一次真实状态变更的人数；起点 0 时区 Asia/Shanghai，周一至周日；用户同意后采最小事件，排除测试账号和自动任务；两周活跃不提前算达标

6.3 更新流程与迟到数据

采集适配器或用户上传写入原始证据引用；领域校验来源、单位、口径版本、观测区间与最小证据要求。通过后追加 Observation，并在同事务更新读投影、写事件。任务报告可提出候选观测，但执行器的成功措辞不能跳过校验。

observed_at 是结果发生/采样的时间，received_at 是系统收到的时间。快照型指标按有效观测时间取最新，不按到达顺序；累计型按去重后的事实重算，窗口型按约定窗口计算。更正以 supersedes 追加、保留原因；失效的旧观测不继续参与当前投影。

明确区分自动验证、用户核对与未核验。只凭人工输入无法证明的指标保留“用户填报”标记，是否可用于 KR 由开始时的口径决定。来源过期时保留上次值和时间，标 stale，不补零。来源不可用只阻塞相关观测，独立的任务可继续。

外部发布、合并、部署的实际状态先从其来源核对，未知时不自动重试副作用。P0 支持文件证据与本机测试；GitHub webhook 和内容渠道直连是独立适配器，未接入时不宣称已经同步。

6.4 每日原始数、窗口投影与修订

新增 okr_daily_facts 逻辑对象：owner_id, node_id, objective_id, source_account_id, metric_contract_revision, local_date, fact_kind, value, source_record_key, observed_window, received_at, author_kind, author_id, evidence_ref, revision, supersedes, correction_reason。一个导出含多个指标时用 submission_id 绑定同一批事实；分子分母必须来自兼容口径和同一窗口。

每天的智能体填数任务沿用 jobs 与网关授权路径。去重键至少覆盖来源账号、口径、日期、事实类型与来源记录；同一批结果重试只产生一次有效事实。每日新增量、累计快照和预聚合窗口值有不同类型，不允许靠字段名猜测。微信公众号与视频号保留各自账号身份。

写入顺序：读取实际来源，解析原始数，检查日期与窗口，校验非负整数/比例分母和证据，事务追加事实及 Observation，再更新受影响的投影和事件。Agent 只提交事实，不直接提交任意达成百分比。已授权的正常写入自动完成；来源缺失、重复冲突或口径漂移进入待处理，不制造数据。

对于七日窗口，日期 d 的点赞率为 sum(likes[d-6:d]) / sum(plays[d-6:d])，完播率为 sum(completed[d-6:d]) / sum(plays[d-6:d])。平均观看时长为 sum(watch_seconds[d-6:d]) / sum(plays[d-6:d])，单位为秒，不乘 100、不平均各天均值。七天不完整或分母为零时为未知。点赞量窗口变化为 window(d)-window(d-1)；当天新增点赞取 daily_likes(d)，二者不得混用。百分比变化以百分点显示，不能把 3% 到 3.5% 写成 +0.5%。

更正 d 日原始数时保留旧版本、原因、填写人与接收时间；重算 d 至 d+6 的有效窗口以及相应回顾，超出已有观测日期的部分不生成虚构数据。原始事实的接收顺序不能改变业务日期。读接口支持“最新有效口径下的历史曲线”，后续可用 received_before 查看当时已知的数据，区分补录后重算与当时决策所见。

新增面板查询提案：GET /api/agent/objectives/:id/metrics?from=:date&to=:date&asOf=:receivedTime 返回有界日期序列、当前值、前一日差、周期净增、分子分母、来源水位与数据状态；GET /api/agent/objectives/:id/daily-records 分页读取原始日记录和修订。提交仍走 observations 领域入口，不让前端直接写读投影。大跨度趋势按明确的聚合粒度下采样，同时保留按日明细，不把缺失值当零。

原型对应验收：11 月 12 日写入粉丝 334、当日点赞 40、播放 700、完整播放 340；七日结果应为点赞 150、播放 4286、完整播放 1200，点赞率约 3.50%、完播率约 28.00%。11 月 11 日保持粉丝 328、七日点赞 120、播放 4000、完整播放 1000。更正历史日期后相关窗口重算、旧值可见；未受影响日期的原始数保持不变。

观看质量的结果 KR 与度量契约

粉丝净增、完播率、平均观看时长各自拥有 KR 身份、目标、口径与日期序列。不能由涨粉推定另两项达标，也不能把交付清单算成观看效果。约 45 秒视频的 30% / 18 秒仅是回放建议，实际基线来自取样；用户采用目标时固定统计窗口与验收规则。

连接最少提供 completed, plays, watch_seconds，带账号、业务日期、平台口径、时间窗口与来源版本。分子分母必须来自同一兼容播放集合；平台直接提供平均观看时长时记录其口径，缺少总时长或权重不能反推，也不能跨窗口聚合。单视频另存 video_id, published_at, age_hours, duration_seconds；播放时长与片长不同，重播的处理遵循平台口径，不猜字段。

原型新增受限公式 {op:'average', numerator:'watch-seconds', denominator:'plays'}；仅接受秒/次，计算总观看秒数 / 对应播放量。比例公式仍乘 100；缺字段、单位不符拒绝样本，零播放结果未知。新数据进入 reviewInputKey，晚到或更正观看秒数也使旧 Review 失效。okr-watch-quality.tsx 共用于搭建预览、长期 Swarm 和每日闭环；主面板支持七日加权计算、原始秒数填报和更正。

日期样本：11 日 144/600=24%、8400/600=14 秒；12 日 224/700=32%、12600/700=18 秒；13 日 162/600=27%、10200/600=17 秒。与之独立的两条视频 T+24h 为 24%/32%、14/19 秒。复盘同时保留账号整体回落和样片改善，不将探索性样片的参考线达成提升为整体周期成功。

7. 拟议 API 与事件契约

所有路径均为新增提案，由 Go /api/agent/... 转发 runtime；与已有 Go /api/tasks 编队接口和 /api/agent/tasks Agent 任务接口区分。以下采用目标父路径下的子资源，服务端仍检查对象归属，不能仅凭嵌套 URL 信任关联。

8. 前端、缓存和跨端恢复

目标列表和详情按节点、用户、目标、周期分 cache key。进入先快照，后 SSE；事件过密合并读取，稳定数据保留引用。前端切节点或离开目标时丢弃旧请求，防止旧观测污染新目标。列表分页不拿最近任务窗口冒充全量目标历史。

共享现有任务数据源，不为每个行动开启独立轮询。新目标视图优先事件更新，必要的活跃回退刷新使用 pollWhileVisible、共享在途请求与失败退避；结束任务及归档目标不周期轮询。导航、恢复前台、收到事件或明确恢复操作可读取最新快照。

可见偏好先从 localStorage 恢复，再等 preferencesLoaded() 合并服务端权威值。草稿按节点/目标/修订保存，提交接受后才清空。结果数值仍以服务端投影为准，不能在浏览器自行判定 KR 达成。

实施沿用主题 token、SVG 图标、i18n、useLayout()、MobileSubPage 与单滚动容器。手机详情用路由管理返回，不重复推 overlay history。草稿、展开状态、筛选、滚动位置跨来回导航保留；图文、视频和基准报告链接使用来源节点的现有文件/产物入口。

9. 交付顺序与验收

P0 先做 schema 和领域约束，再接计划与任务，最后提供界面和回顾。旧任务不强制归属 OKR；用户主动关联，历史报告不能伪造成历史指标。升级失败按现有存储迁移流程处理；停用功能后停止新调度，旧任务和成果仍从原入口可访问。

验收组 必须证明的行为
用户故事 从一句话创建个人/项目目标，生成阶段和今日任务，交付可用产物，记录真实观测，次日计划反映差距；两个故事都需端到端通过
幂等与崩溃 双端同时重排、创建 task 后崩溃、重复 job/webhook、断线重放，不重复任务、会话、通知、PR 或发布动作
时间与恢复 跨日、夏令时、切时区、暂停、离线多日恢复和周期到期，不重放过期工作；迟到证据有明确周期归属
KR 正确性 草稿不算发布、PR 不算发布版达标、重复读者不重复计、快照不累加、未知不补零、回归能降进度、更正能追溯
资源与边界 并发和网关拒绝正确传播；不另设 Python 额度；跨 owner/node/项目访问被拒；过期 revision 无法控制新 run
策略与用户控制 多目标不超售用户时间，固定安排不被静默覆盖，无效果时给出可验证调整，改变 O/KR/周期保留采用记录
