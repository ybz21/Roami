1. 先看现有产品如何连接目标与执行

调研日期：2026-10-30。范围为公开官方帮助、产品说明与开源仓库；没有登录试用，也没有完成第三方部署。下表的“产品事实”来自链接，“设计取舍”是本方案的判断。未在资料中确认的能力不判定为不存在；不使用营销页的效率数字作为效果证据。

1.1 六个参考对象

产品 官方材料呈现的做法 我们借鉴什么、需要补齐什么
Operately，GitHub 开源项目 Goal 设可衡量 targets，关联 project；项目有任务和里程碑。目标 check-in 更新状态、指标与障碍，官方描述至少每月一次，并允许随时更新。仓库提供 CLI/API 与 Agent 接入说明。仓库、目标 check-in、功能说明 借鉴目标到项目的关联、责任人和定期复盘。Roami 在这个结构上设计每日行动与跨天续作，不要求个人用户模拟公司的层级和评审组织
Asana Goals 目标进展支持手动和自动更新；自动来源可以是子目标、项目或任务，汇总方式随来源与度量类型变化。官方帮助 借鉴每个目标声明进展来源。对业务效果，Roami 采用实际指标观测；只有明确以验收项为口径的交付型 KR，才按验收项计数
ClickUp Goal 由可衡量 Targets 组成，包含数字、金额、是/否和任务型；任务型可追踪关联任务或列表。Super Agent 可由定时、自动化或人工触发。Goals、Agent 触发 借鉴指标类型和明确的周期触发。Roami 要把每次触发关联到当天计划、实际任务、产物和结果观测，避免只配一段“每天努力工作”的提示词
Linear Initiative 组织目标相关项目；项目里程碑组织阶段，Cycles 形成重复执行节奏；Updates 给出健康状态与说明。已支持将 issue 委派给 Agent，Coding sessions 可写代码、测试并返回待评审 PR。层级概念、Updates、Coding sessions 借鉴阶段路线、短周期计划和人仍负责结果的委派关系。Roami 聚焦用户已有本机仓库、持久会话和手机接管，并把“代码已写好”和“发布后的结果”继续连起来
GitHub Projects 同一批 issue、PR、草稿可呈现为表格、看板和 roadmap；roadmap 使用日期和 iteration 字段在时间线上定位，能够展示里程碑标记。Projects、Roadmap 借鉴“一份工作数据，多种视图”。Roami 的 roadmap、今日行动和任务详情引用同一工作对象；issue/PR 的变化也须与现有任务关联，避免两套待办各自完成
Motion 自动排期依据优先级、截止日期、可用时间等把任务放入日程，并在安排变化时重排。自动排期帮助 借鉴容量约束、未完成工作的重排。首版不做精确到分钟的日历优化，分开计算用户参与时间与 Agent 执行条件；留出临时事项空间

1.2 调研后的产品判断

目标关联工作、定期更新、AI 委派和日程重排已经各有可参考的实现。不能把“别人只记目标、我们能执行”作为结论；Linear、ClickUp 已有明确的 Agent 工作流。

对本需求的判断是：Roami 应把这些环节连成一段用户可长期依赖的体验。用户给出方向后，系统每天根据结果差距选择行动，在用户已有环境中执行，留下可用成果，并用证据决定下一天。首版价值由两个故事能否跑通衡量，不以功能菜单数量衡量。

调研启发 本方案中的具体决定 用户能看见的变化
目标要与工作保持关联 每个行动有主要 KR、阶段、验收条件 用户能回答“为什么今天做这件事”
不同进度来源不能混算 指标变化由其声明的数据源驱动 发布草稿完成，不会使关注人数增长
阶段与短周期承担不同职责 八周路线、近期一周计划、今日行动逐层展开 远期不铺满僵硬待办，今天有具体交付
Agent 已是协作者 保留人的目标责任，委派到现有任务与会话 能看结果、补充要求、接管和继续
时间安排要能变化 计划受跨目标总容量与优先级约束 临时 bug 或时间减少后，有可解释的重排
更新要形成决策 日回顾讲事实，周复盘调整策略 连续无效果时，改变行动而不是增加打卡

2. 产品模型：六个概念，用户不必填写六种表

概念 解决的问题 关键内容
O，目标 这段时间为什么做 方向、周期、负责人、个人或项目范围
KR，关键结果 要取得什么结果 结果方向、期望边界、相关指标与达成规则
Roadmap，阶段路线 先后经过哪些阶段 里程碑、目标日期、依赖、阶段出口；可同时支持多个 KR
行动 接下来具体做什么 关联 KR、验收条件、交付物、人机分工、依赖、预计参与时间
今日计划 今天选哪些行动 已选行动、选择原因、容量、变更记录；引用原行动，不复制任务
观测与回顾 产生了什么结果、下一步怎么变 证据、实际值、数据时间、差距、阻塞、调整建议

目标不要求先有 Git repo。博主可以是个人目标，绑定素材目录；维护者绑定节点与项目。后续可把已有项目关联到个人目标，仍沿用同一条执行链。

每个行动有一个主要 KR，可标记其他受益 KR；一份产物支持多个结果时按各自口径核验，不能重复加总“目标完成次数”。没有 KR 关联的临时任务允许存在，系统建议归属，用户可保留为日常事项。

2.0 搭建态与运行态：两种不同的工作界面

体验搭建态 · 进入短视频 Swarm 运行态

状态主要交互与呈现形成什么
搭建态左侧与主责聊目标，右侧生成/调整 KR、指标、数据连接与看板；确认项目和职责。有版本的目标与执行定义，发布后可启动长期 Swarm。
运行态全宽 Swarm 工作台：目标数据、成员状态、共享任务看板、事件回执、复盘与调整；对话作为可打开的侧栏。持续累积的任务、产物、观测、回顾与下一轮行动，人可查看、暂停、恢复或给主责新决定。

前面三条故事线处于搭建态。项目关联也在发布前确认，随后通过“启动长期 Swarm”明确进入运行态。第四条故事线展示同一个 Swarm 的执行、回填、复盘与调整，跨天保留成员职责、目标和任务，而不是每次从头组班。当前设计书为短视频 20 幕、repo 16 幕；回放结束时，产品中的 Swarm 仍保持等待下一次触发的运行状态。

Swarm 持续保存工作状态；成员按事件、依赖和时间窗口执行或待命。工作台显示下一次规划/采集时机、当前接棒者和来源更新时间。断线或服务重启后恢复到同一组织与任务水位。日常调整动作在运行态进行；修改 KR、指标口径或看板结构时打开新搭建草稿，原生效版本继续运行，发布后才切换配置。

演示运行态可查看搭建配置、打开主责对话、暂停新派发并恢复。暂停保留已有产物和数据，已在执行的任务保持原状态并单独控制。页面中的团队、调度和数据均为回放，不创建真实蜂群。

2.1 长短目标、project 与智能体怎样组成闭环

体验短视频的两天闭环 · 体验 repo 的执行与复盘

OKR 保存“为什么做、取得什么结果”；project 承载“在哪工作、用什么资源执行”；任务记录一次具体执行；看板显示结果事实。一个目标可以先独立存在，执行时关联已有项目或创建合适的项目。不能把每条 KR 等同于一个新目录，也不让一条主会话承担所有状态存储。

关系产品决定例子
OKR 与 project多对多关联。绑定可细化到 KR 和行动，每个关联说明贡献与执行范围。“AI 编程内容增长”由“栏目素材”和“内容自动化工具”两个 project 支持；同一工具项目也服务其他栏目。
project 与目录项目有稳定身份、节点与工作根目录。目录是资源，不是目标身份；素材项目不要求 Git。视频脚本、素材、渲染结果放内容目录；代码在 Git 项目的独立 worktree 执行。目录移动不创建一个新 OKR。
数据与执行项目浏览器账号、API 和 connector 独立关联指标，可供多个项目的行动使用。粉丝数据来自创作者后台，不来自视频目录。没有取数项目也能单独观察一个目标。
主责与执行者一个目标有一个主责协调身份；跨项目调度任务，按需要使用执行、取数和复盘角色。主责安排做视频和修 connector；任务能独立并行时才开多个执行者，不为每个项目固定养一群智能体。

用户新建目标时可先点“只跟踪”；开始执行时再选“关联已有 project”或“创建 project”。系统先检查是否已有合适目录和项目，不重复创建。关联页展示项目名称、目录、负责的 KR/行动与可自动执行范围；新建和绑定不等于取得账号、发布、合并或线上实验权限，已授予的范围持续沿用。

2.2 长期 KR、短期 KR 与每日观察

允许有长期 KR 和与其关联的短期 KR / 检查点。长期结果保持稳定，短期围绕一个可验证的假设设时间窗口；每天可以查看实际增量、任务交付和证据成熟情况。每天的行动不必新建一套 OKR，短期目标也不按天平均拆出机械配额。

层次短视频示例怎么看
长期 KR，八周净增 200 个真实粉丝，起点 328周期净增和剩余差距；发布一条视频不直接推进粉丝 KR。
短期 KR / 检查点，一周验证更短开场；同龄样片的完播率参考目标 30%持续追踪同一实验的假设、参考线、观察窗口和结论。数值达线与证明方法有效分开。
每日观察今日粉丝 334，昨日 328，净增 6；第二天变成 332，净减 2切换“按日看增量”，保留正负变化、数据日期和来源，不覆盖历史。
每日行动制作一条 5 秒开场候选视频，核对字幕和复现步骤在 project 中执行并验收；属于推进手段，不能用完成率代替实际效果。

短期目标可以与长期目标共用指标，也可以是支持它的诊断或实验指标。完播率改善不自动换算成粉丝增长分数。短周期结束保留结论和数据，下一周期另建版本；修改长期目标需有明确采用记录，不因每日波动反复改口径。

2.3 四种职责，一条按证据推进的链路

职责读什么、做什么交给下一步什么
主责智能体读取长短 KR、上次复盘、未完成任务、时间与授权范围；提出今日实验和行动。带 KR、实验、project、验收条件与版本的任务；同一个目标跨天保持连续。
执行角色在具体 project 准备视频、验证代码或提交候选 PR。产物、测试/验收、版本与发布状态。没有视频制作或发布能力时准确交付草稿或阻塞，不报成视频已发布。
数据角色调用 connector，核对账号、日期、单位、视频/版本身份和原始字段，按日期填数。可追溯的事实和数据水位；读取失败保留旧记录，不补零。
复盘角色独立读取冻结的交付证据和数据，区分已知变化、可能原因与尚缺证据。继续、调整、停止或补测建议；主责再把建议落实为下一天的具体任务。

这些是可独立运行的任务职责，不强制使用四种模型或四个永久会话。默认一个主责，少量任务按需运行；只有独立任务可并行、有资源且不冲突时才增加执行者。两人同时改同一仓库时用隔离 worktree，读取同一个浏览器账号时协调访问。复盘角色不因为换了名字就天然可信，仍须引用原始证据。

正常产品按约定窗口与事件自动串联：早间计划，任务完成后的验证，晚间账号取数，视频发布后到达观察龄的取数，复盘与次日计划。用户默认看到结果、判断和必要决策，不必每天手动点四次“启动智能体”。原型使用回放按钮便于逐步验收，未创建真实任务或对外发布。

2.4 每天复盘，持续做实验

把一轮探索记录成“假设、改动因素、对象与版本、主要指标、约束指标、观察窗口、停止/继续条件”。做视频时可以分别研究主题、开场、节奏和风格，每次尽量明确本轮改变什么；做代码时固定发布版本、数据集、并发与环境。执行、上线、观测和判断有各自的状态。

每天复盘先回答：今天交付了什么？什么已上线？数据更新到何时？长期结果与短期信号各怎样变化？接下来需要继续观察还是改变一个因素？新视频发布 3 小时，不能直接和旧视频累计 3 天的数据相比；先等同一观察龄。没有随机分流时标为探索性比较，不把两条视频的差异宣称为因果效果。发布后 24h 数据无法实际取得时，显示实际观察龄并保留不可比状态。

参考 Microsoft 的实验前设计与运行中监测实践：先明确假设、指标和实验条件，运行中持续监测数据质量与效果；每日查看不等于可以每天按普通显著性检验挑赢家。推断与停止规则须与观测方式匹配。实验前设计、运行中监测。在此基础上，本方案把“补数据 / 继续观察”也作为有效的每日结论。

原型的第一天：粉丝 +6，但新视频未满 24 小时，主责继续收样。第二天：粉丝 -2，样片 T+24h 完播率从 24% 到 32%，仍不能把涨粉归因到新开场；复盘建议维持其他条件再试一轮。repo 场景中候选 p95 为 280ms，发布版仍为 720ms，长期 KR 不提前达标。

3. 从一句话开始，到一次明确的持续工作约定

3.1 目标草稿

用户从首页说出目标，或从项目的“目标”入口创建。Roami 复述 O，提出少量 KR，并只追问影响推进的缺项：周期、指标口径、必要的数据或执行范围。用户提供过的信息沿用，不强制重新填写。

编辑页按“方向与周期 / 如何衡量 / 怎样推进”三组组织。KR 支持数值增长、数值降低、阈值和固定验收项。基线未知时明确写“待建立”，允许创建测量行动；不展示虚构百分比。

3.2 开始推进

开始前显示一屏摘要：目标和周期、每个 KR、每天需要用户投入的时间、执行时段与时区、工作目录与数据来源、可以自动做的事。用户可修改后点“开始推进”。开始只表示按此约定持续工作，不能自动取得尚未配置的账号或发布权限。

默认在现有授权范围内执行调研、准备、实现与验证。发布、对外发送、合并等沿用已有授权和用户选择；已有授权不增加逐日确认。真正缺少发布权或结果口径变更时，展示具体待决事项与影响。

3.3 生成路线与近期工作

系统生成阶段出口及其依赖，同时细化近期一周。用户可改顺序、日期、交付标准，也能将已有任务关联进来。计划保留用户固定的安排；依赖冲突会显示受影响项。

启动后展示第一批行动和下次自动推进时间。没有可执行任务时，只显示一个准确原因，例如“等待你提供性能测试环境”，并继续可独立开展的其他工作。

4. 信息架构：从已有入口看目标与今日行动

位置 放什么 不占用什么
首页主对话 今日简报、成果摘要、真正需要用户处理的问题；链接到目标或任务 不把每日计划和工具记录整段刷入聊天
首页现有任务工作区 今日计划关联的实际任务，行内可显示目标归属 保持任务 / 消息 / 记忆三标签，不增加第四个目标标签
Projects 的“目标”视图 当前节点下个人目标和项目目标，默认先看活跃目标；个人目标无需伪造 repo 不新增手机底部主导航
项目详情“目标” 当前 repo 关联的目标、阶段与今日行动 不复制一套执行任务列表

新增 Projects“目标”视图是本提案的产品扩展：个人与项目目标统一收纳，列表明确标识“个人”或所属项目。首页待处理摘要继续进入 Projects；对话内的“查看今日行动”可直达目标详情。

4.1 目标详情四个视图

今日：先展示需要用户做的事，再展示 Agent 已在推进的行动和交付。每行只保留短主题、状态、主要 KR、选择原因与用户预计时间。展开进入现有任务详情，先看结果与文件，后看执行记录。

路线：按阶段列出出口、日期、依赖和相关 KR。桌面可切时间线，手机默认阶段列表，提供“调整日期”动作，不要求拖拽才能修改。远期未细化不是缺失任务。

结果：每条 KR 独立展示基线、当前值、目标、差距、最近观测时间和来源。点开看趋势、证据、口径与更正记录。C1 可显示“334/500 人，本周期净增 34/200”；R2 显示“发布版 720ms，候选分支 280ms”，两者有清楚标签。

回顾：日回顾按“交付 / 结果变化 / 阻塞 / 明日”组织；周复盘比较预期与实际，提出路线调整；周期回顾归档成果与未达结果。未来计划是预计，已选计划是安排，已核验交付才是事实。

4.2 桌面与手机

桌面沿用导航、主内容和现有任务检查器，页头用 .tt-pagehead。目标详情打开时能继续访问主对话和相关会话。手机保留首页、项目、工具、设置四个主入口；目标与任务详情走全屏二级页，一个返回栏、一个内容滚动区，返回保留筛选、草稿和位置。

页面同底色 --bg-base，相邻模块用单线分隔；字号、间距、圆角、状态色用已有 token。使用 useLayout() 与现有 MobileSubPage；操作有可见名称、触控范围和键盘焦点，不依赖 hover 或 Tooltip。消息从顶栏进入；自动更新和到顶下拉刷新复用现有机制，不新增常驻刷新栏。

4.3 整体 OKR 面板：由口述产生，按日期追溯

面板统一收纳个人与项目目标。用户口述“我要做什么、看哪些结果、在什么时候达到”，Roami 整理成 O、KR、基线、目标、周期、指标来源和每日工作约定，保存原始口述。用户核对口径后开始推进；没有历史数据的新目标显示待填报，不复制其他目标的曲线。

面板默认展示最近一次有效观测，明确标注日期；今天尚未更新时保留“智能体填入今日数据”的入口和下次自动整理时间。五类内容指标分别标注平台与窗口：视频号粉丝总量、视频号近七日点赞量、点赞率、完播率、平均观看时长。项目目标切换到功能、性能和有效使用指标；不把不同单位或不同平台混成总分。

选择日期后，指标卡、趋势读数与每日记录联动。每张卡有原单位数值、目标和较前一日变化；粉丝展示周期净增，比例展示百分点变化、平均观看时长展示秒数变化，近七日点赞量展示滚动窗口变化。曲线保留下跌，缺失数据留空，不连成一条虚假的持续增长线。

数据类型 每天保留什么 面板如何计算变化
粉丝总量 来源账号、日期、总量 当日总量减前日总量为净增；减周期基线为周期净增
当日新增点赞 该自然日新增的有效点赞 原始新增量单独保留；近七日量等于同口径七日原始数之和
点赞率 有效点赞数与有效播放数 先对同一窗口汇总分子分母再相除；3% 到 3.5% 是 +0.5 个百分点
完播率 完整播放数与有效播放数 同窗口汇总后相除；保留分母与样本量，不直接平均每天的比例
平均观看时长总观看秒数、对应播放量、视频 ID 与片长（如有）同窗口总秒数 / 播放量，前后相减以秒表示；不平均日均值。缺字段或零分母保持未知。
发布版性能 日期、环境、发布版本、基准结果 比较相同口径与环境；候选分支结果独立展示

示例中，11 月 12 日新增点赞 40 次，近七日点赞量从 120 变为 150，只增加 30，因为窗口移出了 11 月 5 日的 10 次。两种变化在页面分别命名，不都写成“今日新增”。真实接入须确认平台提供的是每日增量、累计快照还是窗口指标；口径不兼容的来源不能直接求和。

4.4 智能体每日填数与更正

开始推进时可约定每天 21:00 整理数据。智能体读取已经授权且实际可用的来源，校验账号、观测日期、单位和数据完整性后按日期写入；常规填报不增加人工确认。原型中的“预览智能体填报 / 写入面板”用于让评审者逐步体验真实写入的结果，并不意味着真实产品每天都要人点一下。

每日记录有观测日期、原始数、来源、填写人、接收时间和修订。缺来源时显示待填报并说明缺项；重复导出不重复累计。相同日期的更正必须有原因，保留原值与来源；晚到数据归到其观测日期。更正历史原始数后重新计算受影响的滚动窗口，让整条波动曲线保持可追溯。

计划、任务和数据仍是三种事实：任务完成可以留下产物；发布可以留下凭据；只有实际观测写入才改变结果曲线。复盘根据有效日期数据提出下一天的行动调整，不能用“智能体做了很多”替代增长结果。

4.5 重点流程：先确认衡量指标，再获取和绑定数据

KR 与指标分开建模。一条 KR 可以分析出多个指标；目标值和指标来源也分开确认。示例“提升抖音粉丝量”先得到粉丝总量、周期净增等建议，解释用途和计算方法，用户取舍后才进入数据接入。

  1. 口述目标：用户可以只说方向，不必先给指标名或后台地址。
  2. 确认 O/KR：整理结果方向与建议目标，保留原始口述。
  3. 分析并确认指标：每个候选说明关联 KR、结果/派生/诊断角色、单位和窗口；用户可改名、改目标、删除。来源此时保持未绑定。
  4. 寻找与接入数据：询问已知账号或入口，也可让智能体检查现有能力与登录态；实际取样后核对账号、字段、观测日期和基线。已授权且身份清楚的来源可自动校验绑定，歧义才请求用户处理。
  5. 预览看板：每块内容能反查到已确认指标和 KR；明确区分已绑定、待接入、数据待积累。缺失项保留，不画假趋势。
  6. 开启每日推进：定时读取可用来源，按日期追加；登录失效、字段缺失、条件不满足时只阻塞对应项。

接入方式可为后台页面读取、已有授权接口、导出导入。首次登录由用户在对应平台完成，不把密码或会话凭据写进看板。样本验证前，“找到网址”“识别出指标”均不等于绑定成功。公众号、视频号和抖音账号身份不能混用。

原型支持抖音与视频号示例，演示需要登录、读取失败、字段不全和正常取样。它不访问真实后台，也不声称 Roami 已经具备这些连接器。可先生成待接入看板，之后从“指标来源”继续接入；切换账号保留旧账号记录并隔离新曲线。

平台接入核对（2026-10-31）：抖音官方的一类小程序粉丝接口需要申请能力与用户授权，返回昨日及之前的数据，并有账号门槛；不能据此承诺任意账号当日实时数据。官方接口说明。抖音创作者中心是候选后台入口；本次未登录取用户数据。视频号实际后台能力与字段尚需实施时核验，不从第三方营销说明推断已经可读。

4.6 模型怎样决定该衡量什么、该生成什么界面

原六步向导使用预设示例，没有真实大模型分析。新增的动态构建原型逐步展现智能体生成 KR、指标、看板和连接方案的机制：推理使用标明来源的响应回放，界面按响应配置渲染，也可导入其他领域的合法方案。实际产品应让模型生成本次目标的衡量方案与看板配置；已有组件提供稳定的交互与样式。指标名称、数量、角色、提问和组件组合可以变化，不把所有目标归入“内容增长 / repo”两个固定分支。

对话推进用户看见什么后台实际发生什么
“帮我提升抖音号。”“你更想扩大影响力，还是获得咨询？这会影响主要指标。”已知：平台；待确认：成功标准。模型识别意图歧义，提出影响方案的问题；不直接套三条 KR，也不要求用户先懂指标术语。
“八周内多 200 个真实粉丝。”推荐粉丝总量与周期净增，说明一个提供原始数、一个衡量本周期结果。周期起点和可用历史待核对。模型生成带理由、依赖和未知项的指标提案；200 是用户要求，当前基线未知，目标总量还不能确定。
“也关注点赞率和完播率。”新增两项候选，解释需要的原始数与分母。询问它们是达成标准，还是帮助找问题的诊断信号。模型修订方案，只改变相关项；用户确认指标与用途。候选口径须在取样时对齐平台。
“这些可以，账号后台已经登录了。”发现来源进度与实际账号、样本日期、可读取字段。缺少完播字段时显示待接入。智能体查找可用能力并调用工具，重新核对登录态与账号；工具证据通过校验后绑定，不能凭模型推测成功。
预览并创建按确认指标生成卡片与日期趋势；没有历史时保留空趋势。可追溯每个组件对应哪条 KR、哪份数据。模型提出组件组合，服务校验引用，前端渲染。数字与变化量由数据层计算，不由模型填写。
后来补充“咨询更重要，粉丝只是辅助”方案差异：“建议新增有效咨询量，粉丝改为辅助；需要明确有效咨询的判定和记录来源。”预览改变后的看板。新意图进入推理，提出新的 KR/指标和来源需求；确认后保存修订，旧口径与历史保留。

页面只展示推荐理由、假设、已核实事实与下一步，不展示模型内部思考过程。没有明确目标时先澄清；目标清楚且信息充足时直接给可审阅方案。用户不需要猜系统支持哪组指标，也不需要先找到接口。

看板中的通用能力保持一致：日期选择、追溯、更正、来源状态、手机导航与输入。模型选择展示内容：规模指标适合卡片和趋势，不同视频的效果适合比较与明细；没有视频维度的数据时不能凭空生成有数值的排行榜。repo 维护则可选择发布版性能趋势、核心旅程验收和版本明细。

日常更新不重新生成整页。智能体按原约定采集，服务更新按日期的事实，模型给出变化解释与行动建议。建议新增指标或调整布局时，以变更预览让用户决定；不因一次模型回答就丢失原有指标、历史和布局。

生成式 UI 的公开实现参考：json-render 用组件目录约束模型生成的规格，AI SDK 将工具结果交给组件。我们借鉴这种分工，具体推理契约、模块与验收见技术设计 2.2–2.7；本次没有引入依赖或接通模型。

短视频的三类结果 KR

涨粉、完播率、平均观看时长都可以是用户明确追求的结果，分别建 KR；点赞量、点赞率按用户约定作为结果或诊断。智能体分析后提出各自指标与来源，用户确认再搭建，不把所有短视频目标固定成同一模板。

结果本例建议与起点每日动作与决策

4.7 在原型中看见整套机理发生

体验：智能体逐步构建 OKR 和连接

  1. 说目标。回放“八周增加 200 个真实粉丝”。智能体给出四条待确认 KR：粉丝增长、完播率、平均观看时长，以及阶段式内容交付建议。每条呈现简短依据；基线与发布节奏保持待确认。
  2. 补充信息。点“回放补充：也看点赞率和发布验收”，观察 KR 由四条变五条，出现数值、阶段、清单三种形式。指标由四个变五个，看板由七块变九块。自由补充没有模型响应时会留在草稿，不伪装成已经理解。
  3. 从 KR 到指标和界面。确认 KR 后，自动展开每项指标的来源字段与理由，以及将生成的指标卡、日期趋势、验收清单、数据明细。交付型 KR 保留验收证据，不强行变成业务指标。
  4. 从指标到连接。确认衡量方案后，展示来源发现和读取计划；v1 读取粉丝、完整播放、有效播放和总观看秒数，补充方案 v2 再增加点赞字段。连接详情提供可下载 JSON 和可执行浏览器 runner。
  5. 取样才算接上。可回放需要登录、字段变化、账号不符和有效样本；也可导入实际 runner 读取本地夹具生成的 JSON。核对账号、版本、日期、单位与字段后，才把样本写进看板。
  6. 日期累积与失效恢复。使用有效起点计算净增，次日数据追加，缺失值保留为空。回放来源失效时停止新采集，旧日期数据保留；重新取样通过后恢复，不复制一份重复记录。

项目维护回放使用同一机制，生成性能数值、功能阶段、维护清单及不同组件组合。开发评审还可导入新领域的方案，验证界面没有把 KR 数量、指标 ID 或故事类型写死；协议与代码边界见动态 connector 技术设计。

正常产品主流程只呈现目标、建议、数据状态与下一步。连接代码、字段选择器、协议和回执在明确的详情中展开，避免让用户先理解实现细节。此原型中的响应回放、浏览器夹具实读和未来真实第三方采集有分别的标记。

5. 每日推进：先选择，再执行，最后验证效果

每天按目标时区进入规划窗口；任务事件、用户补充和重要结果也能触发有范围的重排。首版每天生成一次主计划，必要时增量更新，不因每个工具步骤都重跑规划模型。

顺序是：读取有效 KR 观测及阶段出口，核对未完成任务，剔除依赖未满足或无权执行的行动，再从剩余行动中选择。优先解除关键阻塞、守住回归护栏和验证低成本假设，之后推进最迫近的结果差距。选择原因使用事实和明确的推测，不编造收益数字。

用户参与时间在所有活跃目标间共用；本机 Agent 并发和模型可用性沿用现有调度与网关。示例默认只占用户可用时间的 80%，给临时问题留空间，这个比例可修改。若博主和 repo 目标同时开启，不能各自占满用户的全部一小时。冲突时按用户设置的目标优先级安排，并显示被推后的工作。

今日行动一旦派发，就引用实际 task。未完成工作保留身份，次日先续作、核对或重排，不复制一个新任务伪装成新的进度。重排只更新尚未派发部分；运行中的动作通过原任务干预与取消流程处理。

5.1 交互形式设计书与详细原型

跟着对话看设计书 · 切换 repo 故事

设计书按“聊 OKR、拆 KR 与关键看板、把看板建起来、智能体运转与决策”顺序展开，先讲前期建设，再进入持续循环。参考用户提供页面的交互呈现方式：左侧出现用户输入和智能体响应，右侧工作台随之生成；字幕说明本幕的设计意图，章节和进度控制支持逐幕查看。可以播放完整故事，也可以选择“自己推进”发送示例输入。每幕可展开输入、系统处理、界面输出与状态边界，详细状态验证保留在下面的独立原型入口。

可以依次体验：口述目标、确认 KR、分析并确认指标、寻找和验证来源、预览看板、安排填报、生成面板、查看历史波动、智能体填报、进入每日行动、查看成果、采用复盘调整。内容增长与 repo 维护使用同一套面板与导航。

6. 指标怎样变化、怎样影响下一天

KR 的度量配置决定进展来源。固定验收项如 R1，只有发布版本验证通过才计入；数值类如 C1、R2，使用账号快照或同条件基准。上传文件只表示已收到，结构检查和来源核对后才产生有效观测；人工确认有明确标签，不包装成自动验证。

指标可下降，旧观测可被更正。C1 取消关注、R1 回归、R2 新版本变慢，都会反映到当前结果和健康状态。数据过期时先呈现“数据待更新”，不能根据旧数字继续声称按计划。

自动重排可以改变行动顺序、细化近期工作和调整容量内的准备任务。改变 O、KR 口径、目标值、周期、已固定的里程碑或扩大执行范围时，先给出变化和原因，由用户采用。每次采用保留版本与历史，既有授权内的日常工作不重复询问。

周复盘至少回答：实际结果发生了什么变化，哪些行动有支持证据，哪些只是相关，接下来要验证哪个假设。点赞、阅读量、提交数等可以作诊断信息，不默认变成新的 KR。

暂停目标后停止新派发，说明现有任务是否仍在运行，用户可选择继续收尾或请求停止；停止确认前不显示全部已停。周期到期停止新工作，核对未决任务并给出回顾；新周期需用户选择开启，不自动无限续期。
