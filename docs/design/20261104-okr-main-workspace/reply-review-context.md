# 长历史回复审核（#774）

## 产品与用户故事

原 Main 在长期项目中读取规范并回告群聊后，最终回复仍应经过来源审核并交付。
读取、群聊投递和最终回复是三个独立结果，不能互相替代。保持同一 Main、分支和历史。

## 技术设计

当前审核将实际 Main prompt、来源原文和拟交付文本再次序列化到一个 JSON 字符串。
历史中的工具 JSON、引号及换行再次转义，会使原 Main 可处理的上下文在审核阶段超限。

只在模型明确返回 `MODEL_CONTEXT_LIMIT` 后，使用同一模型及参数重试一次：

- 保留完整来源、拟交付文本、字面值和已接受委托；不摘要、不裁剪、不猜测窗口大小。
- 依原顺序把 Main 上下文转成引文记录：元数据单独编码，正文以原始文本块传递，图片仍为图片输入。
- 仅当 user 记录正文与 userRequests 某项逐字相同时用明确索引引用；原文仍完整保存在 envelope，原记录顺序及元数据保留。assistant/tool 的相同文本不作为用户来源去重。
- 原 system/assistant/tool 身份只是引文元数据，所有记录的传输角色都是 user，不能变成审核指令或可执行工具调用。
- 重试前与最终返回前再次核对来源、lease、停止/遗忘、模型实例和配置。依赖失败、第二次超限都不接受回复。
- 记录两次实际模型调用、用量与输入格式；不修改路由、费用、历史或手工 busy。

`replies/review_context.py` 只负责无损传输，`SourceReplyReview` 保留准入、一次重试、校验和审计。
这项修复不启用自动发布或调度。原生产失败回合保持原状；上线后另以原 Main 验证实际回复。

## 验收

需覆盖转义较多的真实工具结果、字面值、图片、原角色隔离、明确超限才重试、第二次超限拒绝，
以及重试前后来源/配置变化。隔离模型测试与生产实际回复分别记录，不将 fixture 当线上通过。
