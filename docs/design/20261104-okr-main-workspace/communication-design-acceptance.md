# 通信机制设计核对

2026-11-06。设计与本地交互演示验收，不是新增通信引擎的生产验收。

## 真实代码基线

已核对 CLI 的私有 Unix 通道、Web 的 Go 登录代理及 Python Swarm 入口。成员 post、人的 say、完成回报和受管续派具有不同语义。

发现并反映到设计的实际约束：

- 顶层任务完成已经创建原 Main completion turn；handoff 不能再为同一结果另起通知。
- completion 当前禁止续派，project wake 当前写 user/scheduled 消息；新协调入口必须明确原委托，不能直接拆掉保护或冒充用户。
- `UNIQUE(owner_id,name)` 会阻止跨 OKR 同名团队；owner 级 commandKey 与范围化新协议还需兼容旧回执。
- 当前 SSE 是状态快照；可靠收件箱与完整历史恢复不能只靠最近快照。
- Go 模板初始化仍读内置常量；完整模板资源需实际接通新项目创建入口。

12 项现有专项通过，覆盖 completion 续派保护、当前 run 发言、群聊去重与回复、原用户来源保留、项目 Main 身份/忙碌/待用户及重复唤醒。它们证明当前基线，不能当作新协调协议已实现。

## HTML 机制演示

使用自有 CDP 页和 roami chrome 操作，无真实后台调用。8 个场景通过：

1. A Main 忙时保留消息，B 独立处理；切换来源选择不改变在途消息归属。
2. 同一请求回执丢失后取回原消息；两个 OKR 可使用相同本地业务键。
3. 跨范围与过期运行在模拟落库前拒绝。
4. 普通进展不额外唤醒模型。
5. Main 指令投给原任务，受管接收不当作任务验收。
6. 交付先到、完成后到，仅一次 Main 处理。
7. 完成先到、交付后到，沿用原结果处理回执。
8. Main 等用户/失败时保留问题；恢复合并处理；新增第三个演示 OKR 继续共用一套引擎并保持独立收件箱。

总览页另验证两种 handoff/completion 顺序及重复回报不自我唤醒。
