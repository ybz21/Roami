# 同一批次的显式恢复与结果通知：下一段接线草案

schema25基础层已随 PR #754 合入，自动调度与公开目标工具仍未开放。本文是后续接线设计，不是已交付行为。

用户仍在原OKR Main里说“继续刚才未完成的工作”。Main定位实际未解决批次；只有范围或目标不明确才追问。不给用户增加一页技术设置，不以新会话、新任务或新业务键绕开历史。

## 恢复需要保留的事实

原batch、turn、冻结inputs、原目标与摘要、成员/task/revision/run、所有工具/投递回执都保留。恢复授权是一条附加记录，关联本次真实用户消息、原Main当前分支/lease、实际目标委托以及原batch。旧授权即使被撤销也不改成从未撤销；旧来源遗忘/删除时不能通过新授权恢复原正文。

恢复前先核对旧Main执行器已停止；写结果unknown必须按原operation/业务键对账，不能换key重放。原任务仍cancelling、执行状态未知或会话已明确关闭时，保留阻塞，不创建替代实例。相同恢复请求幂等，不创建第二个批次或执行轮次。

- 新用户抢占导致的deferred属于同一有效目标下的正常恢复，沿用已有队列/lease；无需额外授权记录。
- 已失败、撤销或持久stop后的恢复，需要当前实际user turn给出的明确引用；定时输入/成员消息/completion不能签发。
- 有效范围必须同时满足原批次项目/原稳定成员集合与本次明确选择，不能由恢复扩大角色、项目或发布权限。
- 原用户目标、恢复用户来源及其摘要均进入实际manifest。任一被遗忘、分支不可见或有持久stop时拒绝后续模型/工具操作。
- turn沿用原ID，重新排队后lease增长；旧执行器的流式、已读及写操作全部拒绝。

## 续派操作的恢复

同batch/task稳定业务键继续恢复原task.steer操作。已applied时返回原回执，不创建第三轮；真实失败/blocked记录须保留失败原因和恢复授权来源，不能静默删除error或改原payload。恢复授权作为附加账本由宿主求有效权限，不采信模型传入新的authorization字段。

如果原操作尚未真正执行，重新确认当前task/revision/latest run、stop proof、原provider/native branch与项目目录后才允许同op继续。若期间真实用户已手动续派，旧operation不可附着到新revision；提示重新检查实际任务。原指令与原目标都不可被模型用恢复改写。

数据record/review与记忆追加也须有宿主业务身份和写入回执。仅保留tool call ID不足以防恢复后的模型换call/key重复入库；仅有CAS也不足以防模型重读新SHA后再次追加同段记忆。接公开恢复前应把已有批次/证据身份、review身份与追加条目身份绑定到本batch，核对同业务身份的原payload和回执；冲突保持未解决，不默默生成新业务键。优先复用已有项目批次与CAS追加组件，不另建第二份观测或记忆存储。

当前持久stop规则会阻止旧turn再次执行。恢复实现必须追加可验证的授权代次与停止边界，让旧执行器失效、后续stop仍能阻止新执行器；不能为了重用turn而删除control.stop记录。普通Main中断或无委托旧completion不属于本恢复入口，不能事后伪造batch取得权限。

## completion与handoff

稳定身份至少包含project/swarm/task/revision/run及宿主实际result身份。成员handoff正文仍是未经信任的交接，不等于最终结果、更不等于用户同意。宿主实际task.report产生的结果独立留证。

1. 未冻结：同一真实result可合入待消费通知；业务正文/补充证据以自己的messageKey保留。
2. 已冻结/正在处理：不能把晚到completion直接标为旧批次已读。只有实际manifest或成功task_status读取覆盖同一result，才可判定旧批次已经观察到该结果。
3. 已处理：相同result通知恢复原处理回执；新的补充问题、不同业务消息或不同run不吞掉。
4. 传统无目标授权的团队沿用原completion，不从历史记录猜测长期权限；开启协调前的已运行completion输入不修改。

建议增加明确的宿主result receipt与观察账本；凭run相同就丢通知不够，也不能把任意handoff字符串当真实result身份。自动生产者仅在这些观察/去重规则及恢复测试齐全后接入。

## 必测情形

- Main回复已经落库、回合输出失败：恢复不重复回复。
- task.steer已接受但Main断连：仍取得同operation，不能再给原成员新开实例。
- workspace已准备后暂停/恢复：同run/native branch，业务事件幂等（当前基础层已有专项）。
- 撤销之后新用户明确恢复，随后撤回该恢复消息：旧/新执行器均不能继续写。
- 原目标或冻结来源遗忘：不返回旧内容、不以新目标补授权。
- completion晚于冻结、早于task_status；晚于task_status；晚于批次完成：分别保留未读或恢复准确回执。
- 原成员新业务消息与同run重复结果同时到达：新消息不会被结果去重吞掉。
- 同名双项目同时恢复同样文本/业务键：保持各自原Main/原成员/文件范围。
- record/review或记忆追加已经成功而Main随后中断：换tool call、重读revision/SHA后仍复用同业务回执，不新增重复观测、复盘或记忆段。

## 实现顺序与模块边界

先在存储层追加恢复授权账本与同一batch/turn的恢复准入，再接TurnMailbox、Journal和真实工具上下文；复用既有任务操作回执，随后接结果观察/通知桥接。公开工具和Scheduler生产者最后接入，不以模型提示词代替宿主校验。每段必须保留当前正常Main、旧completion和成员交付的回归。

恢复授权保留原用户来源和原委托的撤销事实，同时记录本次真实用户消息、分支及lease。新的有效执行代次必须在宿主账本中可证明，旧持久stop/未知结果不能靠修改busy或删除历史绕过。具体表结构与旧stop准入的组合在实现前继续验证；未经验证不开放公开恢复入口。

运行态只给用户原Main中的“继续这项工作”入口与可行动阻塞，技术ID、完整历史与去重诊断留在执行记录。[恢复机制原型](coordination-recovery.html)补充同一批次恢复、旧执行器回写被拒绝、晚到消息保持未读与双项目隔离；与communication-engine.html一起阅读。两个HTML均为本地模拟，不连接真实服务。
