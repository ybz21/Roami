# 原生 Main 的直接消息结束对账

## 产品设计

在 OKR 的原生会话里直接发消息后，同一个 Main 会回到群聊协作、任务验收和定时执行。直接消息完成后，平台上的新回合和成员回调应继续排入原 Main。已发表的原生答复与后续受管任务的结果各自保留。

## 用户故事

- 用户在 Claude 原生会话与 Main 对话后，可以回到项目页继续协作。后续回合沿用同一会话、历史和模型。
- 工具前置分类失败且原输入随后结束时，宿主能核实完成的工具结果并恢复准入。
- 工具仍在执行、输入被替换或提供者不匹配时，宿主保留保护，等待可信证据。

## 技术设计

原宣传 Main 的一条直接消息已出现最终正文与未阻挡的 Stop。宿主仍挂着 9 项工具，当前项目回合一直重试 SESSION_NOT_IDLE，X 的终结回调因此排队。只读重放完整记录得到 24 项工具结果，覆盖全部 9 项，原进程检查为已停止。该直接消息没有受管 launch key，原有受管完成对账无法接手。

受管续派在校验原 prepared provider 和配置模型后，尝试核对这类无 launch key 且存在未配对工具的 Claude 状态。使用原生 hook 的 prompt ID 和精确正文哈希定位根输入，用既有完整记录对账核验当前记录的模型、目录、父链、工具与结果、Stop 及实际进程。两次观察必须一致。凭证与模型配置沿用原实例。

凭证保存在现有 message-completions 位置，下次 prepared 查询以原 transcript 复核。续派仍经过正常工作区准入。正式 reconcile-session 也支持以初始 prepared key 对账本次直接消息，原 prepared 回执的内容保持原样。直接消息没有新的受管结果、任务验收或平台动作。

## 验收

在隔离实例中检查原 prepared 身份、自动准入和重复正式恢复。未配对工具、模型/正文不符、受管输入、后续用户输入和阻挡 Stop 均应拒绝。随后用合入产物恢复原 Main，核对受管回合与真实 X 完成回调，保留原会话。恢复 Main 准入和 X/B站发布、取数闭环分开验收。
