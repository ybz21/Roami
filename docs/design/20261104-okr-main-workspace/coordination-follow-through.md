# 验收之后必须有下一步

关联 #826、#761。[交互机制原型](coordination-follow-through.html)。本地实现与隔离测试已完成，尚未提交或部署。

## Product Design

Main 仍负责判断先做什么。收到交付并独立验收后，必须留下真实的后续动作、可核验的等待或具体阻塞，再结束当前协调回合。只说“下一轮另行派发”不算接续。复用原 Main、原目标、原成员和任务；群聊保持一个简短结果，不增加常驻控制面板。

现场证据：2026-11-09 08:03，X revision25 发布四条并被原 Main 验收；Main 回合结束，三个原任务均 succeeded、持续目标未撤销、没有 queued/running 后续 job。Root 未另发“继续”，因此确实暴露了接续缺口。证据 `/tmp/okr-memory-edit-20261109/autonomous-follow-through-gap.json`；原型不调用生产接口。

## User Stories

- X 发布完成，Main 自动决定让原 B站成员制作或让原数据成员取数，无须用户催促。
- 某个原任务仍在运行时等待它，不复制实例或同时续派共享目录。
- 所需通道缺失时显示具体阻塞；普通群聊回告不能冒充实际派工。
- 中断恢复及重复完成回调沿用同一决定，不重复发帖或新开 Main。

## Technical Design

### 收口点

优先在 Main 的最终 `reply` 被接受之前校验，允许模型在同一回合补齐下一步；不要在文本已交付后把整个 turn 改成失败。`TurnJournal.finish` 的完成事务负责最后复核和持久记录，不单靠 prompt 提醒，也不根据回复中的关键词判断是否已经派工。

只约束当前有效持续目标下、实际处理成员交付/验收的协调回合；普通 Home、人工聊天、历史批次、被撤销目标不进入此规则。原授权、项目、成员、task/revision/run 与 stop/forget/lease 检查继续复用。

区分持续运营与一次性交付：不能只因 delegation 仍有效就逼迫有限目标无限派工。实施最终回复约束前，必须依据真实用户的原目标判定是否要求持续接续，保留一次性任务已达成时正常收尾的能力；不靠“每天”等关键词匹配。语义判定复用当前已保存的模型设置，按目标版本和真实来源摘要缓存，来源变化/遗忘后失效。缺少判定能力时明确报告，不能把它当已实现。

### 决定与证据

1. 已派工：读取当前批次实际 task.steer 账本、最新任务/attempt 与应用状态。排队、停止中、已应用分别记录；不能把投递叫完成。
2. 等执行：宿主检查所选原成员确有当前执行或待处理接续，绑定最新 revision/run；旧消息或成员自报不够。
3. 等排期：必须有当前项目范围、已登记的唤醒回执与真实到期时间；没有可读能力时不支持此分支，不接受随手写一个未来时间。
4. 阻塞：专用 `swarm_goal_checkpoint` 保存具体原因和本回合实际失败/等待证据，不授予发布权限，也不把目标标为完成。

已有可核验的派工/等待可以自动形成 checkpoint，避免 Main 每次多调工具。无后续动作且没有有效等待/阻塞时，最终回复返回 `SWARM_GOAL_NEXT_STEP_REQUIRED`，提示读取原任务后续派或记录具体阻塞。该错误是可恢复的工具结果，不结束 turn、不清空草稿、不重放已执行的发布。

### 持久化与恢复

复用当前协调批次与事件/命令账本，保存 delegationRevision、batchId、来源执行回执、决定种类及实际后续引用；同一批次、同一租约重试复用原身份；恢复获得新租约时重新读取状态，保存独立 checkpoint，既有 task.steer 业务身份仍防止重复派工。最终完成事务复核目标来源及租约。已接受的派工决定是历史事实，不因异步任务恰好执行完成而失效；后续完成事件由原协调回调接续。暂停/撤销保留历史但拒绝新决定。

不定时盲目启动 Main，不把 Main 自己的 progress 变成新输入，也不为每次空闲创建新回合。若需要独立恢复 job，它只能消费已经持久化且尚未执行的决定，不能根据“目标仍 active”自行重复派工。既有每天09:00外部日槽与成员完成回调仍各保留真实身份。

### 代码边界

- `storage/swarm_goal_checkpoint.py`：当前目标与后续引用的事务校验、不可变 checkpoint。
- `tools/swarm_goal_catalog.py` 与协调目录：仅开放本目标/Main 的 checkpoint；不开放管理其他项目或任意调度。
- Main 最终回复处理：可恢复的缺下一步错误；`storage/turn_journal.py`：最终事务复核。
- `context/swarm_coordination.py`：准确说明本批验收后需有真实下一步，明确制作验收不等于 publication prepare/review。
- 通用 Skill 和真实项目手册：协作收口、阻塞与等待的用法；所有新能力上线前保持候选标记。

## Acceptance

先隔离覆盖：实际 Main reply 不允许仅有验收和“以后继续”；原 task_steer 后可结束；等待运行必须绑定 fresh revision/run；跨项目、撤销/暂停、来源遗忘、旧租约、重复回调和中断恢复；阻塞必须引用实际证据；普通会话不受影响。用现有真实执行/SQLite fixture，不用纯字符串断言代替状态校验。

再用 roami chrome 在原项目验收：原成员交付 → 原 Main 独立验收 → 原任务后续执行或真实等待/阻塞；过程中 Root 不另发“继续”。平台公开、Connector确认、实际看板、复盘记忆和下一轮仍分别验收，不因此直接关闭 #761。

### 本地验证（2026-11-09）

35 项针对性测试覆盖实际 AgentLoop 的直接文本与 reply 工具、同回合错误恢复、唯一原 task.steer job、真实 revisions.advance、租约恢复、有限目标、人类暂停与成员不能冒充暂停。扩展既有 Foundation、最终回复、协调目录/权限与目标测试共 120 项通过（50.52 秒）。证据 `/tmp/okr-follow-through-20261109/expanded-continuation-tests.log`。完整质量门禁和原 Main 生产接续尚未验收，不因此关闭 #826 或 #761。
