# 原生工具前置失败的观察

## 产品设计

原成员仍有模型和工具活动，不代表它正在推进业务。本轮只读核验到原 X 的当前 launch/provider 未变，Go 返回 running、无 result 和 observationErrorCode；同一原生记录反复出现自动模式安全分类模型超时，Bash 因此前置检查未放行。这不是平台发布失败或用户拒绝，也不能通过改模型、权限档或费用配置处理。

作为 Main，需要在正式执行状态里看到当前轮真实发生过的工具前置错误，区别于成员自述和业务回执。作为用户，无需由开发者逐屏追踪才能发现这类问题。

## 技术设计

先实现有界、带来源的 `reportedToolError` 观察，不直接取消任务或自动修改权限：

- Go 复用现有 Claude transcript 的身份、原 prompt、目录、文件所有权、大小及稳定快照校验；同一次解析同时获取 reported progress 与工具错误，不增加第二个轮询器。
- 当前长提示可能带 Claude 原生 bracketed-paste 包装。沿用 `claudeInputHash` 的精确解包与哈希核验，不因包装丢失整个当前轮的观察，也不接受修改过的正文。原成员可在项目内子目录继续工作，观察目录须经规范化仍在绑定项目内；这不改变 provider 根绑定、权限或停止证明。
- 只识别同一已匹配原输入中的 assistant tool_use 和对应 user tool_result，is_error 必须为真，原生错误必须匹配已观察的分类器暂时不可用格式及同名工具。普通正文、工具输出里的引用、旧轮次和子链不形成这项观察。
- 回执仅含标准错误码、工具名/调用 ID、原 provider/prompt/目录、记录时间及来源摘要，不回传命令、正文、凭据或任意错误全文。缓存版本更新，原记录不变则不重复解析。
- 字段含义是“本轮曾观察到的最近一次前置失败”，不是当前仍阻塞、输入已停止、业务失败或发布结果。后续仍需结合当前活动与真实停止证明。此步骤不改变 running、result、busy、目录保护或准入权限。

后续 Python 桥接将同一 run 的观察保留为宿主事件，并由 #979 的监督协议判断恢复；不能伪造成成员问题或绕过停止证明。显式成员让出先由独立变更实现。

## 验收

验证精确 paste 包装、当前 tool/result 关联、旧 prompt/provider/目录和子链隔离、原生暂不可用与普通失败区分、缓存幂等/失效，以及观察不产生完成或停止回执。再用原实例的只读正式状态核验部署效果；平台发布、取数和自动下一轮另行验收。
