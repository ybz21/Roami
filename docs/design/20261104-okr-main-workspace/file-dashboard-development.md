# 从聊天开发文件化 OKR

关联工作区 #656。补充 2026-11-05 用户对目录、动态看板和原始开发 skill 的要求。

## 产品设计

项目根是工作目录，`.roami/okr/` 是定义与数据包。看板组件、顺序、指标绑定由
`dashboard.json` 定义；Connector 配置与目标指标共同确认取数口径。Connector 采集后
更新文件，页面读取已确认版本。文件是 OKR 主存储，SQLite 保留旧归档与归属索引；
运行中的成员、会话和任务仍由受管运行时管理。

新增 `okr-development` skill 作为聊天入口：从用户已有信息确定 O、KR、手段、图表、
来源和团队分工，调用真实保存能力生成目录。KR、指标、图表和成员数量按目标确定。
用户无需手工填写配置页。沿用已有目录，不迁移真实历史或重建项目 Main。

## 用户故事

- 用户聊清目标、来源和分工，得到可加载的 OKR 目录，而不是一份待人手实现的方案。
- 通过聊天调整图表与角色，保存后重新加载同一文件包；原数据、Main 和长期成员保留。
- Connector 更新日期化事实，看板随确认版本变化；失败不覆盖旧值，也不伪装成零。
- 用户可以检查分工文件，同时从真实团队状态判断成员是否登记、执行或完成。

## 技术设计

`okr-development` 的唯一正文位于 runtime 内置 skills 目录，新项目保存前即可发现。
本地开发和安装入口把相同正文与 bundle reference 同步给 Codex / Claude；不维护
内容相同的三份手册。原有项目规划、采集和执行 skills 继续负责项目内专项工作。

`Config.team` 是可选的期望团队定义，版本 1，含稳定角色 id、名称、执行器和职责；
保存/同步到独立的 `agents/team.json`。名称、id、执行器和必要职责受校验。旧客户端
不提交 team 时保留已确认定义，显式空 roles 才表示空团队计划。定义不含运行实例 ID，
不能据此创建会话、改派或回收成员。Main 使用真实登记回执中的 memberId 执行既有
Swarm 操作，计划与实际不一致时核对；不按名称猜任务身份。

`dashboard.json`、Connector 文件与 `agents/team.json` 的手工编辑先作为草稿。
`sync` 校验并确认；失效版本拒绝写入。确认后的工作区和观测经不可变快照发布，最后
原子替换 `state/current.json`。`data/observations.jsonl` 是同次发布的事实导出，不能
手工替换它来覆盖 live 数据。目录内的 Connector Go 文件仍是实现参考，当前只执行
已注册的 GitHub/manual 协议，不把任意代码或 HTML 宣称为已支持的动态组件。

前端 `configurationOf` 保留并复制 team 定义，不把派生字段、运行历史或项目元信息
送入配置保存。看板渲染继续使用已确认 API 工作区；没有新增配置页面或 UI 操作。

## 验收

新增隔离链路回归：编辑图表、Connector 和职责文件 → 确认修订 → HTTP fixture 采集
→ JSONL/确认快照一致 → 更换为空 SQLite catalog 后恢复同一工作区。采集失败保留
确认指针；不会构造历史值。覆盖无效/重复职责、旧客户端保存、已确认角色文件缺失、
真实 HTTP API 发布，以及 skill 在无项目时的按需发现和安装字节一致性。

测试使用临时目录和模拟数据来源，不改真实项目数据或模型路由。skill 验证器只证明
格式和资源有效，不把工具级回归当作真实 LLM 使用验收。最终门禁、PR 与发布结果
随交付追加；此子项完成不代表 #656/#658 的聊天和长期成员体验全部完成。
