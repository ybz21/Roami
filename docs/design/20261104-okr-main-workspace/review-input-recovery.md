# 验收与发布输入纠正

## Product Design

Main 输入不符合宿主要求时，失败回执同时说明下一步如何纠正。保持原错误码、任务、执行身份与业务键；不把输入校验误报为账号授权失败，也不通过新成员、空证据列表或绕过校验继续。

## User Stories

- Main 读过磁盘文件但未读取所选留存产物时，知道使用 `read artifact://ID` 完整读取当前轮次文本。
- Main 知道制作任务先验收，之后才能冻结发布版本；等待验收不是账号问题。
- 成员从完整初始化模板获知发布清单的嵌套身份和相对路径基准，无需反复试错。

## Technical Design

`tools/review_input_recovery.py` 为七个已有的验收/准备错误提供固定恢复说明，`ToolGateway` 将其放入失败工具回执的 recovery 字段。原错误码、failed 状态、上下文/角色/原始成员/当前轮次/工作区/哈希检查保留，不自动重试、不扩大权限、不修改任务或发布状态。其他错误不套用这类说明。

现有 Swarm 验收与发布准备工具目录同步说明 `artifact_read` 与 `file_read` 的区别、manifest.identity 的对象结构，以及 files[].path 相对 manifest 所在目录。模板根/内层 AGENTS 引导先读发布手册；完整 assets 与 package.files 同步。

## 真实触发与验证

原项目 Main 在当前 X 第15轮通过 file_read 读取 manifest、verification、业务键及图片，随后四次 swarm_verify 没有成功；所选三个留存文本产物没有对应 artifact_read 回执。宿主拒绝是正确行为。该轮清单另有顶层平铺身份、相对执行目录的路径，独立用宿主解析器得到 INVALID_PUBLICATION_MANIFEST，且文件按清单目录解析不存在。

首轮专项45项通过。真实 Gateway 回归先拒绝缺少产物读取的制作验收，再按提示完整读取留存文本并验收成功；发布回归拒绝平铺身份/正文原文，没有生成冻结版本，修正后同一业务键只生成一条事项且不授权发布。当时真实线上 Main 的纠正、冻结和发布循环尚未验证；后续真实回执见下节。

## 原团队上线复验与账号字段补充

#797 已以 193a8394 合入、部署为 okr-runtime-8d695075。原 Main 收到错误恢复指引后完整读取三个留存产物，独立验收第15轮，再续派原 X 成员修正清单。第16轮保留原 session/provider 对话，完成回调自动唤回 Main；Main 完整读取新产物并验收，按原五个业务键冻结了五份真实版本，没有 Root 代验或数据库回填。私有验收记录保留于 `/tmp/okr-review-input-recovery-20261108/`；发布循环仍未完成。

本轮另发现 `accountIdentity` 缺少工具字段说明：Main 传入 `@账号名` 被正确拒绝，之后省略该可选字段，五份版本的账号绑定仍为空。这些冻结版本不能作为已核验账号或实际发布的证明。恢复指引需明确平台数字 ID 字符串、独立来源证据和保留原业务键；历史 ID 不证明当前登录，不能猜数字、换账号或跳过发布审核。模板发布手册同步解释；每个 files 条目直接带 taskId/revision/runId，与顶层嵌套 identity 区分。

工具 schema 的描述与已有错误回执增加说明，不放宽数字 ID 校验，不自动补 ID、不自动重试，也不改变冻结、审核或执行权限。Gateway 回归先用账号名触发拒绝并确认零冻结版本，再以测试夹具的数字 ID 修正同一事项，核对实际保存的账号值且仍无发布权限。
