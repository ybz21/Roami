相同名字可以共存

不同 OKR 可以都有 Main、数据成员和“运营团队”。后端按范围和稳定 ID 查绑定；名字有歧义就要求明确目标。

有调度容量时，A 的 Main 忙不会阻止 B 独立处理；共用账号、设备或 workspace 时，仍服从共享资源准入。

目录与身份一起绑定

现有项目保留原 Main、成员和 .roami/okr 目录。底层登记 OKR scope 与项目/定义根的关系。

同项目新增独立 OKR 需要明确登记，不能把一个 KR 或同名文件夹自动当成新实例。

现有入口怎样接到一起

原生成员 CLI

Go CLI 经本机私有通道进入 Python Runtime，检查当前 task/revision/run。

Roami 成员工具

结构化工具进入同一 Swarm 服务，作者来自真实绑定。

网页 / 手机用户

经已登录 Go API 进入受管入口。人的 say 与 Agent post 保留不同署名。

群里到底展示什么

  • 成员显式发出的进展、问题和交付。
  • 真实任务结果的引用及关联回复。
  • Main 受管派工与处理回执。

原生终端全文、无群聊关联的私聊不自动广播。群聊投影引用源事实，不再复制成新的 human 消息。

消息与执行分别对账

场景后端动作不能当成
普通进展落群消息；同群可读所有成员自动执行
问题/阻塞持久收件箱；Main 空闲后合并处理新的用户授权
Main 派工原委托、有界指令、原成员任务通道随便找个同名终端发送
交付 + 完成回报同一结果只建立一次处理入口成员自述即独立验收
重试/切页/重启原范围与原键对账换 key、换 Main 再试一次
实现与后续接线

项目范围、持久收件箱与原目标协调基础层已合入代码，未计生产验收。普通 completion 仍不获得续派权限；自动协调必须继承有效原委托，不能把成员消息塞成 user wake。

显式失败恢复、结果观察去重及事件/日程生产者仍未开放。查看继续原批次的机制原型；本页逐跳效果仍为本地模拟。

数据与协作分开存储

协作运行时保存消息、收件箱、真实会话与任务。每 OKR 的业务 SQLite 保存结构化取数和看板发布，Markdown 保存个人/团队/周期记忆；源文件与发布素材按日期归档。

这是本节点多个 OKR 的设计，不宣称已交付多租户或跨节点消息联邦。

通信与多 OKR 方案投递与授权契约完整数据与团队设计所有动作仅为本地演示。
