# Main 建团队的来源准入与原子写入

关联 #744，前置多OKR范围绑定 #751。本批修复明确的来源校验缺口，不实现自动唤醒或自主续派。

## 产品与故事

Main 的建团队请求如果没有真实用户来源，应拒绝且不留下空团队、回执、事件或首页替身。用户请求已被接受，但工具进程在数据库提交后丢失回执时，再试仍找到同一个团队和原来源。

## 根因

现有 `SwarmPlans.create` 先提交团队与幂等回执，再读取 Main 用户消息并写 origin_message_id。缺失来源会在已经提交之后返回错误；合法创建在两次提交之间退出，也会留下没有来源的团队。省略 mainConversationId 的绑定调用还会先退回首页 Main。

## 技术实现

绑定调用先按 owner、真实 user turn、消息可见性、指定/绑定 conversation 检查来源，并使用来源对话作为 Main；不按名称、目录或首页默认值猜测。在创建事务中再次检查来源，原子保存团队、原来源及回执；旧回执恢复时仅补缺失来源，不替换已有来源。空 binding 不解释成人的无绑定请求。来源检查同时复用原 context admission：持久停止、已撤回上下文和失效证据不能在迟到写入中重新获得执行权限。completion 与 continuation 不能冒充新用户来源；未来协调必须另走已设计的原目标委托准入。

用户直接通过 CLI/Web 建团队的既有入口保持其 kickoff 协议；这不是把成员 post 变成 user 消息的路径。没有新增schema、模型路由或外部发布权限。

## 验收

缺失/空绑定、错误对话、非用户turn、来源被删除或在查询与提交之间撤回时，团队/回执/事件/对话计数不变；合法来源继续原Main，重试不创建替身；模拟数据库提交后丢失工具回执，原来源仍在同一提交中，恢复返回原团队。跑原Swarm命令、项目Main/长期成员及完整受影响门禁，截图记录命令/测试证据。生产运行时与原团队不变，不关闭#744。
