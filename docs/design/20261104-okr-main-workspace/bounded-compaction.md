# 长会话的有界摘要

关联 [#738](https://github.com/ybz21/Roami/issues/738)。长期 OKR Main 继续原会话和历史，不靠新实例、清消息或换模型恢复工作。

## 产品设计与用户故事

负责人持续处理群聊、任务与数据后，需要继续独立验收下一轮。历史可以超过一次模型请求容量，摘要操作必须能处理这样的历史；失败或取消不改变原对话、任务和既有确认数据。

真实旧运行时在独立验收时出现 CONTEXT_TOO_LARGE，随后同一 Main 的手动整理返回 MODEL_HTTP_400。只读重放当前历史投影约3679条、JSON约8.12MB，默认摘要来源估算约149.9万token，超过节点保存的104.9万窗口。估算不是供应商实际分词结果，400的上游正文不传播；这些证据足以复现没有摘要输入预算的问题。

## 技术设计

`context/summary_input.py` 负责摘要请求构造和逐段合并；`projection.py` 仍负责作业状态、历史选择和快照原子启用。

- 从当前 request_context 读取已保存窗口及压缩阈值；不修改模型路由、参数或网关额度。已知容量时，以现有压缩阈值（没有则用窗口）约束实际待发送的完整 prompt 估算，包括 focus、前一段摘要与 JSON 转义。未知容量沿用原有单次摘要，不臆造窗口。
- 小历史保留一次结构化 history 请求。超限时将完整历史序列化，按实际请求预算二分选择片段；带字符起止位置、总长度和上一段摘要。单条工具记录也可跨片段，所有字符按序覆盖，不截掉超长结果、不把片段作为新指令。
- 每段只输出简明摘要，并延续现有30000字符结果上限。任何一段失败不启用部分摘要；可在保留原历史后重新发起整理。此版不声称已实现跨作业的分段检查点续传。
- 每次模型调用前复核作业未取消、项目 Main 仍在原分支、分支与记忆版本未变；末尾仍完整校验原来源指纹，全部成功后只启用一个快照。取消或并发记忆变化不再继续发送后续片段。

普通对话的模型窗口、自动压缩触发点与硬性入场边界保持既有规则；本改动只约束摘要自身的输入构造。模型相关检查仍走节点实际保存路由，不能通过临时换模型宣称恢复。

## 2026-11-07：上游实际长度拒绝

schema25 新包的原 Main 已能继续回复，但自动整理仍返回 400。只读重放当轮 4278 条来源，按正常模型目录解析的保存能力（窗口1048576、阈值786432）构造首段：估算786432 tokens。走同一 Go 网关、模型和参数后，上游明确报告输入超过上下文长度，返回的上限为1048568。不能把 chars/4 估算视为供应商实际分词，也不将未知错误一律归为容量不足。无容量解析的控制请求另行保存，不冒充实际配置重放。

用户需要原 Main 长期工作，在估算偏差下仍能整理全量历史。补充方案：

- Provider 只在 HTTP400 的有界 JSON 错误中识别明确的上下文长度代码或严格的超限句式，转换为固定 `MODEL_CONTEXT_LIMIT`；不传播、记录或展示上游原文，也不对任意400重试。
- 摘要作业遇到该类别，缩小本次片段预算后重试相同来源位置。已成功的前摘要保留，失败片段不推进位置；全部来源字符仍按序覆盖。若连最小片段与必需前摘要也放不下，明确失败，不死循环或静默丢弃内容。
- 每次重试仍检查取消、原分支及记忆版本，全部成功才原子启用快照。保存的模型、窗口、参数、网关准入及记账保持原逻辑；这只是单个摘要作业的片段自适应，不是新额度或路由覆盖。
- 验收覆盖中文与转义导致的估算偏差、单条超长工具结果、后续片段被拒、其他400不重试、取消与版本变化、最小片段仍被拒以及失败后原历史可重试；最终仍需原 Main 的真实页面整理与继续工作证明。
