# 长期 Main 的聊天历史读取

## 产品设计与用户故事

用户打开长期运行的OKR Main，应立即看到近期对话及同轮工具活动。读历史失败不能被解释为
发送失败；已投递消息沿用原键对账，不能因为页面空白重复派工、重建Main或重发外部动作。

真实生产页出现“请求未完成，请重试”。独立只读调用同一个分页函数，50条请求返回48条消息、
98项活动和约70KB，耗时7.04秒；cProfile中7.005秒花在activity_summaries的SQLite查询。
该会话三万余事件，查询为找到近期消息的活动而遍历全部历史JSON。单writer排队进一步放大
耗时。证据在`/tmp/okr-member-migration-20261111/page-readonly-profile.txt`，跟踪#892。

这是历史读取性能问题。另一次Main通过conversation_history恢复全量历史，估算约76万token
后上游返回400，是独立的模型请求失败；本修复不更改模型容量、路由、参数、账目或历史内容。

## 技术设计

正式schema28迁移新增partial expression index：仅索引activity为object的事件，键依次为
conversation_id、activity.anchorMessageId、activity.id和event id。分页使用同样的object谓词，
按已选消息锚点读取最新活动，再沿用现有预览剥离、删除过滤、400项上限和响应大小预算。
不按event kind硬编码，未来新增kind携带合法activity仍可读。消息游标、分支谱系及顺序不变。

迁移只加索引，不改业务行或执行状态；失败在原事务回滚，重试走既有upgrade_schema。
Go备份允许版本同步到28，部署必须是包含新迁移和读取逻辑的完整运行包，不手改线上数据库。

## 验收

专项覆盖更新后的最新活动、不同锚点、未来kind、预览剥离与实际索引执行计划；真实旧库升级
失败回滚后事实不变，重试通过，旧出版历史升级和分页/活动专项共29项通过。隔离副本做新旧
结果逐字段对比和耗时记录，不在生产上试建索引。合入前跑quick/full，部署后重新验证真实
页面读取、Main回复和原成员继续；后续结果补在本目录，不把模型上游400算作本索引已经修复。

真实数据库固定只读快照的独立对比：同一组48条消息、95项活动，旧查询2143.33ms，新查询
49.83ms；迁移487.42ms。结果逐字段相等，规范化输出SHA为
`4145001c84e9295d4acca3dcdc44f22747ae4ad2cafee1ae77943f6a96e2b4d0`。

原生产库未写入；这是固定副本上的查询耗时，不是生产整体CPU、内存或端到端延时的结论。

## 2026-11-25 复查团队页的长时间转圈

### 复现与定位

在运行版本 `local-8adf657a` 的真实宣传项目用私有桌面浏览器进入「团队 → Main」。同一个已绑定的 Claude Main 连续打开两次，首条消息分别在 1.71 秒和 13.68 秒可见。慢样本中，`POST /api/agent/conversations` 用 12.44 秒获取既有 Main。它返回后才开始读取执行器绑定和原生转录。该样本的转录请求用了 41 毫秒。

| 同一真实节点，单项复测 | 结果 |
| --- | ---: |
| 既有 Main 身份和绑定的只读接口 | 中位数 1.56 ms、1.02 ms |
| `roami project show`，完整项目列表路径 | 一次 10.65 s，其余 19–29 ms |
| `roami project show --identity`，仅查询登记身份 | 五次 17–25 ms |
| 项目 OKR 确认工作区的读取 | CLI 五次 56–79 ms |
| 项目 Main 原生 Claude 最近 50 条 | 中位数 47.79 ms，响应 77,927 字节 |
| 独立 Claude / Codex 最近 50 条 | 中位数 14.12 ms / 44.93 ms |
| 全量会话概览 | 中位数 296.90 ms，33 个会话 |

调用链见 `OkrMainChat.tsx` → `create_conversation` → `registered_project` → `roami project show` → `ProjectsList`。团队已提供持久 Main 的对话 ID，页面仍串行执行状态查询和创建／获取入口。该入口为确认项目身份走完整项目列表。缓存过期时，项目列表会扫描全部项目的工作树、会话归属与终端状态。这与完整项目查询的慢样本相符。单独打开 Codex 或 Claude 的转录没有这段 OKR 身份解析链路。

Claude Main 的转录文件实测约 23.7 MB。Go 已从尾部倒读，首屏默认 50 条消息，候选取最近 200 条物理记录。这份文件按相同窗口读取约 2.49 MB；向上翻页按 `before` 字节游标读取更早窗口，增量按 `nextOffset` 续读。应用托管历史的单项读取中位数为 72.16 ms；这轮长转圈的慢样本集中在转录发起以前。

### 修复方案

1. **先缩小后端身份查询。** 让 `registered_project` 复用已有的 `project show --identity`；执行器工作区解析已经使用这条路径。保留项目不存在、目录不可用和身份变化时的原错误语义，按需验证单个项目目录。缺少既有 Main 时仍走当前创建流程。这个改动先消除完整项目列表刷新对首屏的影响，也覆盖旧前端。
2. **打开已有 Main 时直接读取。** 从团队选择 Main 时，用已知对话 ID 读取并核对节点、项目、对话、分支及执行器绑定代次。独立的能力与执行状态读取可以并行；验证后的原生转录即可显示。给缺少对话 ID 的入口提供按项目读取既有绑定的轻量查询。全量会话概览移出聊天首屏，用绑定中的原生会话身份或单会话查询验证可用性。切回同一核对过的对话复用近期消息；切项目、节点、分支、绑定代次或登录状态时隔离缓存，并丢弃晚到响应。原生会话暂时不可用时明示状态，并按现有策略提供相同项目的只读历史。
3. **转录优化按实测排序。** 保留现有的尾部读取、字节增量和历史锚点。受管转录现在会遍历配置目录找文件，后续若在大配置目录上测得瓶颈，再缓存经过身份验证的文件定位。保留目录约束、文件轮换和唯一性检查。需要限制长 JSONL 记录的首屏开销时，使用按字节的批次预算和继续读取的游标，覆盖长记录、半行追加与工具结果的关联。

### 验收方案

- 固定同节点、同项目、同会话，分别记录入口点击到首条消息、Main 身份查询、执行器就绪、转录下载和 DOM 渲染。冷开及切回各跑至少 20 次，覆盖项目列表缓存过期。目标为同机打开既有 Main 的 p95 不超过 2 秒，已验证同一绑定的缓存切回 p95 不超过 400 ms。
- 让完整项目列表和全量会话概览故意延迟，核对近期历史仍能出现。覆盖首次创建、归属冲突、绑定代次切换、失效文件游标、只读历史、滚动翻页以及模型等待期间照常读历史。普通 Codex 和 Claude 会话一起回归。
- 本轮只有诊断和方案。浏览器两次实测的明细位于 `/tmp/okr-history-latency.lZ7QocMw/browser-timing.json`，CLI 对照位于同目录的 `cli-timing.json`。

### 首批实现（2026-11-26）

已有专用 Main 的团队入口直接读取并校验会话身份。缺少已绑定 Main 时仍走创建或迁移，服务端改用已有单项目身份查询，检查返回的项目 ID。原生会话仍按原有概览匹配项目、执行器和会话生命周期。概览拆分与转录文件定位优化留作后续。

用本次构建包和原项目实际只读接口复测，两次打开原生 Main 的首条消息分别用 2.81 秒和 1.49 秒。两次都读取真实转录，且未请求创建接口。另将旧流程的创建接口响应在浏览器中延迟 12 秒，旧版首条消息用 14.08 秒；新版在同一延迟条件下直接打开。公开截图使用示例消息。以上为专项证据，尚未完成冷开与切回的 p95 验收。
