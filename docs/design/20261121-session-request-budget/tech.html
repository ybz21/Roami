技术方案

现在是谁在发请求

工作台每轮都查三个 Agent

在桌面，useTerminalRuntime 每 5 秒给每个打开的命令行会话依次请求 /claude、/codex 和 /opencode。不同会话同时查。手机只在打开会话时查当前会话。固定的计时器会照常开下一轮，所以慢请求可能重叠。 运行时轮询

会话概览只要有内容变化，例如更新了最后活动时间，工作台就会重新生成标签清单。即使还是同一批会话，前端也会重启 Agent 查询和标签抓屏，立即发出新一轮请求。 会话索引 · 标签清单

好几个地方分别读取终端画面

TerminalPane 每 4 秒给所有命令行标签读取屏幕，用来判断是否等确认或需要恢复。桌面收起终端区时只把它缩为零宽，组件还在。终端确认框和对话里的确认框分别按 1.2 秒读取。隐藏的对话也保留了确认框。LiveTail 用来显示生成中的终端输出，有需要时再按 800 毫秒读取。 终端面板 · 终端区 · 确认框 · 实时输出

项目详情每 6 秒查一遍它的会话，分别问 Claude 和 Codex 是否在跑，再请求终端画面。会话树和注解每 5 秒更新时，前端会重新生成项目会话清单，可能提前开始下一轮。展开的工作区还每 5 秒查一次末尾预览。 项目详情

每个对话各自读取新消息

前端把 Agent 存下来的对话记录叫作转录。对话打开时每隔约 1.5 秒读一次，切走后约 6 秒读一次。每个对话各自安排下一次请求。浏览器标签隐藏时，前端没有暂停或取消这些请求。遇到错误也没有延长间隔。 对话请求

工作台和项目 Main 可以打开同一个会话的对话。两个地方会各自记录上次读到哪里。截图中相同的参数也可能来自一个对话连续两次没读到新消息。看 Network 的完整 URL、时间和 Initiator（发起请求的代码）才能区分。 项目中的对话

小响应也可能让服务端做不少事

服务端要查 tmux（管理终端会话的程序）和系统进程，才知道某种 Agent 在不在跑。找到 Claude 或 Codex 时，还要找对应的记录文件。找到 OpenCode 时，还会读取屏幕并查 SQLite。读终端画面也会调用 tmux。读转录要检查访问权限，再定位或打开文件。 Claude 和批量查询 · Codex · OpenCode · 读屏请求

分三步改

一 · 整批查状态，只给当前会话查详情

让工作台、独立会话页和项目详情共用 useAgentKinds 和 useSessionOverview。第一个每 6 秒查一遍会话各用哪个 Agent。第二个每 5 秒查一遍它们是否在响应、是否等输入和终端最后一行。项目详情用这份数据更新标签。用户展开工作区、需要完整的末尾文本时，再单独取一次。会话清单仍是原来那批时，普通状态更新无需重启 Agent 查询。

只有你正在看的会话需要查目录、对话 ID 或恢复信息时，工作台才请求对应 Agent 的详情。刚打开、Agent 刚换、手动启动或恢复时立即查一次。可见期间每 5 秒再查一次，切走就停。

批量请求对每个会话只给一个 Agent。一个会话可以有多个终端窗格（pane），里面可能跑着不同的 Agent。结果还没到、刚启动或窗格归属不清时，只允许当前会话多查有限几次。确认新 Agent 和对应的对话之前，保留已经核实过的关系。验证普通命令行如何进入和退出 Agent，以及桌面和手机手动切换显示方式。

二 · 让同一个会话共用一次终端画面请求

其他标签用批量状态判断是否等输入。对你正在看的会话，确认框、实时输出和恢复入口共用一次画面请求。合并前，要用同一窗格验证一次请求能覆盖现有 lines=40 和 lines=50 的读取范围，然后按各自范围取用。一般每 1.2 秒请求一次。需要显示实时输出时，用 800 毫秒间隔，两种情况都只跑一个定时器。

收起终端区、切到文件或隐藏浏览器标签时，停止为离开视野的会话请求画面。如果同一会话还在项目里显示，它可以继续请求。最后一个显示该会话的地方关闭后，取消正在等的请求和下一次定时。沿用 pollWhileVisible，等上一条请求结束才安排下一条，超时会取消，失败后逐步拉长间隔。

请求失败时，可以保留上次画面，但不能用旧问题发按键。发送按键后要用这次操作之后读到的画面核对结果。Codex 恢复前也要重新读屏，继续执行原有的备份、中断和恢复校验。

三 · 让同一个对话共用新消息请求

两个地方都在看同一个对话时，只发一份新消息请求。合并前先确认它们连的是同一个节点（运行会话的机器）、同一个会话和同一种 Agent，也确实用同一份记录。受管会话额外检查执行代次（服务端用来区分这一次运行和上一次运行的编号）。草稿、滚动位置和项目 Main 的当前回合状态各自保留。

请求转录时，offset 记住上次读到了文件的哪个字节。它就像书签，让下次只读后面的新内容。对话活跃时约每 1.5 秒查一次，连续几轮确认空闲后约每 10 秒查一次。没人看就停。发消息、重新打开对话或断网恢复后，马上从书签接着读。

首屏仍取最近 50 条。往上翻用 before 读更早一页，Pi 仍按现有规则替换消息窗口。文件被替换、截短或会话换了一次运行时，重新确定从哪读，忽略随后返回的旧请求。权限或绑定变化时清掉旧数据，切换节点时取消旧节点请求。需要跨页面保留的消息放进现有的工作区缓存，并沿用它的容量上限。

每一步都可以单独测试、提交和回滚。会话创建、关闭等事件继续触发刷新。做完生产对照后，如果服务端仍有明显的重复工作，再考虑由服务端统一采样或主动推送消息，并验证断线后能补齐。

怎么做上线前对照

  1. 改前、改后用相同的生产构建配置、节点和会话。等首屏稳定后录 30 秒 Network。测 0、1、8、20 个命令行会话，并覆盖收起终端区、打开文件、项目详情、独立会话页、同一对话在两处打开、切到后台再回来。首屏和恢复过程各自单独计。
  2. 按完整请求路径、会话、参数和发起代码归类。记录失败、取消、重叠、没有新消息的请求比例和传输量。分享结果时删除会话路径和敏感参数。用 scripts/dev/isolated-roami.sh 启停本地测试实例。
  3. 在同一个测试窗口测服务端的请求耗时、tmux 查询和读屏次数、转录读取量、CPU 和内存，再单独测浏览器的主线程和内存。用真实会话测权限框出现到可点击、消息写入到可读的时间，比较两版较慢的一批操作（P95）。
  4. 复查 Claude、Codex、OpenCode、Pi、普通命令行和 Roami 原生会话。覆盖慢请求、乱序、暂时没有转录、旧版本节点、换节点、多个窗格、同名会话重建、会话原地重启、记录换文件和权限失败。桌面测 1280、1920、2560、3440 CSS px，手机用 Android 真机确认触摸和前后台切换。
