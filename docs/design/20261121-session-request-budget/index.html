会话请求频率优化

工作台对每个已打开的 CLI 会话重复探测 Agent 并抓屏。桌面终端坞收起时组件仍然挂载，隐藏的对话也会持续读取转录和提示。优先复用现有批量状态，并让每个可见会话共享一份实时读取。

各项来自独立计时场景，使用当前组件和固定 API 响应，排除挂载首轮。数字对应前端发起的调用，生产网络及 CPU、内存数据需另测。

截图里的请求从哪里来

codex / opencode
每轮对所有打开的 CLI 标签依次请求 claude、codex 和 opencode，所以 Network 会出现成批的同名条目。后端即使返回未运行，也已经查过 tmux 与进程树。
capture?lines=50
标签每 4 秒逐个抓屏，终端和对话中的交互提示每 1.2 秒再读一份。项目详情也在针对所属会话抓屏。
transcript?offset=…
渲染对话以字节游标增量读取。可见时约 1.5 秒一轮，后台对话约 6 秒一轮。同一会话有两个视图订阅时，可以发出相同游标的两次请求。
agents
/sessions/agents 是已共享的批量种类查询，正常间隔 6 秒。单条记录与现有设计一致。

截图仅显示请求名称和部分查询参数，且开启了 Keep log。还需完整 URL、Initiator 和固定时间窗口来确认各条记录的会话归属与实际频率。用户原图保留在本机。

先去掉随标签数量增长的请求

  1. 用现有批量接口供工作台和项目详情显示 Agent 种类、运行和等待状态。只为可见会话读取所需的 Agent 详情。
  2. 让当前会话的交互提示、恢复检测和实时尾行共用抓屏。收起终端坞、切换到文件或隐藏浏览器时暂停相应消费者。
  3. 合并同一对话的增量读取。恢复时沿用字节游标，空闲会话降频，发送或重新打开时立即追上。
