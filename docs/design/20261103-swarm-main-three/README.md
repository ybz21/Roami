# 蜂群：Roami Main 编排与 Three.js 工作室

2026-11-03 · 方向已确认，首版实施中。桌面、手机统一为「协作 / 群聊 / 看板」三个 Tab。实际交付与未通过项见[验收记录](acceptance.md)，下方保留产品设计。

[打开动态概念稿](index.html) · [架构与实施细节](technical-design.md) · [本轮检查与后续验收](acceptance.md)

仓库里的概念稿固定引用 Three.js `0.180.0` 的 CDN 模块，便于保留可修改源码；本轮另交付了内联依赖的单文件 HTML，手机和桌面均无需访问外部 CDN。单文件产物和截图不提交进主分支，位置见检查记录。概念稿的“手机稿”按钮是显式布局演示开关，正式组件仍使用项目的 `useLayout()`。

## 建议决策

1. **主 Agent 就是现有 Roami Main。** 蜂群绑定发起它的 Main 对话；Main 负责理解目标、拆解、分配、协调、验收和向用户汇报。项目页发起时创建或明确选择一个普通 Roami Main 对话，再绑定蜂群，不另起 Claude 指挥，也不新增一种 Main 运行时。
2. **成员是可持续续派的执行者。** 首批支持 Codex、Claude Code、Roami；Roami 成员使用现有 native Worker 分支，采用节点保存的 worker 模型路线与能力。其他已注册执行器按能力加入，执行器和模型分开选择。
3. **用 Three.js 重做办公室动画。** 保留“大家一起工作”的亲切感，换成有体积、光照、动作和消息流的等距工作室。场景与可访问的成员列表共用业务快照；看板、交付物和 Main 对话仍然是实际工作入口。
4. **蜂群成为现有任务体系的协作视图。** 新增编队、计划、依赖和成员绑定，复用任务、执行批次、回报、验收、续派和停止机制。执行器说“完成”只进入待验收，验证通过才显示完成。

## 为什么要一起重构

| 代码现状 | 本次提案 |
| --- | --- |
| `internal/cli/swarm/members.go:adopt` 默认创建 `cc-<群>`，直接启动 Claude；`swarm new` 依赖本机安装 Claude | 新蜂群从发起的 Roami Main 对话编排；没有安装 Claude 也能使用其他成员 |
| `Swarm.tsx` 1123 行，场景为 SVG、`foreignObject` 和 CSS 工位；页面兼任请求、布局、看板与广场 | 页面、数据订阅、场景、列表、任务视图拆开，Three.js 只承担视觉和拾取 |
| `internal/swarm/swarm.go:liveStatus` 抓终端文本推测活动；会话消失且有日志也可能返回 done | 任务完成以当前 revision/run 的回报与验证为准；终端活动仅作“运行现场”的辅助观察 |
| `--depends-on` 是软依赖，成员创建后立即启动 | 新受管任务支持显式硬依赖；依赖的指定产物通过验收才派发，讨论关系单独展示 |
| 详情页 2 个 3 秒轮询和 1 个 2 秒轮询 | 首次快照加现有事件通道的增量；断线才做共享、可见时、有退避的恢复读取 |

## 产品设计

### 用户故事

| 用户想做什么 | 预期体验 |
| --- | --- |
| “帮我做这个项目，前后端可以并行” | Main 在原对话展示简短计划、成员和验收点；用户已授权执行时直接开工，不增加常规审批步骤 |
| “前端用 Codex，研究用 Claude，整理交给 Roami” | 执行器选择绑定到对应成员和任务，缺安装、认证或能力时提示原因并保留选择 |
| “现在卡在哪里” | Main 回答当前阻塞与下一步；工作室选中对应成员，详情显示所缺输入或恢复动作 |
| “把刚才那部分改一下” | 续派原任务与原执行器，保留原工作区与供应商对话，不另建一份相同任务 |
| “完成后给我能用的东西” | 先显示已验证结果、文件和预览，再按需看执行记录；完成动画不会替代检查 |
| 在手机上查看和干预 | 项目下直接进入蜂群；单栏、短场景、完整成员列表；任务和成员详情用全屏二级页 |

### 入口与布局

- 保留项目下蜂群入口和现有深链；首页 Main 的蜂群任务可直接“查看协作”。不增加底部第五个导航入口。
- 桌面与手机统一为“协作 / 群聊 / 看板”三个 Tab。协作展示 Three.js 工作室、成员与状态；群聊展示绑定 Main 的真实对话和成员讨论；看板展示受管任务、依赖与产物。切换保持草稿、选择与滚动，群聊未读与任务阻塞在 Tab 上提示。
- large：页头用 `.tt-pagehead`；协作 Tab 中并排场景与成员列表，群聊保留对话阅读宽度，看板铺满工作区。群聊使用同一 Main 记录，不另建第二个指挥。
- expanded：保持三个 Tab；协作使用场景与紧凑列表，任务详情按需展开。复用现有工作区与终端停靠行为。
- compact / medium：沿用项目上下栏；场景占一段内容高度，下面直接显示成员及阻塞。成员、任务与长交付结果进入 `MobileSubPage` / 专用路由，一层返回栏、一个滚动区。
- 点击工位与点击成员列表效果一致。桌面在检查器打开，手机打开全屏详情。键盘、屏幕阅读器和无 WebGL 设备均能通过 DOM 列表完成同样的操作。
- 保留“任务 / 结果 / 协作记录”信息；广场的必要讨论进入协作记录。发给指挥的用户消息进入绑定 Main，避免“写入广场但指挥没收到”。
- 常用动作只有查看任务、继续补充、处理阻塞。暂停派发、停止执行、归档和关闭资源分开命名；归档不默认杀成员，关闭复用原任务资源收尾流程。

### 视觉方向：等距协作工作室

单个开放式工作室，中央主工位略高，周围分布成员工位。哑光浅色角色、深色桌面、柔和定向光，蓝色用于选择与派发，绿色用于运行与验证成功，黄色提示等待或待检查，红色只用于失败。角色不穿供应商品牌色；执行器身份用文字和现有官方 `AgentLogo` 表达。

角色用几何体搭建小型机器人：头部、躯干、手臂、显示器、键盘和座椅。轻微敲击、转头、呼吸让工作有生命感。主 Agent 不靠巨大星球或满屏粒子抢占内容；选中工位后镜头只做短距离平滑聚焦，不持续自动旋转。

| 业务事件 / 状态 | 动画与可读状态 |
| --- | --- |
| 计划就绪、任务待派发 | 工位依次出现一次；依赖连线静止，显示“待派发” |
| 已确认派发 | 蓝色光点从主工位流向目标，持续约 600ms；投递结果未知时不重播、不显示运行 |
| 当前执行批次运行中 | 手臂低幅敲击、显示器条带移动、轻微呼吸；文字显示“执行中” |
| 等上游 / 等用户 / 无法继续 | 停止敲击，黄色状态标记；三种原因在 DOM 详情中分开，不能只靠颜色 |
| 执行器已回报 | 光点回到 Main，显示“待验收”，不提前变绿 |
| 独立验证通过 | 短暂绿色闭环和一次抬头动作，随后静止；显示“已验收” |
| 失败 / 未知 / 失联 | 停止工作动作，失败用红色、未知用中性色，保留最后已知时间和恢复入口 |
| 暂停派发 / 页面不可见 | 前者不再开新任务，已运行任务继续；后者停渲染，均不冒充任务取消 |

概念稿用演示状态循环表现这些动作，页面明确标记“演示数据”。其中“等待输入”工位用于验证黄色等待状态；生产场景只能从真实事件触发，不按计时器生成业务进展。

### 动效与性能边界

- Three.js 原生集成，暂不引入 React Three Fiber；正交相机、固定等距默认视角，平滑选择和显式复位。先不做任意拖工位、自由飞行镜头、物理碰撞和角色漫游。
- 页面同底、方形模块、单边细分隔线。舞台空白使用 `--bg-base`；材质从主题 token 读取，主题变更只更新材质；UI 的类型、颜色、圆角和留白只用既有 token。
- 桌面目标 60fps、手机目标 30fps；这些是**待实测预算**。初始 DPR 上限桌面 1.5、手机 1；手机关实时阴影与后处理，桌面只给关键物体柔影，首版不加 bloom。
- 1、8、24 成员为完整工位规模，更多成员按任务组分页 / 聚合，列表始终完整；重复几何与材质复用，必要时用 `InstancedMesh`，不随成员数创建 renderer。
- 运行帧中只改 Three 对象，不每帧 `setState`；场景不发请求、不捕获终端、不调用模型。
- 无动画偏好、用户关闭动画、静止终态采用按需渲染；隐藏标签 / 离开路由停止 animation loop，恢复先获取最新状态，不追补过期粒子。
- 不支持 WebGL2、context lost 或模块加载失败时保留成员和任务列表，给出一句降级提示。卸载释放几何、材质、纹理、监听器与 renderer。

## 推进顺序

| 阶段 | 可评审交付 | 验收重点 |
| --- | --- | --- |
| 0 · 本轮 | 本方案、动态概念稿、源码现状与边界 | 明确 Main 复用、成员执行器、视觉方向和兼容策略 |
| 1 · 任务闭环 | Main 发起蜂群，Codex / Claude / Roami 各完成受管任务，状态可恢复 | 回报、验收、续改、重复派发与未知结果；隔离实例验证，不接管用户现有会话 |
| 2 · Three.js 场景 | 真实快照驱动工作室，列表和详情联动，深浅主题与降级 | 桌面 / Android 触控、帧率、资源释放、键盘和屏幕阅读器 |
| 3 · 依赖与迁移 | 硬依赖、整合验收、旧蜂群选择性接管、事件订阅 | 断线与重启不重复启动；旧会话、日志、未合入分支不丢失 |

不把重构一次推完：先建立受管任务的数据契约，再接真实场景。旧蜂群在过渡期继续可读可用；不为展示新动画批量接管、重启或终止已有成员。

## 评审时需要确定的两点

- 推荐沿用等距工作室。概念稿是几何角色与动作的方向稿，最终模型细节可在同目录修订，不影响执行架构。
- 推荐同一蜂群只绑定一个明确的 Roami Main 对话；允许一个 Main 管多个蜂群。项目页发起时显式关联对话，不把全项目消息自动混进一个对话。

本提案按开发者设计文档例外使用中文；正式产品所有文案、aria-label、错误与提示必须接入全局中英文 i18n。概念稿未接生产服务，不能作为功能或手机产品验收通过的证明。
