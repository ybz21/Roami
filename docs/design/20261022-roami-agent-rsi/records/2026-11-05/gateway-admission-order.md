# Go 网关准入顺序

## Product Design

启用每日额度时，Go 网关等待在途请求结算后再尝试原有额度准入。旧实现广播唤醒后重新抢锁，没有等待顺序；一个已等待的 Main 请求可能持续被后到请求越过。修复让实际准入按入队顺序尝试，保留取消、配置重验和无限额时的并发。

问题由 RSI 并行诊断暴露。其包装器等待时间明显大于实际网关调用耗时；历史未知记录保持，不能从缺少账本行倒推未发送。该历史等待与旧实现相符，但不能用本次受控复现证明那一笔请求的全部原因。原始诊断见 [来源复核候选的脱敏证据](https://github.com/ybz21/Roami/blob/ef3c03ac56230422a514eb26410685ec82e4f999/docs/design/20261022-roami-agent-rsi/records/2026-11-05/evidence/source-reply-review.json)，该候选仍为草稿，#605 未解决。

## User Stories

- 较早到达准入队列的请求获得下一次机会，不被后到的后台请求持续插队。
- 取消队首或队中请求后，其他请求继续按原顺序处理；取消请求不创建调用账目或稍后重放。
- 等待期间撤销密钥或改变模型配置，排队后方请求也及时核对，不必等不相关的调用结算。
- 取消每日额度后，全部合法等待者能恢复并发；公平队列不成为额外的并发上限。

## Technical Design

`internal/modelgateway/admission.go` 在 Handler 原互斥锁下登记等待者，只有队首可调用原 `Ledger.Admit`。每次唤醒仍检查请求 Context、关闭状态及最新路由 / 密钥配置。成功或永久拒绝后出队并唤醒下一位；不是等整个上游调用结束才让下一位尝试。

结算通知只唤醒队首。配置变更继续唤醒全部等待者做验证，实际账本准入仍由队首完成。取消任意位置的请求都移除对应条目；数组空位清除引用。没有本 Handler 活跃调用的历史 pending 仍按原逻辑拒绝，不等待其他执行器或猜测结算。

`Ledger.Admit`、价格、额度、历史未知状态和记账时机不变。等待者没有提前创建的调用账目；无限额时原账本允许并发，队首成功出队后下一位立即尝试。没有新增 Token、请求、消费或时长上限，没有 Python 改动，也没有覆盖节点保存的模型路由、参数和能力。

## 验收

零外部模型的旧源码控制：先让一个请求等待在途结算，再在结算已写入、通知尚未发出时提交后到请求，模拟合法的调度间隙。原实现连续三次先准入后到者，均失败；原来的等待者和账目仍完整结束，不靠停止服务制造结果。

修复后的网关整包 `go test -race` 通过。四组场景各 20 轮通过，其中取消覆盖队首和队中两档：

- 较早等待者先于后到者准入，三笔受控账目各结算一次。
- 在途用量未完成时，队中已失效请求立即拒绝，不创建额外账目。
- 取消队首 / 队中条目，剩余两个请求顺序不变，取消者不落为已发送。
- 取消额度后，三个等待者在原活跃请求尚未结算时均获准，保留四笔真实 pending，再逐笔正常结束。

初稿仅唤醒队首，新增控制发现配置失效的非队首请求会延迟拒绝；该失败保留，最终恢复配置变更时的全队验证。现有密钥撤销测试仅同步等待状态的内部字段，保留未到上游、401、调用次数与记账断言。

完整门禁和竞态结果记录在 [gateway-admission-order.json](evidence/gateway-admission-order.json)，提交钩子 quick 的输出截图随 PR 提供。Go 以外只新增本文和证据；按仓库范围检查跳过无关 Python 依赖、格式和测试，前端基础检查及 full 构建仍执行。
