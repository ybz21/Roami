# Main 来源复核候选

**未验收、未上线，#605 仍未解决。** 本候选增加来源复核机制，但同一保存 Main 的串行新轮仍误将带 `<reply>` 包装的文字判为严格 JSON。不能用单次完整通过或机制测试代替稳定的模型质量。

续 [PR #665](https://github.com/ybz21/Roami/pull/665)，关联 #605、#635、#350、#443、#445、#446。冻结原始对话、判定器、期限和节点保存路由、参数、能力保持。评测后台为合成 checkpoint，不是真实 Worker 交付。

## Product Design

多轮增删约束可能被 Main 解释成占位词、布尔值或另一条指令。候选让 Main 显式提交 JSON，并在最终回复、提问提交前核对有效用户来源。拒绝把具体不一致交给 Main 自行纠正；宿主不补答案、不改任务 ID，也不按 Case ID 或固定标题选择分支。

复核采用保存的同一 Main，是生成策略，不是独立双模型评分。普通终答增加一次复核；结构化终答另加一次无草稿原文阅读，提问另加一次字段提取。拒绝后的重新生成还会增加调用。没有调用、费用、延迟、CPU 或内存降低的结论。

## User Stories

- 逐轮增加、修改、删除约束后，最终 JSON 保留用户当前要求的原文和类型。
- 用户已给出文字时不要求重复提供；真实目标歧义和缺失权限仍能提问。
- 用户忘记来源、租约或模型变化后，不再以旧来源启动后续复核或提交回复。
- 模型依赖协议错误、超时、取消和未知用量保持可审计，不以重复改工具参数恢复。

前两项仍有实模质量遗留；后两项有明确的机制回归，不能把它们混写成 #605 已修复。

## Technical Design

`replies/source_review.py` 实现复核，`protocol/ports.py` 定义循环端口。`core/loop.py` 保存实际 Main 提示及完整投影来源 ID，复核无工具终答；`tools/main_catalog.py` 约束 `reply` / `ask_user` 的提交。Worker、流式预览不使用此复核。后台完成回调不按最近无关用户请求重新审查，原交付绑定继续生效。

`reply` 的 `text` / `json` 互斥；宿主只做标准 JSON 序列化，拒绝非有限数字，不猜类型或修补值。紧凑工具目录保留互斥 schema。`delegate` 可带短标题，用户任务名与文件名分别保留；这不构成通用的任务目标选择保证，#635 仍需真实验收。

复核验证 owner、conversation、branch、running 状态、租约和上下文准入。完整投影 ID 与数据库实际用户消息交集决定来源，排除未来输入、其他未处理回合、任务内部指令和已忘记来源。不能把过滤后的消息列表与原投影 ID 按位置配对，工具回复会造成错位。`TurnMailbox.claim` 返回更新后的运行状态和递增租约。

结构化草稿先由同一路由只读取按时间排列的用户原文，不看草稿或先前助手解释。读出的自由文本仅在最新用户原文能定位字段和值相邻跨度时，才形成回合内字面证据；引号中的材料和另一个 ASCII 字段的后缀不建立绑定。主语义复核仍核对真实用户要求、当前工具上下文和 accepted handoff，区分接收与交付。真实图片按多模态输入转交。

`replies/literal_fields.py` 只拒绝已输出字段中不受来源支持的改写，及把整个字段声明复制成值的情况。显式要求包含前缀的值、来源允许的其他值、null、数组、对象、转换和新创作继续保留语义复核路径。宿主不增加缺失字段，也不输出另一个答案。已验证跨度在同一 owner、会话、分支、租约的上下文重建中保留，按最新用户来源和模型指纹隔离，回合结束清理。

v4 在最终发布前重验来源，但源阅读等待期间发生变化时仍会启动下一次复核。最终 v5 在阅读、提取之后及返回判定之前重验相同上下文对象、来源、模型实例及设置指纹。忘记、租约、上下文、模型、参数变化的答复/提问十项旧控制全部失败，新实现全部通过；不会把旧来源再次送进后续请求。

额外调用复用 MeteredModel、EpisodeBudget 和 Go 网关，Python 不新增 Token、次数或费用上限。保存的零秒期限仍表示不限时，显式期限保持。坏协议和模型超时归为依赖失败，保留原错误码，终止参数修复；取消保留已有用量。私有事件只记录版本、请求指纹、网关编号、用量、状态和错误，不把内部过程塞进聊天。

生产 serve、实际 Native / Container 执行器及保存模型对话验证启用策略，离线协议夹具显式保持旧路径。执行指纹包含策略版本；最终为 `source-drafts-v5-source-admission` / `container-uds-v38-source-admission`。镜像必须声明 `org.roami.rsi.source-reply-review=3`，旧候选在模型执行前拒绝。发布需要匹配宿主与镜像。

## 实模结果与失败边界

v5 实模运行的共同冻结指纹为 `94abfdad2303fdb02c3c6a2847136e2fc0d10e5c44223e9855e568e1fd647cd2`，该批调用结束后才补本文与脱敏证据。以下是独立运行，不能合成一个全通过的成绩：

| v5 运行 | 场景通过 / 观察 | 回合正确 / 观察 / 计划 | 实际结果 |
| --- | --- | --- | --- |
| 完整原始对话 | 16/16 | 62/62/62 | 208 笔网关 known/200 |
| 聊天重复 A | 4/4 | 18/18/18 | 58 笔 known/200 |
| 并行聊天重复 B | 0/1 | 4/4/18 | 原 300 秒场景期限内未完成；一笔包装器用量未知 |
| 新 Runtime 串行聊天 | 3/4 | 13/14/18 | 首轮输出带 `<reply>` 标签，复核误接受；43 笔 known/200 |
| 同镜像真实容器数值任务 | 2/3 | 不适用 | 第一项 RSI_TIME_BUDGET；30 笔网关中一笔 unknown |

串行失败在首轮，后续标题追加轮未观察，不能说本轮又证明标题值错。原 Main 文本包含完整标签；复核却称“仅返回 JSON”。宿主未替换文字或放宽原 `CHAT_JSON_REQUIRED`。这是真实质量失败，当前候选保持未验收；没有继续调提示或做付费重复来挑选通过轮。

并行超时也保持失败。超时前两个包装器耗时 37.238 / 54.443 秒，对应真实网关仅 1.765 / 1.413 秒；最后 162.309 秒等待内另有 52 笔 known/200 请求完成，没有与最后包装器匹配的账本行。它与当前 Go 在日额度下的串行准入等待相符，不能据此断言供应商单次调用超过 120 秒，或证明未知请求完全未发送。没有改大原期限、清账或猜零；准入公平性应单独复现。

数值任务沿 #665 的冻结 units-v3 合同，不是旧套件收益比较。两个成功、一项超时均保留；未知网关项实际 958 毫秒，Token 与费用为空，不补成零。不存在伪造的独立评分、正式全套成绩或晋级。
