# Codex 原生命令完成与丢失回调恢复

关联 #350、#443、#445。修复原生执行回执恢复，不提升内容质量成绩。

## Product Design

Codex 的命令 Hook 使用 `exec-<UUID>`，模型工具响应使用另一个 `call_id`。丢失 PostToolUse 回调后，即使原生记录已保存命令结束，原实现仍保留未收尾工具，阻断完整回合的结果恢复。

现在由既有状态查询路径核对同一提供方、同一回合的原生命令结束事件。每项未收尾工具都有正面证据，且完整回合与进程停止证据通过，才重建原执行结果。查询不会发送输入、停止会话或重放工作。

## User Stories

- 已结束的命令丢失 Hook 回调后，原任务可以继续正常结果核验。
- 另一回合、另一会话、仍运行的命令和未结束的子 Agent 继续保持未知。
- 取消请求、旧未知历史和已有不可变结果保持原来的证据边界。

## Technical Design

`session-codex-completion.go` 的原生记录读取增加 `CommandExecution` 证据。`item_completed` 必须明确匹配绑定的 `thread_id` 和 `turn_id`；命令标识必须为原生 `exec-<UUID>`，进程标识和退出码存在，状态为 completed 或 failed，起止时间有序且不晚于根回合结束。

重复标识使该证据失效。所有未收尾工具必须逐项匹配，不能只找到其中一项；普通模型工具输出和子 Agent 标识不替代此证明。命令 failed 表示命令已结束，不作为命令成功或交付通过的证明。

读取仍要求唯一、同用户所有、非符号链接且大小受限的提供方记录；原提示哈希、工作目录、根回合、工具调用/输出配对、最终答复、稳定 inode/长度/修改时间和完整文件哈希继续核对。原会话与 pane 身份、原进程启动令牌、专用 cgroup 内进程停止证明保持。根进程缺失仍不足以证明已停止。

既有取消的投递证明分支保持；原生完成证明不清理未结束的子 Agent。恢复继续先保存完整提供方记录的哈希，再发布结果并清空已证明结束的 Hook 记录。Python 按既有结果报告和独立核验流程处理后续状态。

## Acceptance

- 当前 main 的旧实现使用相同新增测试，四种有效完成证明均失败，保留原始日志。
- 19 组原生命令证明场景各跑 5 轮竞态检查，全部通过。覆盖正常/失败命令、取消、多命令、部分证明、错提供方/回合、缺少身份、重复记录、非命令项、缺少退出码/进程、时间矛盾、存活进程和未结束子 Agent。
- 执行器整包竞态检查通过，包含原有丢失普通工具回调、取消、重放保护和完成记录边界检查。
- 真实状态查询通过当前会话和进程证明，恢复了一项包含三个已结束原生命令的历史回执；inputStopped/outcomeKnown 均为 true。既有 Python 轮询接收后将任务转为 waiting_user，业务验收继续等待用户决定。未发送输入、停止会话或手工修改数据库，未决的运行/取消任务由三项降为两项。
- 根进程丢失和 Claude 启动未跟踪的另两项任务仍保持未知；没有用本项完成证明替代它们的证据。
- 完整质量门已通过，Python 范围检查按实际 Go/文档变更跳过；Go、i18n、hover、类型检查及生产构建通过。

本修复没有修改模型路由、参数、能力、用量账本或限额，也没有把同一 Main 的内容复核当作独立评分。全套 RSI、内容质量和观察验收继续按原标准进行。
