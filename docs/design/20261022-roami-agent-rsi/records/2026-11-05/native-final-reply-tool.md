# Main 最终回复的原生工具提交

关联 #605、#443、#445。交付范围是提交协议，不宣称解决 #605 的字段理解或全部 RSI 问题。

## Product Design

Main 直接打印 `<reply>...</reply>` 时，原循环可能把包装文字作为最终答复送出。现在普通 Main 终答通过真实 `reply` 工具提交；未提交的文字和前言不流入用户消息。宿主要求模型重新提交，不剥标签、不猜字段或改写答案。

## User Stories

- 请求 JSON 时，可提交对象、数组、原始数值、布尔值或 null，并保留类型。
- 明确要求 XML 或其他原文时，`reply.text` 保留原文，包括 `<reply>` 标签。
- Worker 文字结果、必要提问、任务状态工具和依赖失败的证据收尾继续使用既有路径。

## Technical Design

`core/loop.py` 在普通 Main 回合中要求真实工具调用；缺少提交时记录 `MAIN_FINAL_TOOL_REQUIRED`、`executionStarted=false`、`failurePhase=validation`。既有重复参数无进展保护阻止反复打印同一草稿，不新增 Token、请求次数或费用上限。

`replies/answer_contract.py` 为 `reply.text` / `reply.json` 提供互斥校验及标准 JSON 序列化，拒绝非有限数。模型工具 schema 保留相同互斥约定；类型和字段值由 Main 负责，宿主不修补语义。生产 serve、保存模型对话及非夹具 Native 执行启用协议；原协议夹具保持明确的测试模式。

Native 与容器执行指纹更新，容器协议为 `container-uds-v35-final-reply-tool`；模型 Actor 镜像必须声明 `org.roami.rsi.final-reply-tool=1`。旧镜像在启动模型前拒绝，模型无关渲染器保持独立。宿主与镜像需配套发布。

HTTP、Native 续办及传输/语义分类夹具改为实际 `reply` 调用，原输入、期望、失败分类和独立判定器不变。错误 JSON 仍是语义失败，额度拒绝仍不评分；续办仍须写出原要求的最终文件并沿用工作区。

## Acceptance

- 131 项提交、CLI、容器准入和对话检查通过；补充的 58 项镜像/任务准入及 26 项续办、传输分类、提交检查通过，集合有重叠。
- 关闭新协议的同一缺陷控制失败：未提交包装文字进入最终消息，严格 JSON 解码拒绝。启用协议后对应检查通过。这是功能开关反例，不冒充完整旧源码对照。
- 不挂宿主源码的断网容器 14 项协议检查通过。镜像的 357 个运行文件与宿主逐字节一致，仅排除 Dockerfile 既有删除的三个宿主判定模块。
- 三道原数值任务在同一候选容器中串行通过；使用节点保存的 Main/Worker 路由、参数及能力，冻结 units-v3 合同。34 次真实调用均对应 Go known/HTTP 200，146,551 tokens、0.0538751 CNY。此为新合同诊断，不是旧套件收益或正式全套成绩。
- 完整门禁和提交钩子按仓库命令执行，最终状态见 PR 检查及私有退出回执。此前未通过的完整轮保留：镜像夹具缺声明；另一轮 5 项旧文本协议夹具失败。更新的是注入模型的传输事件，没有放宽业务断言。主动停止的第一轮及被中断的 MCP 检查不计通过。另一个完整轮 3531 通过、1 项旧测试夹具发生时序失败：停止调度器后旧回报回调仍在运行，手动领取下一回合被正常串行保护拒绝。补充等待原回调结束后，原十项业务断言保持，独立重现检查通过；没有修改生产队列保护。
