# 来源复核与最终提交协议集成

## Product Design

Main 的草稿可以误改用户字段、类型或任务目标。普通终答沿用真实 reply 提交；额外的来源复核只拒绝草稿并返回具体差异，不替用户生成答案或改写任务 ID。真实歧义仍需提问。

## User Stories

- 原文已给出值时，保留文字和类型，避免多问同一信息。
- 修改两个任务时保留各自身份；背景工作仅已接收时不声称完成。
- 来源、模型或租约变化时废弃旧判定，用户仍能主动停止。

## Technical Design

无草稿的用户原文阅读先于终答及提问复核；字面证据只接收有原文依据的候选。判定必须真实调用 source_review_verdict，错误协议不冒充接受；最终 reply 的 text/json 互斥规则复用已合入的 answer_contract。每次模型请求之后重新验证原文、上下文、模型设置和租约；回合结束清理缓存。模型请求仍沿保存路由与 Go 准入，Python 不设新预算上限。

容器须同时证明最终提交协议和来源复核能力；无模型渲染不要求这些能力。所有新模型复核属于同 Main 的辅助判断，不是独立评分。
