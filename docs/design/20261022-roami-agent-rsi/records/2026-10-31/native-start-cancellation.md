# Native启动取消与续办卡住

## 产品设计

任务启动与取消交错时，数据库可能已经创建运行中的Native回合，启动协程却在进入取消处理前被取消。后续用户续办缺少停止证据，操作一直停在`stopping`。

保留启动事务的异步结果。取消发生时先等待该事务结束，再依据真实启动结果走既有取消清理；不执行已取消的工作、不把中断标成成功，不重放未知操作。

## 用户故事

- 用户在任务刚启动时补充要求，旧回合能够结束，原任务继续到下一修订。
- 准备工作区与直接运行的Native任务遵守相同停止边界。
- 服务停机取消保留中断状态，启动数据库错误保持原错误。

## 技术设计

`dispatch/runner.py`将启动数据库调用保存在独立Task中，并在同一异常处理范围内等待其屏蔽结果。启动后取消也能取回任务、尝试和Native回合，复用既有停止与结果处理；启动未成功时不伪造执行结果。专业CLI原有协调与未知结果边界保持。

Case78使用与实际测试逐字节一致的公开时序配方，在真实SQLite事务提交前后设置等待点，并覆盖准备/运行状态。保留原CLI集成测试的5秒断言，不以扩大时限或跳过检查来通过。

## 验收证据与边界

统计Skill变更的完整门禁先出现一次CLI续办停止超时；单独运行原检查通过，首次超时的精确时序没有保留下来，不能断言它必然来自本竞态。随后在未修复代码上定点复现：事务提交前两项通过，提交后两项保持`stopping`失败。初版夹具遗漏执行验证作业的结果单独保留，不计为功能复现。

修复后新增六项涵盖四种提交/准备组合、启动错误和停机取消；连同原CLI往返、续办和会话存储共33项零跳过。源码与时序配方冻结。后续完整门禁、固定Actor回归和CI证据另存对应验收记录；本机制检查不代表音频、视频、量化内容、独立评分或人工参考已经通过。
