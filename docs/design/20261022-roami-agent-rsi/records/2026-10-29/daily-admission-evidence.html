RSI 设计修订与验收记录

每日准入的评分与 Case 证据 · 2026-10-29

Product Design

RSI 沿用模型页的每日限额。Case 准入记录必须与执行策略一致，不能把已经停用的 RSI Token／请求数配置写成“生效限制”。冻结 Case 的原限额继续作为历史协议保存，实际 Token 用量继续记账；技术超时仍单列保留。独立评分器也不再注入 RSI 自有输出上限，改用模型页主模型参数；两名评分模型及盲评证据要求保留。

User Stories

  • 我打开单个 Case 的预算证据时，能看出它由模型页 Go 网关准入，而不是误以为还有独立 Token 上限。
  • 我能对照冻结原协议和实际用量；旧记录不改写，旧冻结协议的测试模式仍能看到有效数值限制。

Technical Design

workflows/pipeline_runner.py 写 budget-*.json 时增加 spending_policy，与 budget-plan.json 的策略相同。shared_model_daily 下 effective_limits.tokens／requests、run_token_limit、reserved_for_later_cases 为 null；seconds 与原始 original_limits、已用 run_tokens_used 保留。frozen_protocol 下保持数值限制和原有预留逻辑。不改变原 Case、已发生用量和费用账本，不新增页面、轮询与配置。

evaluation/artifact_review.py 在构建评分路由与校验校准证书前固定 spending policy；daily 模式移除旧 profile 的 max_tokens 覆盖，仅继承模型页主模型的显式 max_tokens（缺省不注入），预算计量同样不使用旧 profile Token 限制。预览、排队、执行与候选验证显式传同一策略，不用 provider_factory 是否存在来猜政策。有效路由进入 route_hashes；不匹配的旧证书拒绝，不能拿冻结上限时的校准代替新路由。每日模式不要求 profile 填写 max_tokens／output_tokens；预览、诊断排队与执行器不再为这些字段计算本地预留。冻结协议模式继续保留旧限制。

calibrate_artifacts 的 shared_daily_limit 模式要求已绑定网关 provider_factory，忽略旧 token_limit 预留；启动记录明确策略和 null 预留，不增加设置页选项。未知用量仍失败，已开始样本仍不重放，必须提供人工参考与两名独立评分者；未确认样本不会被脚本自动改为已确认。离线冻结协议接口保留原参数供历史对照。

验收记录

真实视频复测的 budget-plan 已声明 shared_model_daily，但单 Case 仍写 run_token_limit=300000、effective_limits.tokens=512000、requests=64，构成审计歧义。此记录保留为修复前证据，不在运行中改写。75 项定向回归通过，新增 19 项：两种策略、模型输出上限缺省／显式配置、跨越旧评分预算、路由改变拒绝旧证书、12 样本每日准入、缺网关在启动前拒绝、未知用量停止和已开始校准不重放。合成模型的计量仅为测试数据，没有外部消费或能力得分；真实 12 样本新协议盲评仍待人工参考确认。新证书保存 spending_policy 和模型页输出参数快照，configure-artifact-review 按快照重建相同路由后校验；运行时仍以当前模型页参数重新核对，不能用配置安装绕过路由变化。三种证书安装路径及无效策略／快照在写入前拒绝的回归通过。注入 provider_factory 的校准默认仍标 protocol_fixture，真实网关执行须显式声明 live_models，不会把合成测试证书自动转成生产证书。早期 quick 为补齐证书安装兼容而主动中断；中间版本 quick 1968 项通过，full 为清掉无效必填字段主动中断，均保留日志、不冒称最终门禁通过。最终完整门禁、正反例及截图随 PR 留证；没有产品界面文本、人工评分、现用服务部署或自动日程变更。
