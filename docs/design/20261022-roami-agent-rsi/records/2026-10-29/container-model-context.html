RSI 容器继承模型上下文配置

Product Design

当节点配置 Main 或 Worker 的上下文窗口时，RSI 的宿主请求已沿用正确路由，但容器仍把窗口视为未知，并用默认压缩比例和保留量。这会使自动压缩无法按保存的窗口触发。每日策略改为传递各角色窗口和已有上下文策略，模型连接、真实模型名、密钥及生成参数继续仅由宿主处理；代理客户端仍不重复重试上游调用。

窗口未设置时保留未知，不估计模型容量、不添加 RSI Token 上限。修改上下文策略后，执行指纹变化，旧结果不充当相同配置的验证。新的共享协议在启动模型前拒绝旧镜像。

User Stories

  • 我在底层配置的上下文窗口和压缩策略，在隔离评测中同样生效，Main 与 Worker 可有不同窗口。
  • 窗口为空时，系统不替我填入另一个容量或宣称已经触发压缩。
  • 我能区分代码回归、离线容器验证和真实 Case 的质量；历史失败及未知费用保持原样。

Technical Design

模块职责
execution/container_context.py只映射 Main/Worker 窗口、reserve_tokens、keep_recent_tokens、compaction_ratio 五项上下文元数据；严格校验字段、数值范围及有限比例，拒绝额外连接字段和布尔数值。
execution/containers.py、container_agent.py宿主将已有上下文策略写入私有 request.json，共享容器入口必须读取；之后应用原图片能力，保留角色窗口。上游路由与重试留在宿主，容器端传输仍使用固定私有 socket。未使用每日策略的冻结协议保留旧行为。
execution/executors.pyNative 执行指纹纳入上下文策略，容器指纹升级 v31；变化后不复用旧配置结果。
improvement.Dockerfile共享镜像协议升到 5，预检拒绝协议 4 及更旧镜像，避免仅更新宿主却继续丢失窗口。非共享的历史模式仍可使用旧请求格式。

验收记录

六项初始回归在旧代码中五项失败、一项通过；修改后 144 项相关检查通过，包含真实 Runtime 回合用量触发压缩、两个角色的窗口/阈值、窗口未知、配置指纹、非法元数据、旧请求和镜像边界。最初扩大测试范围时误写两个不存在的测试文件名，未执行测试；保留该日志，改为实际文件后通过。

v42 冻结镜像在无网络、只读文件系统、无密钥挂载中验证：190 个核心/资源/入口文件哈希逐项匹配，脚本回复在真实 Runtime 记录用量后排队压缩，Main/Worker 窗口为测试数据 24000/48000，阈值 14400/28800；外部模型调用为零。该脚本数据验证配置传递和生命周期，不是任务能力成绩。

当前节点只读核对：保存的 Main/Worker 窗口均为空，新旧容器均保持未知，压缩阈值为空；宿主重试仍为 2，代理重试为 0，Worker 图片能力仍关闭。没有保存模型配置或发起 provider/模型目录请求。不能据本次修复宣称现有视频、音频、PPTX 或 CSV 已通过。
