运行架构

触发器是常驻程序，不让Agent自己记时间。单台无版本差异60次；有候选同机配对120次。多机先展开评测，复盘按Case核对，汇总Issue每Run一个；修复/验证可按待修点展开子节点，保留父Run。

评测 ──无论成功/失败/阻塞──→ Codex复盘 → Issue
                                       │
              发布确认 + 有证据可行动的问题 + 用量可对账
                                       ↓
              Codex修复 → 独立验收 → 草稿PR → 开发版观察

失败也要有诊断报告和Issue；缺分、缺日志、未知用量不阻止提出问题，但禁止冒充质量通过或自动晋级。UI必须选择Run后再画状态，禁止拼接不同Run各节点的“最新一条”。

    一次运行的数据与状态

    实体必须保存唯一性 / 约束
    experiment_definitions实验kind、revision、节点默认值与覆盖、边、Schema版本owner + kind + revision；CAS保存，旧版本保留
    workflow_runsRun ID、触发来源、定义快照、选中Case/hash、机器/模型/源码/评分版本、权限与预算、开始/结束owner + kind + trigger_id 幂等；运行中改配置只影响下次
    node_attemptsrun_id、node_id、attempt、父条目、状态、租约、起止、耗时、用量、阻塞原因、输入/输出引用run + node + item + attempt；按lease与revision完成，旧worker不可回写
    artifactsartifact_id、相对路径、SHA256、字节数、类型、可见性、生产者attempt、是否完整绑定owner和Run；隐藏答案永不返回前端，原始记录不公开到GitHub
    events / effects状态事件、GitHub/模型调用意图、稳定幂等key、请求hash、原始回执与未知标记同DB事务落状态和outbox；未知副作用先对账，不盲重放
    pending → queued → running → succeeded
                       ├→ failed / blocked
                       ├→ unknown（付费或远端结果不确定，先对账）
                       └→ cancelled
不满足诊断模式权限的后续节点 → skipped（必须有原因；不是成功）
失败重试新增attempt，保留旧记录；节点汇总不覆盖历史。
    落盘与恢复协议
    1. 先创建Run与7个pending节点、冻结配置，再允许第一次模型调用。
    2. 产物写临时文件，fsync后原子rename；随后同SQL事务登记hash、节点终态和后继节点。UI只有在产物存在且hash吻合时显示成功。
    3. 文件/数据库不是跨介质原子事务：崩溃留下的孤儿文件等待回收；数据库引用缺失/损坏文件时节点转blocked，不能假装成功。
    4. 租约过期：仅确定无副作用且账单已结算的工作可重试；付费调用、Issue或PR结果未知，先查询或人工对账。幂等key=run/node/item/attempt/operation。
    5. 取消只停止本Run明确拥有的进程与资源；保留已产生的partial产物，后续节点取消或跳过。
