产品设计与用户故事

配置下次流水线；选择一次运行，查看每个节点的职责、状态、历史尝试和文件。点击本地问题可回到最近运行；“复测同组 Case”沿用 Case 清单，重新冻结当前配置，不覆盖旧记录。

架构

程序每天触发完整60项 / 用户手动诊断10项
                   ↓
         Roami Agent + 容器外判定器
                   ↓ 失败、阻塞也记录
     Codex复盘 → Codex问题排序 → GitHub汇总Issue
                   ↓ 有正式证据与可信源码配置
     Codex修复 → 程序独立A/B验收 → 草稿PR → 两日观察

诊断模式只生成报告与Issue，不跳过正式验收而自动改线上代码。源码修复沿用独立 ResearchWorker；手工修复版本也可通过同组复测追踪问题。

节点执行手段

节点 / 执行者做什么保存什么
评测 / 程序与Roami Agent冻结Case/hash和预算，隔离运行；逐项独立判定Case结果、用量、工具/角色日志、产物、镜像指纹
复盘 / Codex逐项检查指标和行为，区分事实与根因假设review.md、调用计量与原始回执
Issue / Codex与程序Codex排序已确认问题；程序生成脱敏清单并自动发布issue-plan.json、issue.md、GitHub回执
修复 / Codex在可信源码范围内、独立worktree产生候选源码差异、候选hash、修改说明
验收 / 独立程序回归与正式冻结Case配对；缺分和未知用量不能晋级验证报告、A/B指标与证据hash
发布 / 程序质量门禁通过后创建草稿PR，不自动合入用户版本提交hash、PR与检查回执
观察 / 程序两个后续完整合格日，回归则撤回评测候选按日证据、关闭或回滚回执

工程实现

SettingsPage / AgentImprovement / PipelineRuns
                  ↓ 登录与owner鉴权
Go /api/agent/improvement/pipeline/* → Python私有HTTP
                  ↓
ImprovementControl + EvaluationWorker（共用单执行队列）
RunRecords（SQLite）+ PipelineReportWorker（Codex / GitHub）
ResearchWorker（正式复盘 / Codex修复 / 验证 / 发布 / 观察）
                  ↓
data_root/agents/improvement/
  ledger.sqlite3                   Run / Attempt / Case / Issue / Observation / Effect
  pipeline-artifacts/owner-hash/run-id/stage/  不可变文件 + SHA256
  pipeline-artifacts/owner-hash/run-id/case-hash/  私有运行原始记录

Run与7个节点先同事务落库，再开始模型调用。配置CAS保存，运行冻结快照。每个Run、节点、文件均按owner查验；文件限制大小、边界与hash，只作为文本预览，不执行HTML。GitHub稳定标记按owner+Run生成；POST结果未知时先查远端，禁止盲重提。付费用量未知也不自动重放。取消排队立即结束，取消运行只停该Run拥有的资源，保留已产生证据。

如何确认修好

本次状态程序依据
仍存在同Case再次观测到相同错误码或失败检查
本次未复现相同Case合同通过，评分非待定、用量已知；仍不自动关闭Issue
未验证 / 未覆盖失败、阻塞、待评分、未知用量 / 本次没有运行该Case
不可比较Case合同hash变化；不借改题获得“修复”

页面分别显示真实任务与零模型机制回归。失败耗时不当成速度提升，未知Token不记0；提高输出上限等配置变化写入快照，不能据此宣称Token节省。
