谁参与，怎么执行

负责者执行手段交付物
常驻控制器服务内置定时器，按日期幂等入队；重启仅补本周期，无需用户发消息。冻结套件、机器、预算与版本
被测 Roami Agent每台机器全跑 60 项；稳定版单跑，候选对照为 60 × 2。程序算分并扫描每条日志。产物、效果、时间、Token、工具与模型调用记录
Codex 复盘 Agent最多 4 项一批，逐项看指标与具体证据；异常按索引展开，事实与假设分开。所有测试机完成后合并文档。完整周期复盘、编号待修点、证据、建议与验收指标
Codex Issue Agent根据复盘列全量修复清单、排序与优先级；程序核验并发布一个汇总 GitHub Issue，确认成功才派修复。每天一个 Issue，不按 Case 或测试机拆单
Codex 修复 Agent按条目读允许范围的源码，生成最小补丁；程序在 detached worktree 校验并应用。每问题最多两次自动尝试。代码补丁、说明、关联 Issue 与条目 ID
独立验收程序复测原问题、冻结回归、同机全量 A/B 和私有门槛；通过 quick / full 后提交草稿 PR，回链 Issue。验收证据、PR 与截图；拒绝则保留未完成
观察与同步程序只绑定开发评测实例；后续两个完整周期通过才勾选条目，全部完成才关闭 Issue；退化回滚并重开。可追踪进度、观察记录、关闭或重开
人查看每日汇总文档、Issue 和 PR，处理明确阻塞并审阅合并。合并决定；普通用户通过正常版本升级获得改进

闭环条件

一个周期，一个 Issue

全机结果与复盘齐全才汇总；缺测不冒充完成。未发现确认问题仍保留复盘记录，不生成空补丁。

提 PR 不等于修好了

通过独立观察才勾选。一次只观察一个源码候选，其他修复排队，防止版本互相覆盖。

断线先对账

Issue / PR 请求结果未知时先查远端，不重复创建；未知付费调用不重放，保留日志等待核对。

模块、预算与边界
EvaluationWorker → behavior_observer（Codex 批量逐项复盘）
→ review_report（完整文档 / 全机汇总）
→ Codex Issue Agent → github_issues（发布确认）
→ source_revision（Codex 补丁 / 隔离应用）
→ candidate_checks → github_publication（草稿 PR）
→ release_observation → github_issues（勾选 / 关单 / 重开）

三个角色通过 codex exec --json --sandbox read-only 接收证据包，复用本机 Codex 登录和配置模型，不回退 Roami 主模型。禁用个人 hooks、MCP、插件与执行工具；修复只返回补丁，源码写入和 GitHub 写入由程序完成。每次保留原生 thread ID、JSONL、输出、耗时和用量。依据 Codex 官方非交互文档。

整套测试先做预算准入；复盘、Issue 和修复也计入账本。Codex 每次保留 model_tokens 准入额度并设置超时，完成后记录真实用量；超过额度或用量未知即停止后续付费调用。CLI 未提供可验证的供应商侧总 Token 硬截断，不能把准入预算说成费用硬封顶。使用供应商配额独立控制金额。所有阶段按执行日期共享日预算。

完整复盘在登录后的开发页面读取；公开 Issue 仅含安全的 Case / 路径 / 指标 / 优先级 / 验收清单及报告 hash，原始日志、隐藏集和用户数据留在开发机。源码允许范围、评分器与隐藏集不能由修复者修改。
