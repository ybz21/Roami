Roami · Plugin

会话守护 roam.keepalive

Agent 停下来不吭声，十有八九不是它死了，是它在等一句话：等你回「继续」、 等你发现刚才那次请求断在半路、等你想起来让它自己回头检查一遍。而你可能两个小时后 才点开那个标签。这份稿子设计一个替你看着的插件——它盯的不是进程还在不在， 是屏幕还动不动；它说的也不是一句死话，是看见什么说什么。 形态先定在 §01：builtin Go 插件 + 由 plugind 托管的常驻循环， 点开关就跑，不用再装任何东西。

01形态：它长成什么、谁来驱动它

先定形态。这个仓库里「形态」有三层，三层都得定死，而第二层——谁来驱动那个 「每隔一段时间」——才是真正的分水岭：它决定了用户在设置页点一下开关之后， 东西到底会不会真的跑起来。

1.1 分发形态：builtin Go

builtin Go（cron / im / review-mesh 那档）插件包（exec/node）
分发编译进 ttmux 二进制，默认启用ttmux plugin install，默认不启用
迭代改了要 go build 重装才生效热迭代，改完即用
平台 API完全一样（同一套 JSON-RPC 协议，宿主分不出谁是谁）

守护会话是「24 小时得在跑、装完就该有」的能力，和定时任务、IM 桥同一档 → builtin。plugins/keepalive/，独立 Go 模块， init() 里 sdk.RegisterBuiltin 自注册，宿主代码零手改。

「改了要重编译」为什么不咬人

会频繁调的东西只有一样：守护语。而它本来就该落插件私有 storage 而不是写死在 代码里——面板上要能改，常驻循环还要每轮重读（见 §10）。真正需要重编译的是判断逻辑， 那本来就该慎重。

1.2 运行形态：常驻循环挂在 plugind 上（决定）

宿主的 watcher 调度器（manifest watchers / onSchedule） 还没落地，所以只剩两条路，而这两条本仓库都各跑过一遍：

路 A · 常驻循环（im.listen 那条路）✅

_ttmux-keepalive 会话里跑 keepalive.serve，30 秒一轮， 由 plugind 那个 3 秒循环托管：插件在 storage 里举一面 wanted 的旗， 有守护对象就拉起，掉了重拉。

路 B · 外部 timer 叫 tick（roam.cron 那条路）

装一个 roami-keepalive-tick.timer，每分钟叫一次 keepalive.tick，机器上不多一个常驻进程。

选 A，两条实打实的理由：

1
B 这条路在真机上是断的 自检脚本里「没人叫 cron.tick —— 定时任务一条都不会触发」 这一条至今会亮红。让用户在设置页点了开关、还得再去装一个 systemd unit 才真的跑起来 ——这个产品就是坏的。点了开关就该跑是这个插件的底线。
2
B 更贵 plugin run 每次调用都新起一个子进程。30 个会话、每分钟 拉起一次进程再 capture 一轮，比一个常驻进程睡 30 秒贵得多。

而且这不是单点押注：两条路共用同一份逻辑

serve 就是 for { tick(); sleep(30s) }——屏幕指纹反正都要落 storage 才能跨轮比较，所以 tick 本来就是幂等的、可被任何人驱动的一轮。 两个都给的成本接近零：A 作默认，B 作退路， 面板顶上那条状态横幅对两种来源一视同仁，它只问「上一轮巡检是什么时候」。

// internal/plugin/daemon.go —— 抄 ensureIMListener 的同一套
func ensureKeepaliveLoop(env Env, store *Store) {
    if env.RT.HasSession("_ttmux-keepalive") { return }   // 已经在跑
    if !enabled("roam.keepalive") { return }
    // 插件自己举的手：storage 里 wanted=1 表示「我有守护对象」。
    // 宿主只读这一个键，不去解析插件的数据结构——那是插件的家事。
    if env.LoadStorage("roam.keepalive")["wanted"] != "1" { return }
    tmux new-session -d -s _ttmux-keepalive 'ttmux plugin run keepalive.serve'
}

由此白拿的三个性质

  • 开了就跑：打开第一个开关后 ≤10 秒循环起来，不用装任何东西。
  • 关了就停：最后一个开关关掉 → wanted 落下 → 循环下一轮自己退出，tmux 会话随之消失。不留空转进程。
  • 24h 自愈：plugin run 的 invoke 上限是 24 小时， 到点被回收后 plugind 3 秒内重拉——和 IM 长连接同一个机制，已经在线上跑着。

1.3 面板形态：宿主侧内置面板

manifest 的 configFields 自动渲染撑不起这个交互——要列所有会话、 每行一个开关、还要一张规则表。走宿主侧内置面板，和 CronPanel / HostMonitorPanel 一样按插件 id 挂进详情页的 tab （PluginsPanel.tsx 里已有现成的挂载点）。交互全文见 §07。

1.4 顺便否掉的两个形态

✗ 塞进 roam.cron 当一种新动作

cron 的模型是到点触发，守护是没动静才触发，判据根本不是一回事。 硬塞进去，cron 的 Job 要长出 idleMin / streak / hash 这些对它其它任务毫无意义的字段，一张表服务两套语义， 下一个人改哪边都会踩到另一边。

✗ 做成核心功能（会话列表上直接一个开关）

更顺手，但守护会替你花钱、会往会话里写东西——这正是需要权限声明 （sessions:write）和审计日志的那类能力，插件机制现成提供， 做成核心功能反而把这层丢了。折中：以后在会话列表上放个入口，能力仍归插件。

02先说清楚：要接住的是哪三种「停住」

三种都长得一样——会话还在、进程还在、屏幕不动了。但它们该说的话完全不同， 这是整个设计的起点。

1
它在等你说话 干完一段、问了个问题、或者停在「要我继续吗」。最常见的一种。 该说的话：继续。
2
它断在半路 API Error: Connection lost mid-response、 Request timed out、fetch failed ——上一句话说到一半没了， 它自己不会重来。该说的话不是「继续」，是 刚才那次请求断了，从断掉的地方接着说：一句「继续」很可能让它 从头再跑一遍，白烧一遍 token。
3
它以为自己干完了 改完就停，没跑构建、没跑测试、没回头看一眼。该说的话是 先自查一遍：跑构建和测试，把结果贴出来。

为什么不能用同一句话糊过去

第 2 种是真正贵的那种。断线之后发「继续」，Claude/Codex 往往理解成 「继续这个任务」而不是「接上刚才那句」，于是它重新开一遍思路；如果刚才已经改了半个仓库， 第二遍还会跟第一遍打架。守护语必须能按屏幕上看见的东西分叉，否则这个插件 在最该帮上忙的场景里反而添乱。

03怎么判断「它停住了」：别信 tmux 的活动时间

第一直觉是拿 tmux 的 session_activity——错的，而且错得很隐蔽。

session_activity 不行

它在我们自己 paste-buffer 那句守护语的时候同样会跳。 拿它判断「它动了没」，等于自己跟自己确认「它动了」——催完一句， 活动时间刷新，插件满意了，而会话那头一个字都没多出来。

屏幕指纹可以

每轮 capture-pane 末尾 40 行，压成一个哈希。 Agent 干活时这块一直在滚（连 · Thinking… 45s 那个秒数都在跳）， 停下来等人时它一动不动。值变了 = 真的有新东西；值没变 = 真的停住了。

那催完之后的那次变化怎么办？

我们打进去的那行字自己就在屏幕上，指纹必然变。所以设一道 60 秒宽限：催完 60 秒内的变化一律不算「它动起来了」，只有过了这道坎还在变的， 才记成一次真正的响应。60 秒 = 比巡检周期（30s）长一轮有余，又短到不会把 「答一句就完事」的正常响应误判成没反应。

04守护语不是一句话，是一张规则表

这是这份设计里唯一一个「结构」上的决定：把「说什么」从一个输入框， 升格成一张有序规则表。每条规则回答「屏幕上出现这个 → 就说这句」， 最后一条是兜底。表从上往下匹配，命中即用。

守护语规则（默认装好三条，可改可删可加）
屏幕上出现就发这句启用
断 Connection lost mid-response
|API Error|Request timed out 刚才那次请求断在半路了，从断掉的地方接着说，别重头再来一遍
查 （不按屏幕匹配，按「催到第 2 次」触发） 先别往下写了，回头自查一遍：跑一遍构建和测试，把结果贴出来
底 其它一切情况（兜底，删不掉，只能改它说什么） 你是不是已经完成了你的任务？没有完成，那么继续。

三个必须讲清楚的细节

  • 匹配只看屏幕末尾 40 行。往上翻整屏会把半小时前的一次报错重新认成「刚断线」， 然后对着一个正在好好干活的会话喊「你断了」。
  • 匹配串是子串，不是正则——第一版故意不给正则。规则表是给人填的， 填错一个正则的代价是「这条规则永远不命中」，而且没人看得出来。 多个关键词用 | 分隔，插件按「任一命中即算命中」处理。
  • 「自查」那条不按屏幕匹配。屏幕上没有任何字样能表示「它该检查了」。 它挂的是另一个条件：同一个会话第 N 次被催（默认 N=2）。 第一次说「继续」，还不动，第二次就换成「先自查一遍」——这恰好也是人的做法。

预设，不是让你从空白开始

输入框旁边给一排预设胶囊，点一下填进去： 确认是否完成 继续 断线重连 回头自查 清空自己写 ——绝大多数人这辈子只会用第一个，不该逼他们自己想措辞。

默认兜底语是第一条（「你是不是已经完成了你的任务？没有完成，那么继续。」）而不是「继续」： 一句「继续」不给 Agent 留台阶，真干完了的它会去找点事做——翻出个无关的改进、 再重构一遍刚写好的东西；你本来只想确认它还活着,结果换来一次计划外的改动。 先问后推那句则是干完了就回一句交代，没干完才接着干。 详见界面稿 §05.1。

05什么时候发，以及什么时候绝不发

发消息很容易，难的是不发。打断一个正在干活的 Agent 比不守护更糟： 它会把你的「继续」当成新指令插进上下文。四道闸，全过了才发。

闸判据默认为什么
① 安静够久屏幕指纹连续未变 ≥ N 分钟10 分钟 够把「正在想」和「真停了」分开
② 离上次催够久now − lastSent ≥ M 分钟30 分钟 就算①判错了，一小时里也最多打扰它两次
③ 看得见capture 成功且会话还在— 「看不见」不等于「安静」，读不到屏幕就这一轮什么都不做
④ 没到停手线连败次数 < maxQuiet3 次 见下一节
 
// 一轮巡检对一条守护做的全部判断（纯函数，可单测）
if !enabled || !alive || hash == "" { // ③ 看不见就什么都不改
    return
}
if hash != g.Hash {                 // 屏幕变了 = 它还活着
    if now-g.LastSent > graceSec { g.Responded = true }  // 过了宽限的变化才算响应
    g.Hash, g.QuietSince = hash, now
    return
}
if now-g.QuietSince < idleMin*60 { return }   // ①
if now-g.LastSent   < everyMin*60 { return }   // ②
if g.Responded { g.Streak = 0 }    // 上次催真换来了干活，旧账一笔勾销
if g.Streak >= maxQuiet { stop(); return }    // ④
send(pickPrompt(screen, g.Streak))  // ← 规则表在这里分叉

被排除在外的会话

_ttmux-* 命名空间的基础设施会话（plugind、IM 长连接、守护循环自己） 在平台 API 那一层就被滤掉了——否则这个插件会对着自己的循环发「继续」。

06停手：一个会一直烧钱的功能必须有刹车

被守护的会话可能早就不是 Agent 了——它崩回了 shell。那时候每一句「继续」 都变成一行 command not found，而插件会永远催下去。

1
连败计数每催一次 +1；只要观察到一次「宽限期之外的屏幕变化」就清零。 也就是说：它真干活了，账就一笔勾销。
2
到 3 次自动停手把这条守护置为停用，不再发任何东西。配置留着， 面板上这一行显示「连催 3 次没反应，已停手」，旁边一个「再试试」按钮。
3
发一条通知keepalive.stopped 进 Roami 通知流； 装了 IM 桥就会变成一张飞书卡片。停手必须吭声—— 静悄悄停掉的守护，和从来没开过是一回事。

07交互：设置页

这一页要在不滚动的情况下回答四个问题，顺序就是下面这个顺序—— 每往下一个，用户的关心程度就低一档：

1
它在跑吗 顶部横幅。这类插件最恶劣的失败是「配得好好的，但根本没在跑」——所以它排第一， 而不是塞进某个角落的状态徽章。
2
它在守谁 主列表：所有会话，每行一个开关。
3
它会说什么 横幅下面那句白话（全局默认）+ 「守护语规则」抽屉。
4
它刚才说了什么 「发送记录」抽屉。

信息架构：一个 tab，两个抽屉，不新开页

插件详情页里只加一个 tab（「守护」）。规则表和发送记录都走抽屉—— 它们是「偶尔要看一眼」的东西，做成并列 tab 会让主任务（开关谁）和它们抢同一层级的注意力。 逐会话覆盖同理：抽屉，不是展开行。

7.2 六个交互决定，以及理由

① 列的是「所有会话」，不是「守护表」

你要开守护的时候，脑子里想的是某个会话，不是某条配置。列全部会话、 每行一个开关，开关就是全部操作——不需要「新增守护」这个动作， 也就不存在「新增了一条守护但会话名填错」这种错误。这一条是和定时任务插件 最大的分野：那边的对象是你造出来的任务，这边的对象是本来就在的会话。

② 全局设置 = 一句白话 + 一块守护语

三个数字嵌在句子里，点一下就地变输入框——一张有四个 label 的表单说不出 它们之间的关系（间隔和安静阈值哪个套哪个？），而这句话说得出。 但守护语单独成块：它是一整句甚至几句话 （「你是不是已经完成了你的任务？没有完成，那么继续。」）， 硬塞进句子里只会挤成一坨。见界面稿 §05。

③ 「催一下」对未守护的会话也给

它是试用入口：还没决定要不要长期守护时，先手动催一次， 看看发出去的到底是什么、那个会话吃不吃这一套。试过一次再打开开关，心里是有底的。

④ 「全部守护」带一个默认打开的过滤

下拉里是「全部守护（只挑 Agent 会话）」而不是光秃秃的「全部守护」。 往一个裸 shell 里打「继续」换来的是一行 command not found—— 认不出是 Agent 的会话默认不碰，但允许你单独打开它。

⑤ 调度器状态永远在第一行

见 §01.2：这条横幅是这一页的诚实性担保。它不说「已启用」（那只说明配置存在）， 它说「12 秒前巡检过一轮」——一个只有真的在跑才写得出来的数字。

⑥ 「单独设置」是抽屉，不是展开行

逐会话覆盖是少数情况。放进抽屉，主列表就只剩「谁被守着」这一件事； 抽屉顶部写清楚「不填就跟着全局走：10 分钟 / 继续 / 30 分钟」， 把默认值直接印在占位符里，而不是让人回主页面去对。

7.3 顶部横幅的四种状态

横幅永远在，措辞跟着状态走。关键是每种非正常状态都要说出「怎么办」， 而不是只报一个现象。

四态
正常 · 守护中 3 个会话 · 12 秒前巡检过一轮 · 每 30 秒看一眼
还没守护任何会话 · 下面挑一个打开开关，守护循环会自动起来
守着 3 个，但巡检停了 6 分钟 · 守护循环没在跑，这 3 条一句都不会发
插件已停用 · 守护表留着，但不会巡检也不会发送

「怎么回事？」点开说什么

不是一句「请检查 plugind」。按顺序给三条可核对的事实： plugind 在不在（_ttmux-plugind 会话）、 守护循环在不在（_ttmux-keepalive 会话）、 上一轮巡检是什么时候。再给一条可直接粘的命令作退路 （ttmux plugin run keepalive.tick）。 用户得能自己判断是「循环崩了」还是「从来没起来过」。

7.4 空态：第一次点进来看到什么

第一次进来时守护表是空的，但会话列表不空——这是这一页的运气： 它天然就有内容可显示，不需要画一个抱着箱子的插画。空态要做的只有一件事： 把第一个动作指出来。

7.5 守护语规则抽屉

规则表（§04）的编辑界面。三件事决定了它的样子：兜底那条删不掉、 顺序即优先级、填完能当场验。

抽屉 · 守护语规则

「试一下」是这个抽屉里最要紧的按钮

选一个正在跑的会话，抽屉底部当场显示：命中了哪条规则、会发出哪句话。 没有它，用户填完一条匹配串只能等下一次真出事才知道对不对—— 而那正是最不想试错的时刻。

顺序可拖，但不玩花的

左边一个拖柄，上下拖改优先级。兜底那条钉死在最后、不可拖不可删， 只能改它说什么。不给正则（§04）：多个关键词用 | 分隔， 填错一个正则的代价是「这条永远不命中」，而且没人看得出来。

7.6 单独设置抽屉

抽屉 · 小慧优化 的单独设置
三项都可以留空——留空就跟着全局走：安静 10 分钟、 发「你是不是已经完成了你的任务？没有完成，那么继续。」、最快 30 分钟 一次。
守护语 跟着全局：你是不是已经完成了你的任务？没有完成，那么继续。 预设：确认是否完成 · 继续 · 断线重连 · 回头自查 · 清空自己写
安静多久算停住 跟着全局：10 分钟
最快多久催一次 跟着全局：30 分钟
这个会话 共催过 2 次 · 3 分钟前一次 · 连败 1 次 再连败 2 次就会自动停手

最后那一块是抽屉的隐藏价值：它把「这条守护此刻处在什么位置」摊开讲—— 还差几次就要被自动停掉。主列表上塞不下这句话，但它恰恰是用户在 「这东西是不是要放弃我了」这个时刻最想知道的。

7.7 反馈、确认与撤销

动作反馈要不要确认
打开/关闭一行开关 就地生效，那一行右侧的状态字改写（「未守护」→「刚开始守护」） 不要。开关是可逆的，加确认只是噪音
催一下 行内变成「刚刚催过」，同时发送记录里多一条；不用 toast—— 用户的眼睛在那一行上，不在屏幕角落 不要，但受最小间隔约束（§05 第二道闸）
全部守护 横幅数字跳到新值，并说清「开了 5 个，跳过 3 个非 Agent 会话」 要。一次动很多行，且每一行都会开始花钱
全部取消 同上，外加一句「配置留着，随时可以再打开」 要，但语气轻——这是刹车，不该比油门还难踩
自动停手后「再试试」 连败计数清零、安静起点重新计时，立刻变回守护中 不要。它本来就是从一个安全状态出发
改全局那句话 失焦即存，那句话本身就是回执；改完下一轮巡检生效（≤30 秒） 不要

一个必须避免的反模式：静悄悄

这个插件的所有动作都发生在你不看着的时候。所以三件事必须留下痕迹： 发了一句话（→ 发送记录）、自动停手了（→ 通知 + 那一行的红字）、 循环没在跑（→ 横幅转黄）。静悄悄停掉的守护，和从来没开过是一回事。

7.9 加载、失败与无障碍

  • 加载：keepalive.list 一条命令给齐全部数据（§10）， 所以这一页只有一个 loading 态，不存在「会话列表已到、守护状态还在转」的半截画面。
  • 失败：命令挂了就在横幅位置报错并保留上一次的数据， 不清空列表——把用户看着的东西抹掉换成一句红字，是最糟的错误处理。
  • 轮询：这一页开着时每 5 秒重取一次（「安静了多久」要走字）。 抽屉打开时暂停轮询，免得数据在手底下跳。
  • 可点的都是 <button>：「看一眼」真的跳路由才用 <a>。 图标按钮把名字写在 aria-label 里而不是只挂 Tooltip （粗指针下 Tooltip 站点级隐藏）。
  • hover 一律 :where(html[data-pointer="fine"]) 门控， npm run hover:check 守门。

09平台 API：补一条 session.listAll

现有的 session.list 只给本插件自己 spawn/track 过的会话—— 而守护插件要守的恰恰是别人建的那些。插件不能自己去敲 tmux （plugins/README 的铁律：一切经平台 API， 否则没有权限记录与审计），所以这条得补在宿主侧。

字段含义取自
session会话 id（改名不变，守护表的主键）#{session_name}
label展示名（只配拿来显示）@roam_name
agentclaude / codex / 空台账 agent_kind，兜底看 pane 在跑什么
idleSec粗粒度的安静时长（只用于显示）max(session_activity, window_activity)
attached / dir / created列表上的辅助信息tmux + 台账

权限面没有变大

仍是 sessions:read。capture / log / alive 本来就对任意会话名放行，少的只是「有哪些名字」这一条——而缺了它，插件只能去猜名字 或自己敲 tmux，反而绕开了审计。idleSec 只用于列表显示， 真正的判据始终是屏幕指纹（见 §03）。

为什么设置不走 manifest 的 configFields

两个原因。其一，ctx.Config 是激活时注入的快照——常驻循环一跑 24 小时， 中途改了守护语它看不见，得重启循环才生效，而用户不会知道要重启什么。 放 storage 则每轮重读，改完下一轮就生效。 其二，全局默认和逐会话开关是同一件事的两层，拆到「配置」页和面板两处填， 人就得在两个地方来回对。

11风险，和这一版明确不做的事

风险：它会替你花钱

每一句守护语都是一次真实的 Agent 调用。所以默认值全部偏保守 （10 分钟 / 30 分钟 / 3 次停手），而且开关默认全关： 插件默认启用只意味着「这一页能用了」，守护表是空的，一行都不会自己打开。 新建的会话也不会自动进来——没有「以后新建的自动守护」这个选项， 每一条守护都必须有人亲手打开过。

风险：打断正在干活的会话

§05 那四道闸就是为它设的。真出现误判，代价是上下文里多一句「继续」； 可接受，但不能频繁——所以第二道闸（最小间隔）是硬的， 连「催一下」按钮也认它。

不做：自动回答确认框

Agent 停在 Do you want to proceed? (y/n) 时替你按 y —— 这是另一个量级的 授权，规则表能表达，但不预置、不推荐。真要做，得先有一套单独的授权模型。

不做：正则匹配 / 跨会话编排

第一版只有子串与 |。「A 会话停了就去问 B」这类编排属于蜂群， 不属于守护。

12验收

  • 不打断：对一个正在滚输出的会话开守护，20 分钟内一条都不发。
  • 能叫醒：让一个 Agent 会话停在等待态，10 分钟后它收到「继续」并动起来。
  • 断线分叉：屏幕上造一条 API Error: Connection lost mid-response， 发出去的必须是断线那句，不是「继续」。
  • 会停手：守一个裸 shell，第 3 次之后自动停用并发通知，面板那行显示「已停手」。
  • 开了就跑：打开第一个开关 10 秒内，顶上横幅从灰转绿；关掉最后一个开关后 _ttmux-keepalive 会话消失。
  • 改了就生效：循环跑着的时候改守护语，下一轮巡检用的就是新的，不用重启任何东西。
  • 手机：360 宽下不横滚、按钮 ≥44px、按 web-ui-checklist 过一遍真机。
  • 纯函数有单测：§05 那段判断逻辑（Step）与规则匹配（pickPrompt） 各自覆盖到边界，不依赖 tmux。
