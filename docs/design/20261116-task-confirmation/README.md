# 后台任务确认与停止核对

## 产品设计

执行状态未知时，无论是否已有回报或文件，都提供「核对执行状态」。核对只恢复同一次执行的真实状态；进入待验收后，再在回报区域提供「确认完成 / 不通过」。不把执行器回报直接当作成功。

核对失败显示可操作的原因，保留回报、下载、追加要求草稿与重试入口。「正在停止」且停止尚未确认时，也可核对。提示不声称一定存在回报或文件。按钮、提示与错误同时支持中文和英文。

## 用户故事

- 我在手机看完回报后，能直接找到确认入口。
- 子进程晚于完成通知退出时，任务能重新检查停止状态，不永久卡在待确认。
- 执行仍未停止、任务版本变化或执行已被替换时，确认不能误标完成，也不能重放工作。
- 核对失败后，我仍能看文件、保留草稿并重试。
- 没有回报或文件时，我也能主动核对执行状态。
- 停止请求发出后，我能重新核对停止证据，界面不把取消请求当作已经停止。

## 技术设计

- `internal/agentexecution/session-claude.go` 保留已匹配 Stop 与 idle 的候选。后续工具、输入或失败事件使候选失效。
- `session-claude-completion.go` 在状态读取时重查进程、执行绑定、任务提示和工具状态；使用宿主已记录的 Stop/idle 证据生成结果。未停止时继续保留未知状态。
- 老宿主已记录 `SESSION_STOP_UNCONFIRMED`、但没有保留候选摘要的任务，只能经显式 `reconcile-session` 核对；同时要求同一任务的转录摘要、稳定摘要指纹和停止证据。其它未知状态不进入该恢复路径。
- Python 的 `dispatch/task_confirmation.py` 使用同一 launch key 查询与核对，保留原有 report、verify、confirm 流程。请求必须携带 revision 与 runId；复用正在运行的后台验收，不重复核验、不重新派发、不发送提示、不关闭会话。
- `AgentTasks.tsx` 将确认放在回报后，使用既有变更互斥、状态刷新、草稿和错误处理。没有新增轮询或页面状态容器。
- `POST /agent/tasks/:task/reconcile` 与成果验收分开，必须携带当前 revision、runId 并验证 owner。复用 `task_confirmation.py` 的证据核对和原有验收调度；观测恢复运行时只恢复运行状态，未知停止仍返回 `TASK_STOP_UNCONFIRMED`。停止中的 unknown/stopping 尝试也能进入此入口。不会调用人工确认、重新派发或关闭会话。
- `session-codex-completion.go` 识别完成与失败的 `McpToolCall`：需要有效 ID、服务/工具名称、线程/轮次和开始/结束时间。MCP 没有本地进程 ID 或退出码，不套用命令进程字段。命令仍要求进程和退出码；沿用转录摘要、未完成调用、子智能体、重复事件及真实进程停止检查。

## 2026-11-17 部署前兼容回归

现场旧转录文件的 mtime 晚于已认证的 idle 通知，但其中所有真实用户、助手和请求事件均早于 idle。文件观察时间不再代替执行活动时间：宿主记录最后一条可定时活动，允许其后的成本等元数据落盘；后续助手、API 请求、排队指令或无法定时的尾部活动仍阻止恢复。旧报告缓存升级格式以重建活动时间。

回归覆盖仅元数据改变 mtime、早期无时间戳的请求诊断、idle 后助手调用/API 请求/排队指令和无时间戳尾部活动。现场通过只读 status 核对活动时间，未接受用户结果或重放任务。
