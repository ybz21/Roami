建议方案

创建和关闭都快速确认，后台完成耗时步骤

保留一个很短的同步边界：服务端先可靠保存请求与操作标记，再告诉用户“已接收”。耗时的 Git、会话启动、停止和清理不占住页面。

响应目标：接收确认 P95 小于 500 ms。属于待验证目标，并非实测结论。

创建：先占位，后就绪

提交后立即出现“准备中”的会话条目；可以切去别处，也可以先写草稿。工作区和执行器没有就绪，不发送开工指令。

  1. 同步校验权限、参数、请求键并保存意图。
  2. 后台准备工作区、创建会话、绑定目录。
  3. 核对实际就绪，按原调度和额度规则开始执行。
提交失败保留表单；准备失败在原条目重试，复用资源身份。

关闭：先标记，后台收尾

确认保留、合并或丢弃后，条目标为“关闭中”，确认框退出，可以继续处理其他会话。

  1. 保存关闭意图，阻止新消息、续派和工作区新占用。
  2. 停止执行器及关联写入，确认停止再释放执行槽位。
  3. 目录清理独立进行，失败留在“收尾”中可恢复。
“会话已关闭”和“工作区已清理”分别记录；关闭不等于任务通过验收。

轮转：不等磁盘清理

确认上个执行器已停止，原队列中的下一个任务可进入执行；尚未清理的工作区仍被占用标记保护。

同一 Git 仓库的写操作沿用仓库锁。清理和创建可以排队，不让无关仓库或主界面一起等待。

轮转不凭点击立即释放资源，不绕过现有 Go gateway 的额度与准入规则。

失败：从出错的步骤继续

临时故障有限重试；权限、占用、内容变化和合并冲突需要用户处理。不能因为进入后台就无限重试删除。

刷新、手机断线或服务重启，都从同一份持久记录恢复。已经完成的合并不重复执行，启动结果未知时先核对，不直接重发开工指令。

用户选择“保留工作区”是新的明确决定，不能把它当作原删除操作成功。

三种方式的取舍

方式页面反馈断线或重启建议
整个请求同步等待创建／关闭按钮一直忙恢复结果依赖各接口实现保留兼容入口，逐步收敛
返回后启动临时后台线程看起来很快服务退出后可能丢失操作不作为最终实现
持久化意图 + 后台工作流已接收、准备中、清理中可区分可核对、重试、恢复推荐

现有代码已经做了什么

普通会话的 NewSessionModal 依次等待能力读取、工作区／会话创建、发送开工指令与跟踪登记；Go 的 worktree 创建和关闭接口也在请求内完成组合步骤。原生任务的创建与 task.close_session 已经有持久化作业，因此应复用它们，不能把所有任务再包一层新的调度器。

目前没有逐阶段耗时数据。异步解决的是页面等待和恢复方式，仍需记录真实阶段时延，定位 Git、远端同步或启动过程中的慢点。

技术方案

一个持久操作标记，一份执行事实

前端统一展示生命周期进度；普通会话资源操作由 Go 负责，原生任务继续使用已有 jobs 和关闭记录。统一读模型，不建立两个互相竞争的状态源。

短同步

接收意图

权限与版本校验、去重、预留身份、保存请求与事件；事务提交后返回 202。

持久工作流

后台执行

领取租约、资源核对、分步回执；按仓库串行写入，超时后重新观察。

共享事件

更新原位置

会话树、任务详情与收尾记录共用状态流；断线后补快照，不逐会话轮询。

操作记录的最小字段

operationId / requestKey / kind
owner + node + project
resourceId + incarnation + revision
intent + approvedWorkspaceSnapshot
state + stage + stageReceipts
leaseEpoch / attempt / retryAt

资源身份与展示名分开。每次副作用写回时检查租约代次；跨数据库通道使用可重放的投递记录，不假设跨库原子事务。

三条状态轴分别保存

任务
排队、执行、待核验、已核验、失败／停止。
会话
准备中、就绪、关闭中、已关闭。
工作区收尾
待处理、清理中、已清理、已保留、需要处理。

原型中的清理完成不会把“待核验”改成“已核验”，也不会根据 Agent 自述宣告成功。

创建与关闭的阶段顺序

操作后台阶段完成条件
创建准备工作区；创建／恢复会话；核对目录；派发开工；观察回执工作区和会话已就绪；开工按既有调度受理
关闭并保留冻结入口；停止并核对；关闭会话；保留资源；留痕会话确已停止，工作区明确保留
关闭并删除冻结入口；停止并核对；关闭会话；复查资源；可选提交与合并；删除；留痕停止、合并（若选择）与清理分别有实际结果
取消创建记录取消；等待安全中断点；停止已启动部分；回收本操作独占资源确认停止和补偿完成后，才标为已取消

重启和重复提交

同一请求键返回同一操作。阶段先落意图，后记录实际结果；服务重启后观察会话、Git 注册和启动回执，再决定继续或补偿。未知不等于不存在，也不等于可安全重放。

删除前再次核对

核对工作区身份、所属仓库、会话代次、其他占用与用户确认的内容快照。新写入、HEAD 变化或新占用会转为需要处理；不让延迟执行删除用户后来新增的内容。

避免请求风暴

复用当前共享会话概览与事件机制。列表只显示当前阶段；详情按需加载执行记录。无订阅时后台照常执行，结束状态不持续轮询。

分阶段落地

先补阶段耗时与持久操作记录，再迁移关闭清理，最后迁移普通会话创建与开工投递。CLI 若需要同步结果，用同一工作流的 wait 模式，不保留另一套实现。
