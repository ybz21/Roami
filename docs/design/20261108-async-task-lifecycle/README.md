# 任务创建与关闭的异步生命周期

[交互方案 HTML](index.html) · [实现与验收](implementation.md) · 2026-11-08

方案已实现并完成隔离回归与手机实测，尚未部署正式服务。以下保留批准时的方案，实际接口、模块和边界以实现记录为准。

## Product Design

建议创建和关闭都使用**短同步受理、持久化后台执行**。同步边界不是“全部做完”，而是服务端确认权限和请求约束、可靠保存意图及操作标记。事务提交后返回操作身份，页面可以离开。耗时的远端同步、Git 操作、会话启动、发送开工、停止与目录清理放在后台。

创建不能省略“就绪”门槛：接受请求后可以展示占位条目、记录草稿，但工作区、会话和目录绑定核对完成前不能发送开工指令。会话准备完成也不等于已获得执行容量，仍沿用现有调度及 Go gateway 的准入规则。

关闭提交后显示“关闭中”，阻止新输入与续派。确认执行器及关联写入停止后，才释放执行槽位，让原队列继续。工作区收尾使用独立结果，不要求下一任务等待目录删除；但尚未收尾的工作区仍有占用保护，不得立即复用。

本方案不把关闭会话当作任务完成或验收，不自动清理此前留下的工作区。桌面和手机使用相同状态与动作。原型模拟这些行为，不连接真实 API、不执行 Git/tmux，也不代表实际耗时或后台可靠性已经达标。

### 用户看到什么

| 阶段 | 显示 | 可做的事 | 不宣称的结果 |
| --- | --- | --- | --- |
| 提交尚未确认 | 表单提交中 | 保留输入；提交结果未知时按原请求键查询 | 已创建、已关闭 |
| 创建已受理 | 准备中 | 离开页面、写草稿、取消准备 | 已有可用终端、Agent 已开工 |
| 会话实际就绪 | 就绪／排队中／在跑 | 按实际调度进入会话、发送补充 | 就绪即在跑 |
| 关闭已受理 | 关闭中 | 切到其他会话，查看停止进度 | 已释放执行槽位 |
| 停止已确认 | 会话已关，清理中 | 原队列可继续；在收尾记录查看进度 | 工作区已删除、任务已验收 |
| 收尾失败 | 会话已关，清理失败／合并待处理 | 原步骤重试、查看冲突、明确改为保留 | 因会话不在就当清理成功 |
| 全部完成 | 已清理／已保留 | 查看任务记录与实际产物 | 自动将任务改成成功 |

活跃列表保留“关闭中”；停止确认后，该会话退出活跃列表，未完成的清理显示在“收尾”与原任务详情中，不作为普通孤儿目录丢失跟踪。失败摘要只说原因和下一步，完整阶段、身份和回执按需展开。手机详情为一个返回栏和一个内容滚动区，不用大弹窗承载执行记录。

“轮转”只驱动原调度队列，不自动新建目标、发起额外任务或改写验收结果。点击关闭不等于停止完成。若选择保留，未在跑的会话关闭也不影响其他执行槽位。

### 接收确认的同步范围

- 必须：鉴权与所属节点校验、参数及轻量版本检查、请求键去重、稳定身份预留、意图与事件持久化。
- 后台：远端 fetch、重型仓库扫描、worktree 准备、会话创建／恢复、就绪核对、开工投递、停止观察、合并、删除及留痕。
- 同步可利用已有缓存给出快速预检，不能把旧缓存当作执行时的授权。后台在产生副作用前再次检查身份、占用、内容与策略。
- 受理响应 P95 小于 500 ms 是待验证的体验目标，不是本次性能测量结果；长步骤仍可能慢，必须记录阶段时延并优化实际瓶颈。

## User Stories

1. 我点击创建，看到准备中的同一个会话，可以立即回到项目处理其他事；准备完成后它变为可进入，未获得执行容量时如实排队。
2. 我在准备阶段写了补充，切换会话、刷新或失败重试后草稿仍在，且尚未发送给 Agent。
3. 我选择关闭并删除，确认框很快退出；后台确认停止后，下一个排队任务开始，旧工作区继续清理。
4. 我看到“会话已关，清理失败”，可以从原记录重试，不必复活会话、再关闭一次，也不会重复做已经完成的合并。
5. 我遇到合并冲突时，文件与分支保持可恢复；可以处理冲突再继续，或明确改变决定，保留工作区。
6. 我连续点击、手机断线、刷新或服务重启，仍找到同一操作，不多开会话、不重复发送原始任务。
7. 我取消尚未完成的创建，看到“取消中”；停止和补偿确认后才显示已取消。已有工作区、收养分支及用户文件不会被顺手回收。
8. 我关闭一个已通过验收的任务会话，验证结果保持不变；关闭执行中的会话也不会把它标成通过验收。

## Technical Design

### 当前代码观察

依据当前 `9e33478a` 快照，未做逐阶段性能采样：

- `frontend/src/components/sessions/NewSessionModal.tsx` 的 `ok` 顺序等待能力读取、创建／派生 API、发送 Agent 开工命令和可选跟踪登记。浏览器仍参与后半段编排；若只把 Go 的 worktree 创建改异步，浏览器离开后仍可能漏发开工。
- `backend/api/worktree.go` 的 `WorktreeSessionCreate` 先创建会话，再创建 worktree、注入并核对目录，完成后返回。`SessionCloseWithWorktree` 在请求内做预检、停止、合并、删除和留痕。
- 关闭已经使用独立于请求取消的 context；它解决断连中断的一部分问题，但不能代替持久化工作流和服务重启恢复。
- `agent-runtime/src/roami_agent/dispatch/tasks.py` 已在任务创建事务中写入 `task.run` 作业与 `task.accepted` 事件。
- `agent-runtime/src/roami_agent/dispatch/task_sessions.py` 已在事务中保存关闭记录、版本／执行身份、`task.close_session` 作业与事件；`scheduler.py` 已有控制类作业调度。

因此不重写原生任务队列，也不把普通终端会话强行写成原生任务。UI 统一的是生命周期读模型，业务任务、会话、目录分别有状态所有者。

### 所有者与模块

| 所属 | 现有／拟新增模块 | 职责 |
| --- | --- | --- |
| Go，普通会话与物理工作区 | 拟新增 `internal/sessionlifecycle/operation-store.go` | 操作意图、阶段回执、请求去重、资源代次、租约、事件投递记录 |
| Go，普通会话与物理工作区 | 拟新增 `internal/sessionlifecycle/worker.go` | 领取租约、阶段执行、停止观察、重启恢复与安全补偿 |
| Go，已有资源实现 | `internal/session`、`internal/agentexecution`、`backend/worktree` | 沿用 tmux 精确定位、可靠发送、执行绑定、工作区锁与删除策略，不另写 shell 分支 |
| Go，API／兼容适配 | `backend/api/worktree.go` 及拟新增生命周期入口 | HTTP 202 受理与查询；旧同步入口逐步作为同一工作流的 wait 模式 |
| Python，原生任务业务 | 现有 `tasks.py`、`task_sessions.py`、`scheduler.py` | 保留 task.run／task.close_session 的状态权威；扩展投影和关联引用，不重复调度相同动作 |
| 前端 | 拟新增 `sessions/session-lifecycle.ts`、现有共享会话概览与事件订阅 | 映射三条状态轴、按操作身份恢复，统一所有关闭入口；可见性、共享请求和错误退避沿用原机制 |

Go 可为普通会话使用现有 SQLite 主库中的生命周期操作表与同事务投递记录；本机 worker 扫描持久队列，现有实例租约避免重复服务。无需先引入 Redis 或外部消息系统。物理资源处理不能依赖模型完成一轮响应才运行。

原生会话关闭仍由已有关闭作业执行。若用户额外选择清理物理工作区，Go 的清理操作依赖其实际停止回执，而不是另建 Go worker 再关闭同一原生任务。投影可保存原生操作引用，不能产生第二个“关闭事实”。跨主库／原生运行库的投递使用幂等 outbox/收件回执，不假设跨库事务。

### 操作记录与受理

建议字段：`operationId`、按 owner/node/入口作用域唯一的 `requestKey`、`kind`、规范化请求摘要、`owner`、`nodeId`、`projectId`、可空 `taskId`、稳定 `resourceId`、会话／工作区 incarnation、预期 revision、用户意图、工作区确认快照、`state`、`stage`、阶段结果回执、`leaseEpoch`、尝试次数、下次重试时间、错误码与时间戳。

1. 服务端在短事务中去重、预留身份、保存意图和投递事件；**只有提交成功才能返回已受理**。同键同内容返回原操作，同键不同内容返回 409。
2. 创建时预留的是稳定会话资源身份，不是展示名。内部资源创建增加识别预留身份的入口，并核对所属操作；交互式 CLI 仍沿用现有身份规则，不开放客户端任意冒认 tmux 名称。
3. 接收超时不代表拒绝：客户端保留原请求键查询结果；不能换键自动再创建。重连先读快照和版本，再继续事件流。
4. 原生任务受理沿用已有幂等键、task/run/revision 校验。普通终端不凭空生成业务任务成功／验收状态。
5. 用户选定的目录、执行器、原始需求、父会话关系和必要偏好都作为意图保存，浏览器不再负责创建成功后才补发开工。模型和能力准入继续由节点保存的配置与 Go gateway 决定，不增加框架层 token／次数／金额上限。

拟定接口（尚未实现）：

```http
POST /session-lifecycle/operations
{ kind, requestKey, expectedRevision?, target, intent }

202 Accepted
{ operationId, resourceId, revision, state, acceptedAt }

GET  /session-lifecycle/operations/:id
POST /session-lifecycle/operations/:id/retry
POST /session-lifecycle/operations/:id/cancel
```

授权身份由服务端推导。`retry` 和 `cancel` 同样带预期版本及请求键，不能凭操作 ID 绕过所属节点、用户或资源绑定。纯后台资源操作不可使用普通任务对话成功状态作为完成凭据。

### 创建流程

持久化意图；后台预检；准备 Git 工作区；创建／恢复会话并绑定真实目录；确认工作区、pane 和执行器；服务端发送开工；观察回执／转入现有执行队列；更新就绪和执行状态。

- 每个阶段先保存待执行意图，再执行副作用，最后保存实际回执。崩溃可能发生在副作用已完成、回执未写入之间，恢复时必须先观察对应资源。
- 原始开工指令在工作区就绪后由服务端可靠投递，不能留给已离开的网页。启动结果未知且执行器没有可核对回执时，进入需要处理，不能承诺 exactly-once，也不能盲目再次发送。
- 准备失败保留原需求、绑定和已确认步骤，在同一资源身份上重试。若已产生损坏资源，先核对并补偿，再通过新 attempt 继续；禁止静默创建第二个工作区。
- 取消先写取消意图。非安全中断点的 Git 操作需要完成当前原子步骤或安全中止，再观察与补偿。只删除本操作创建且仍独占、未出现新内容的资源；已有分支和工作区不回收。

### 关闭、轮转与清理

推荐顺序：保存明确意图；冻结输入／派生／新占用；停止执行及相关写入并确认；关闭目标会话并确认；释放执行槽位；复查工作区；按用户选择保留，或必要时提交／合并后删除；核对 Git 注册与目录、分支实际结果；记录收尾。

- 相较当前 merge 路径，不能简单把“运行中的 Agent 仍可写文件”连同原同步步骤原样放进后台。先确认停止，才能对文件做提交、合并和删除。
- 发送、恢复、续派与工作区复用的所有公共入口都读取关闭／收尾围栏。使用稳定身份、实例代次、版本和租约 fencing，不按可重复的展示名操作。
- 关闭会话后才进行的合并若冲突，保留可恢复工作区；提供文件／冲突详情，必要时显式创建恢复会话。不能默认复活原 Agent 或继续删除。
- 创建和清理同一工作区互斥；仓库写操作复用现有 common-dir 锁，锁段尽量短。清理旧工作区不长期占住模型执行槽位；新的模型调用仍遵守现有准入。
- 关闭先保存用户确认的 workspace 身份、HEAD、占用及内容快照，实际删除前重新核对。外部新增写入、HEAD 移动、资源重新绑定或新会话占用时，需要重新确认，不删除后来新增的内容。
- “删除本地分支”独立于目录删除，已有／收养分支默认保留。明确保留工作区时不附带删除其检出分支。
- 已合并但删除失败，记录合并结果，从清理步骤恢复；删除目录成功而分支删除失败也单独保存，不能整个操作从头做。恢复对结果进行 Git 核对，不只相信旧布尔标记。
- 修改为“保留”是新的、有版本的明确意图，撤回尚未执行的删除步骤。原合并／删除未完成的事实仍保留，不伪造原意图成功。

### 恢复、事件与错误

worker 用持久租约领取，过期操作进入核对与恢复；所有阶段回写比较租约代次，防止旧 worker 写回新结果。跨进程的文件副作用还需要资源锁与具体 Git/tmux 观察，数据库 CAS 本身不能阻止旧进程继续改文件。

临时网络／文件系统故障可有限重试并退避，权限、占用、内容变化、身份冲突与合并冲突暂停在需要处理。单个作业失败不拖死控制队列；停止／恢复优先级与普通执行分离，避免创建拥堵阻塞关闭。

状态事件与操作更新同事务保存，通过已有共享事件流传播。断线用快照加 cursor 补齐；操作后台执行不取决于当前是否有浏览器连接。列表只有摘要，阶段日志按需读；复用共享概览，隐藏时停止 UI 自己的兜底轮询，结束态不常驻轮询。

需要测量：请求受理时延、排队时间、每阶段开始／结束与重试、等待仓库锁时间、未知结果恢复次数、重复提交命中率、工作区半清理数量。此提案没有“异步等于更省 CPU／更快 Git”的性能结论。

### 建议落地顺序

1. 先给现有同步链路补阶段耗时、身份和实际结果，确认耗时来源；建立持久操作记录与统一读模型。
2. 迁移普通会话关闭／物理清理，补停止证明、租约、恢复和历史关联；原生关闭接已有任务作业投影。
3. 迁移普通会话创建，把浏览器当前承担的开工投递与登记收进服务端；保留同一资源身份和草稿。
4. 所有入口收敛；CLI 可选择 wait 等待同一操作，不另保留一套副作用实现。再根据真实阶段时延优化锁与 Git 工作量。

## 验收标准

- 已受理意味着意图可恢复；持久化失败时表单不丢，不能显示已创建／已关闭。
- 同一请求重复提交与受理响应丢失只得到一个操作、一个会话／工作区。
- 每个阶段前后注入服务退出，重启后先核对实际资源再恢复；未知观察不能当作停止或不存在。
- 准备未完成不发送开工；取消和启动竞态无泄漏、无重复派发，无误删已有工作区。
- 停止证明未拿到时不释放执行槽位；停止确认后，独立任务可先于目录清理完成继续执行。
- 合并成功后删除失败的重试不重复合并；目录删掉而分支保留的部分完成有独立回执。
- 外部新写入、工作区重新绑定、同名新会话和新占用不能被旧清理操作影响。
- UI 中任务、会话、工作区三条状态轴不混淆；重命名不影响操作归属，关闭不改变验收结论。
- 桌面 1280／1920／2560／3440 CSS px，控制栏／详情开关，手机窄屏与粗指针交互均可用；文档不滚动，内部内容滚动，草稿切换／刷新保留。
