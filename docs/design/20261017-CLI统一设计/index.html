01

总体决策

一个核心 Go module、一个 Roami 可执行文件、一棵命令树、一套业务服务与存储契约。 cli/ 的会话实现并入应用核心；CLI 和 Web 适配同一业务层，避免长期保留“总入口转发另一套 CLI”的架构。

首期按阶段迁移，过程中允许适配旧引擎；完成态不内嵌第二份 ttmux 二进制，不用子进程调用自己来执行普通 session 命令。tmux、Chrome、Node 和外部 Agent 仍是必要的外部进程。

本版补齐安装模式 database 目录与升级协议，整合产品规则、技术方案与代码架构，并替代先前“保留两个 Go module”的长期方案。当前已完成统一入口、根 module、共享会话服务、数据库布局与离线备份恢复、远端开工检查及活跃调用迁移；具体完成项和验证边界见末尾实施记录。

03

统一代码架构

应用分为入口适配、应用服务、领域能力和基础设施四层。CLI 直接调用本地会话与浏览器服务；项目客户端通过现有鉴权 API 调用服务端项目应用服务，继续由服务端 Store 维护缓存一致性。

同一代码库不等于所有命令必须依赖常驻服务。session 和 chrome 可以离线于 Roami Web 服务运行；project 首期需要服务在线，避免 CLI 与服务端对同一内存台账同时写入。

兼容适配ttmux / chrome / roam

会话服务session / swarm
项目服务project / worktree
浏览器服务CDP / automation
存储服务catalog / migration
tmux 运行时精确 target、提示提交

SQLite主库、消息流、归档

依赖自上向下。领域包不导入 CLI、Gin handler 或页面组件。

操作 完成态调用链 进程边界

roami session send CLI / SessionService / 原 SendPromptSubmit 继续 paste-buffer 后独立 Enter

roami project create CLI / API client / 鉴权 API / ProjectService / Store HTTP 保留服务端单写者
roami chrome tabs CLI / BrowserService / Node driver / CDP Node 与 Chrome 仍是外部运行时
roami db backup CLI / StorageMaintenance / catalog 与各库快照 覆盖全部参与维护的写者
新任务开工 HTTP 或 CLI / TaskWorkspaceService / WorktreeService / SessionService fetch 与 cwd 绑定成功后才启动 Agent

原 backend/ttmux.Client 在迁移阶段作为适配层保留，逐项替换为结构化 SessionService；完成后只在明确兼容/外部执行路径保留。原有交互、信号与 JSON 测试作为回归基线，不重新实现 tmux 的危险细节。

argv 始终分项传递，不拼 shell 字符串。标准输出与错误分离，已有 session/chrome 数据输出和退出码保持兼容；新 project 命令支持 --json，成功输出 data、失败输出 error.code/message，人类提示进入 stderr。

attach 不额外嵌套 PTY；验证前台进程组、Ctrl-C、Ctrl-Z 和终端恢复。外部进程的终止/退出状态正确映射，不把信号退出误报为成功。tmux target 保持 =name 精确匹配，多行 prompt 继续走原提交路径。

Chrome 保持同一 CDP 实例、profile、端口记录和浏览器设置。帮助不安装依赖、不启动 Chrome；实际自动化缺 Node/Chrome/playwright-core 时给出对应 setup 指引。

07

开工前的远端同步

新任务 worktree 的起点必须来自准备阶段成功 fetch 的远端快照。失败即停止，Agent 不开工。 显式指定 base 也不能绕过同步。

  1. 解析仓库、远端与基准：显式 remote/base 优先，其次基准 upstream，再使用 origin 上可确定的基准；歧义与无远端返回明确错误。
  2. 每次新建执行带超时的定向 fetch，将目标分支写入本次独占的 refs/roami/prepares/<随机ID>。从私有 ref 解析固定 commit OID，不读可能被其他请求覆盖的 FETCH_HEAD。
  3. 在统一仓库锁下协调 ref 更新和创建。同步相应 tracking ref，不移动本地主干，不碰其他 worktree 的未提交修改。
  4. 从固定 OID 建新任务分支与 worktree，记录 base、startoid、来源远端。清理本次私有 ref；失败按阶段回收临时目录、分支和会话，不删除用户既有分支。
  5. 绑定会话 cwd 成功后，再发送 Agent 启动命令和任务提示。

Service.Create 作为共同检查点，覆盖 Web、手机、项目开工、新 worktree 子会话和蜂群/竞赛相关创建入口。只 fork 会话但不建 worktree 的操作不触发同步。

继续已有分支与新建任务明确区分：保留已有提交，不自动 reset 或 rebase。远端随后出现新提交不会自动改写已经开始的任务。“最新”是本次准备成功取得的快照。

竞赛需要同一起点时，由竞赛应用服务先准备一次远端快照，再内部传给全部选手；普通客户端不能自行提供 PreparedBase。这样既保证新鲜起点，也保证比较公平。

准备流程演示

只展示设计分支，不会执行 Git 或启动会话。

  1. 解析远端基准与 upstream
  2. 成功 fetch 到本次私有 ref，固定 OID

08

数据库统一管理

安装版统一使用 ~/.roami/database/ 作为数据库根目录。主库与 Roami 自有分库全部经过同一 StorageCatalog 定位；不得在工作目录、源码目录、~/.roami 顶层或某个 swarm 工作目录里临时再建库。

应用代码统一成一个 module；物理存储按负载保留主库、蜂群消息分库和归档库。数据库集中落盘便于权限、发现、迁移和备份，不要求所有表放进同一 SQLite 文件。

安装模式的目标目录

  storage-layout.json              存储布局版本、实例 ID、生效数据库根与迁移状态
  database/                        DatabaseRoot，仅放数据库与 SQLite 附属文件
    catalog.json                   布局清单：相对路径、库 ID、类型、owner；不取代 schema 表
    meta.db                        主库：项目、会话、蜂群元数据等
    meta.db-wal / meta.db-shm       SQLite 自己管理，不能独立移动或清理

  credentials/                     CLI Cookie，按服务 origin 隔离

  browser/
    profile/                       浏览器拥有的 profile，Roami 不直接管理其 SQLite
  swarms/<swarm-id>/                原有群目录中的非数据库产物，迁移后不再含活跃 swarm.db
  logs/                            按现有日志保留策略轮转
  cache/                           可删除重建的驱动、依赖及缓存
  locks/                           持久锁目录；在线期间禁止删除或替换锁 inode
  run/                             可重建运行时文件：PID、socket 等，不含存储维护锁

以上为默认逻辑布局：数据库布局是本轮必须统一的交付。browser profile、日志等既有自定义路径先保留，通过配置登记；不能为整理目录擅自搬迁用户浏览器 profile 或删除原有产物。数据库迁移只移动已知 Roami 自有库，不扫描并迁移 profile 内的 Chrome 数据库。

可用且归当前用户所有的 XDG_RUNTIME_DIR 优先承载运行时文件，例如 $XDG_RUNTIME_DIR/roami/<instance-id>/；不可用时使用 <DataRoot>/run/。Unix socket 名称使用短实例 hash，并校验平台路径长度；不得让长自定义目录产生无法启动的 socket。

主库和分库各存什么

库与安装路径 内容与写入边界 生命周期
database/meta.db sessions、projects、aliases、races、session_homes、swarms、members/cards、plugin 会话等业务元数据 随实例存在，不随单个会话结束删除
database/swarms/<稳定ID>/swarm.db 蜂群 posts 高频消息；旧成员/看板只迁移进主库，不继续双写 随 swarm 归档策略管理，改展示名不改路径
database/archive/ai-footprints.db Git 提交归档；原建表/补列收敛为版本迁移 历史归档按保留策略清理，不跟 worktree 删除
database/plugins/<插件ID>/<库名>.db 插件确需独立持久化时由平台 API 申请；简单状态优先平台已有能力 停用插件不删库，卸载是否清理按显式策略执行

插件的库名和 ID 只能由受校验的登记映射生成路径，禁止绝对路径与 .. 越界。按实例 ID、库 ID 管理身份，文件路径和展示名都不作业务主键。分库清单在创建和删除时先取得维护共享锁，再取得独立 catalog 独占锁；锁内重读清单、更新并原子发布，防止并发读改写丢登记。创建分库使用 pending/ready 状态及可重试 journal，崩溃后核对库文件再完成登记，删除同样分阶段。备份前再与真实目录核对；缺失或未登记的数据库报告异常，不能假装备份完整。

路径解析的单一契约

所有命令、Web 服务、插件宿主、定时任务只使用一次解析形成的 Paths；子进程传递已解析的实例路径，禁止各自重新用 HOME 推导。help / version 不创建目录；db status 可以报告尚未初始化与迁移需要，不因只读检查自动建立空库。

逻辑路径 优先级从高到低 缺省
HomeRoot --home、ROAMI_HOME、ROAM_HOME、TTMUX_HOME、当前运行用户的 home ~/.roami
ConfigPath --config、ROAMI_CONFIG、ROAM_CONFIG、<HomeRoot>/config.yaml 配置定位不依赖配置本身
DataRoot --data-dir、ROAMI_DATA、ROAM_DATA、TTMUX_DATA、配置 storage.data_dir、HomeRoot ~/.roami
DatabaseRoot --database-dir、ROAMI_DATABASE_DIR、配置 storage.database_dir、<DataRoot>/database ~/.roami/database
BackupRoot ROAMI_BACKUP_DIR、配置 storage.backup_dir、<DataRoot>/backups ~/.roami/backups

新全局参数写在分组前，例如 roami --database-dir /mnt/roami/database db status；现有 server flags 保持兼容。配置中相对目录按配置文件所在目录解析，CLI 相对目录按调用者 cwd 解析，环境变量路径要求绝对路径。仅支持明确的 ~ 展开，不做 shell 命令或任意变量插值。规范化绝对路径并记录来源，避免工作目录变化改变实际数据库。

显式配置数据库根时，先核对 storage-layout/catalog 中的实例 ID；同一路径不能被不同实例悄悄复用。已初始化实例的实际路径与配置不一致时要求显式迁移，不能切换后自动建空库。只有“新实例、无旧库、无既有布局清单”的情况才允许初始化。用户明确新建隔离实例时必须选独立 Home/Data，不借空数据库目录绕过该检查。

# 默认安装不需要配置；以下为数据盘示例。
storage:
  data_dir: /mnt/roami
  database_dir: /mnt/roami/database
  backup_dir: /mnt/roami-backups

HomeRoot 与 DataRoot 继续允许分离：配置可在 ~/.roami/config.yaml，持久数据放到数据盘。与旧行为的关键变化是所有自有数据库统一位于 DatabaseRoot，不再由 HOME 和 DATA 分别决定。旧分离设置必须走下面的登记迁移流程。

持久锁目录不得被 cache/run 清理、服务退出或卸载残留清理删除；只允许所有进程退出后的实例整体清理。维护锁的权威位置固定为 <DataRoot>/locks/storage.lock，不随 XDG_RUNTIME_DIR 或 DatabaseRoot 的选择变化；socket/PID 可以放 XDG 运行时目录，但存储锁不能由每个进程自由选择。Catalog 同时校验 owner DataRoot；两个不同 DataRoot 指向同一 DatabaseRoot 时拒绝并行接管。当前 DatabaseRoot 切换通过离线布局迁移，保留实例 ID；DataRoot 搬迁使用停机后的完整备份与空实例恢复，不隐式重写旧实例配置。旧实例保持停机，确认新实例后再按保留策略处理旧副本。

安装用户与源码开发

普通安装按服务实际运行用户解析 home，目录 0700、数据库/清单/凭据/私钥等 0600，遵守 umask 077。systemd 系统级安装即使由 sudo 发起，也必须显式选择正确的 User、HOME 和数据路径；不能用安装进程的 /root 替代运行用户目录，不能递归 chown 用户自行指定的整块数据盘。

服务配置固定已解析的 Home/Data/DatabaseRoot；CLI 与服务 status 核对同一实例 ID。安装过程只准备路径和权限，首次业务初始化负责建 schema。已有数据库不可写、磁盘满、只读挂载或目录权限错误时报告具体路径，绝不回退仓库或 /tmp 新建库。数据库根使用支持 SQLite 锁语义的本地文件系统；网络文件系统不作为默认支持目标。

开发启动默认沿用既有配置，便于升级兼容，但首次启动日志必须明确实例与实际库路径。隔离开发使用受管隔离启动器：先清除 ROAMI_/ROAM_/TTMUX_ 的 HOME/DATA/CONFIG/DATABASE_DIR/BACKUP_DIR 路径变量，再显式设置 Home/Data/Database/Backup 与配置为同一临时实例下的绝对路径；自动测试始终使用 t.TempDir/临时目录，并断言全部解析路径位于该临时根下。仅设置 ROAMI_HOME 不构成隔离。开发者是否共享安装版实例是显式选择，不能由 cwd 猜测，不能让质量测试触碰真实用户库。

旧布局迁移与冲突处理

现有实现的源位置并不相同：主库来自旧 HomeRoot 的 meta.db，蜂群库来自旧 HomeRoot 的 swarms/<id>/swarm.db，Git 归档来自旧 DataRoot 的 ai-footprints.db。更早的 ~/.roam、~/.ttmux 和 ~/.local/share/ttmux 也可能残留。先复用旧解析规则逐项定位，不按 mtime 选“最新库”，不跨所有候选路径自动拼接数据。

  1. 只读盘点：roami db migrate --layout --dry-run 输出源路径、目标路径、布局/schema 版本、所需空间、旧写者和冲突，不写数据库、不创建目标业务库。
  2. 进入维护：停止旧服务、旧独立 CLI 的持续写者与插件宿主；新版本持独占维护锁。旧进程不理解新锁，不能仅取得新锁就声称停写。无法确认已停写则终止切换。
  3. 保存原始快照：使用 SQLite 一致性快照机制覆盖全部已知库及未 checkpoint 的 WAL，生成可恢复的 pre-layout 备份清单。区分路径布局迁移与 schema 升级，先保存旧 schema 的快照。
  4. 构建目标布局：在目标数据库根的同文件系统兄弟 staging 目录里准备完整快照集，保留稳定实体 ID；校验 quick_check/integrity_check、版本、外键、行数与关键关联。按需在目标副本执行新 schema 迁移，源库不被部分升级。
  5. 发布与登记：生成 catalog 与实例清单，原子 rename staging 为新 DatabaseRoot，再原子更新 <DataRoot>/storage-layout.json 和受管服务路径。记录 recoverable 阶段日志；多文件之间不宣称一次全局原子替换。若中途崩溃，启动根据 journal 完成登记或保持维护状态，不能误开源库或空库。
  6. 重启验证：所有新版读写都使用新根，重建服务缓存，运行会话/项目/蜂群/归档一致性检查。保留旧库与迁移备份，确认后按显式保留策略清理。降级旧程序前必须整体恢复旧布局/版本，不能让旧程序重新接管已迁移实例。

源与目标都已有数据、清单实例不符、任何关键源库缺失、磁盘空间不足或迁移中断未恢复时，停止并给出诊断。目标不存在才允许原子发布；不使用覆盖 rename 破坏现有库。跨磁盘使用快照复制到目标盘的 staging，完成校验后在目标盘内发布，不直接跨盘 rename 源库。

旧库移出活跃位置后保留在明确的迁移归档路径，不建立面向旧二进制的默认写入软链；兼容命令入口必须先升级到新版分派器。迁移不自动合并两个独立实例，也不删除旧目录下非数据库文件。

数据目录与数据库目录的职责

database/ 只收纳数据库、catalog 和 SQLite sidecar；备份、锁、日志、Node 依赖、浏览器 profile、截图和凭据均不放这里。清理 cache/run 不得影响数据库；删除单个 swarm 的旧产物目录不能顺带漏删或误删登记分库，改由 Catalog 协调生命周期。

StorageCatalog 是唯一开库前置：解析 Paths、校验布局与实例、提供版本化 DatabaseDescriptor，再交连接层。业务包不得 filepath.Join(home, "meta.db") 或自行 sql.Open；统一连接、迁移和维护协议都在 internal/storage，schema 更新只追加。

roami db status --json 保留旧主库握手字段，并新增 layoutVersion、instanceId、dataRoot、databaseRoot、pathSources、migrationState 和 databases。真实安装状态和故障必须可观察，业务失败不能静默转写 JSON 台账。数据库根目录本身不构成备份；完整备份另见下一节。

备份迁移与维护协议

一个 Go 二进制仍可能同时运行 Web、插件宿主和多个 CLI 进程。完整备份需要协调所有写者，现有单库备份本身不能提供跨库一致性。

  1. 实例维护锁：正常写事务前取得共享锁；backup/migrate 取得独占锁。所有进程使用同一存储包与实例身份，分库创建/删除同样参与。
  2. 锁顺序：维护锁、catalog 独占锁（需要时）、进程内 Store/DB 锁、SQLite 事务。升级与整套备份先进入维护上下文，避免持独占锁后递归申请共享锁。
  3. 独占锁下排空已有写入，固定数据库清单，逐库使用 SQLite VACUUM INTO 生成包含 WAL 数据的快照。校验完整性与 hash 后原子发布完整 manifest；失败只留下明确的未完成备份。
  4. 迁移前完成备份；各库独立迁移、记录进度。不能假设不同 SQLite 文件具有一笔全局原子事务。
  5. 备份必须包含 catalog 与逻辑布局描述；恢复时从备份重建实例清单并重映射 Home/Data/DatabaseRoot，保留实例与库 ID，核对 catalog 与数据库集合完全一致。空目录恢复不得依赖源机仍存在的配置或 catalog。恢复采用离线流程：停止所有写者、关闭连接、验证版本和整套清单、备份现状、整体替换并核验、重启重建缓存。失败回滚整套数据集。

维护协议覆盖会话、项目、插件、蜂群 posts、归档写入。旧版本写者不能识别新锁时，必须先停止或升级；仅检测当前没有 SQL 锁不构成安全保证。协调改造完成前仅提供停写后的完整备份，不提前宣称支持在线备份。

backups/<timestamp>-<id>/
  manifest.json           格式/布局版本、实例、各库 ID/type/owner/schema/hash
  catalog.json            同一维护窗口下的分库清单快照
  storage-layout.json     可恢复布局描述，恢复时重映射实际目标路径
  meta.db
  swarms/<id>/swarm.db
  archive/ai-footprints.db

备份不包含密码和登录 Cookie。原有单库备份接口保留兼容语义；新 roami db backup 清楚区分完整备份集，避免旧脚本按单文件格式误读。

项目与认证

项目支持 Git 仓库和普通目录；worktree 归主仓库，身份使用稳定 project ID，显示名允许重复。remove 只移台账，不删除目录、会话或 worktree；仍有会话时可能被重新发现。

命令 现有 API / 行为
project ls GET /api/projects
project show <id> 先按 ID 选择列表 summary，不伪造完整详情
project create <dir> --name ... --clone ... POST /api/projects，本机相对路径规范为绝对路径
project prefs <id> PATCH /api/projects/:key/prefs，区分未传与清空
project activity <id> GET /api/projects/:key/activity
project remove <id> DELETE /api/projects/:key

连接使用 --server / ROAMI_SERVER，默认从本机配置推导；服务未启动时明确提示，不偷偷启动。POST/clone 等失败不自动重试，超时可能已生效，需要查询后再决定。

auth login 复用现有 /api/login、口令、TOTP、防爆破逻辑。密码交互或 stdin 输入，不进入 argv、不持久化；只保存服务签发的 Cookie。凭据文件 0600、目录 0700，按 scheme/host/port 隔离，跨 origin 不传凭据。logout 调用现有退出流程并清本地 Cookie。

正常验证 TLS，本机自签证书加载已有 CA，URL 必须匹配 SAN；不默认跳过验证。首期验收限本机服务，远端路径语义和主机管理另行扩展。

存量环境的升级

仓库文件更新还不够：安装器需要刷新机器上的 CLI 兼容入口、补全、已安装 skills，以及由 Roami 生成的受管 service 与任务命令。重新渲染受管模板后展示差异；服务变更按既有安装流程应用，不能覆盖用户自行维护的脚本和配置。

已运行 Agent 不强行重写上下文；其旧指令通过兼容入口保持可用，新会话和后续生成的任务全部注入新命令。对持久化的用户自定义 cron/shell 命令，升级时只识别、提示和提供迁移映射，避免全局字符串替换改变用户逻辑。完成验收必须区分“Roami 自己生成的调用已迁移”和“用户旧内容仍兼容”。

调用清单与防遗漏门禁

实施前用 rg 建立调用清单，覆盖源码、模板、脚本、测试、文档、服务配置、模块文件及生成产物来源。除直接的 ttmux/chrome 命令，还要搜索 TTMUX_BIN、exec.Command、go -C、working-directory、旧 SDK import、安装路径和动态 argv 构造。每个条目记录归属、目标路径、迁移状态和验证方法。

迁移完成后增加脚本 scripts/dev/quality/cli-entry-audit.mjs，接入 quality 门禁和 CI。扫描明确范围内的可执行调用、模板指令与构建依赖；旧用法必须进入有文件位置和原因的窄允许清单。允许兼容测试、历史迁移、协议字段和设计快照，不能以整个目录忽略掩盖活跃调用。原生 tmux 和 Chrome 浏览器可执行文件调用继续保留，不盲目替换同名词。

最终做一次干净 PATH 验收：只安装正式 roami 产物及 tmux/Node/Chrome 等运行时，不安装旧的独立 ttmux/chrome CLI，跑 Web 会话、项目开工、Agent 能力指令、蜂群、插件定时任务、自检与浏览器截图。旧入口兼容验收另跑；主链路必须在没有旧 CLI 的环境下成功。
