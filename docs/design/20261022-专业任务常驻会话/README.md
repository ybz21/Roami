# 专业任务常驻会话

## 产品与用户故事

用户把任务交给 Codex / Claude Code 后，一轮完成不等于用户确认整个任务完成。
保留原任务、工作区、专业会话及供应商对话身份；用户可打开会话手动修改，也可直接在 Main 提补充要求。
修改回到原任务；缺失/忙碌/身份不符时明确阻塞，不按默认配置另派其他 Agent。

任务详情提供“打开会话”和“完成并关闭”。关闭需短确认；只有本轮已停止且原会话空闲，才关闭该确切会话。
关闭不删除交付物、历史或工作区。停止本轮不自动关闭会话。已结束任务不新增轮询。

## 技术设计

- Main 的修改/补交付物使用 `task_steer`；Tasks 在事务内拒绝向已跟踪专业工作区误建新任务，并返回原任务身份。
- 专业新任务通过 Go execution 的 persistent 模式启动交互 TUI，复用既有生命周期回调、发送与进程身份校验。
- 初轮通过绑定的启动收据关联生命周期；后续通过原 sessionId 发送。完成回调只结束该轮，不退出 Agent。
- 初轮与续轮都保留专业供应商 conversationId；不扫描“最新对话”猜身份。
- 关闭由用户界面专用接口触发，校验 owner/task/revision/runId，并用持久关闭记录与续改互斥；Go 再校验确切 tmux/供应商身份与空闲状态。
- 关闭失败保留输入与记录；未知结果禁止自动换会话/重发。旧的一次性任务不能冒充可复用会话。

### 实施自查

- 新任务默认 `persistent=true`；旧单次执行通道保留兼容测试，生产默认不会退回单次执行。
- 关闭操作只能由用户接口发起，不向 Main/Worker 提供自动关闭工具。校验任务修订与执行批次，和排队中的续改互斥。
- Go 关闭前再次校验供应商对话、pane 身份、空闲状态与进程停止证据；另一会话不被关闭。
- 截图所示原 Codex 使用旧单次模式，进程已退出；不能把新会话冒充旧进程。新建任务才具备本次常驻能力。
- 忙碌或缺失的原会话明确失败并保留需求；未知关闭状态保持阻塞，检查原会话，不自动更换执行器。
