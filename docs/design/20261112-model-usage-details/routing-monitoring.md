# 路由策略与模型监控 · 原型增补

本文件记录原型评审阶段。后续正式实现见 [产品接入](product-integration.md)。

本轮继续完善静态 HTML。真实后端的路由、监控采集、磁盘保留机制均未接入，接口规范继续暂缓。示例供应商名称、账号、单价、额度和质量数据均用于交互演示。

## 产品设计

大模型新增同级「监控」页。「聚合」保留先选源、再选模型的添加方式，默认策略改为 `smart`。模型源的免费资格仍先于策略排序；免费聚合没有可用免费候选时停止，不转为付费调用。

### 九种路由策略

| 策略 | 设计行为 |
| --- | --- |
| 智能 `smart`，默认 | 账号与 Key 共同排序，嵌套组算一个。订阅先看周额度重置，只有 5 小时窗口的看该窗口重置；无重置时间的积分看最早到期。重置相同再比较积分到期。还有余量的在前，休息渠道最后 |
| 按顺序 `order` | 从第一个成员开始，不能回答时继续下一个 |
| 用完再换 `drain` | 当前账号或 Key 用完后转移持久游标；前面额度恢复也不切回。休息只临时跳过，不移动持久游标 |
| 轮流 `rotate` | 会话每一轮推进一个账号或 Key；同一轮的失败重试不重复推进 |
| 最少使用 `usage` | 按来源报告的剩余额度从多到少排序；未知不解释成无限额度 |
| 到期前用完 `pace` | 周剩余额度 / 距重置小时数；没有周窗口时使用 5 小时窗口。更早到期的最先一批积分可覆盖该速率。使用达到 90% 的账号最后兜底；Key 按近期发送 Token 数从少到多排 |
| 按权重 `weight` | 每个模型权重 1–1000，默认 1；均匀穿插，模型内部仍使用提供方自己的账号 / Key 路由。嵌套组算一个成员，休息成员退出本轮，失败转下一个 |
| 速度优先 `fast` | 综合首字时间和输出速度，新测量权重更高；不到 10% 的差距保持原序。每五个请求给一小时未测渠道一个探测机会。只采集流式测量，重启清空，休息渠道最后 |
| 最便宜优先 `cheap` | 只用于路由组。自设价优先于标价，再乘提供方倍率与时段倍率；同币种等价保持原序，未知最后。免费组内价格均为 0 时维持原序 |

策略选择下只显示简短说明，完整规则可展开。权重只在选中 `weight` 时出现在成员旁；空值、小数、0 和超过 1000 都不能保存。所有策略以模型源的免费条件、能力要求、余额和休息状态为前提。

按用户提供的分时计价规则设计：DeepSeek 官方 API、Command Code、OpenCode Go 的 DeepSeek 在工作日 UTC 01:00–04:00 和 06:00–10:00 使用 2 倍；Ollama Cloud 的 DeepSeek V4.1 Flash / V4 Pro 在工作日 UTC 12:00–18:00 使用高峰价，其他时间半价。原型不把这些当作已核实的真实供应商价格写入当前配置。

### 策略演示边界

「调度演示」仍使用当前已保存的聚合成员，验证选择、限流休息、耗尽和开始输出后停止切换。「策略数据演示」是独立示例，提供周 / 5 小时额度、积分到期、Key Token、模型权重 / 嵌套组、速度和分时价格数据。可以模拟轮次、耗尽、恢复和推进时间。

独立示例中的嵌套组仅展示“一组一成员”的权重语义，尚未实现嵌套组编辑器或真实的提供方账号列表。当前聚合演示每个源 / 模型映射一个示例渠道；它不能被解释为完整的多账号调度实现。当前源列表未提供统一的真实订阅余额、积分批次与速度遥测，正式接入前须补齐来源证据。

演示对速度使用“首字延迟 + 100 个输出 Token 的耗时”进行比较，最近一次样本权重 70%；真实策略的目标输出长度与衰减参数须随实际遥测校准。便宜策略演示按输入 / 输出 1:1 的示例负载比较，分别展示输入、输出有效单价，不做跨币种换算。以上是明确标注的演示假设，不是已确认的后端计费契约。

## 监控页面

- 顶部选择模型源、模型、最近 1 / 6 / 24 小时；全局卡片、趋势、源对比和详情使用同一范围。
- 展示可用率、首字延迟 P95、成功回复输出速度 P50、质量抽检通过率及抽检数量。质量与速度分别计算，未检测不记为通过或失败。
- 质量抽检设计覆盖固定问答、结构化输出和工具调用，使用相同版本的检查集比较源。原型用预设结果展示，不执行真实探测或发送模型请求。
- 桌面点击源打开右侧详情，关闭即释放宽度；手机是带一个返回栏的全屏详情。详情列出最近异常、错误分类和抽检未通过记录。
- 示例每 5 秒更新，后台或离开监控时暂停生成；重新进入会按实际经过时间推进示例时钟并执行过期清理。页面筛选不改变保留策略。

### 只保留一天，且容量有上限

监控数据最多滚动保留 24 小时，不是按自然日累计。每次写入先清过期记录；达到 **10,000 条或 64 MiB 指标数据**中的任一上限，就从最旧记录开始提前淘汰。不承诺容量受限时仍保留完整 24 小时。

原型使用 `MonitorRing` 有序内存队列，不写 localStorage、IndexedDB 或真实数据库。插入过程中持续限制条数和字节数，允许乱序到达；单条记录超过预算直接丢弃。展示现有条数、序列化指标字节数、过期数量和容量淘汰数量，并可演示推进 24 小时和达到条数上限。抽检未检测、指标未知和空数据保留明确状态。

### 后端存储设计，待确认后实施

保留策略归监控存储本身管理，不依赖浏览器在线。读取时严格过滤 24 小时边界；写入前清理，独立维护任务每分钟回收过期数据。时间跳变也不能使旧数据变成永久保留。

使用独立监控存储和一分钟聚合桶；仅存指标、错误分类、规则 ID / 版本及通过 / 失败结果，不存完整提示词、模型响应或凭证。限制源 / 模型序列数，防止无限标签基数。生产容量预算应包含索引、数据库空页、WAL、SHM 和临时文件，不能只限制 JSON 内容大小。

可采用独立 SQLite 文件，启用可增量回收的空间策略，设置最大页数，并对 WAL 在写入准入处实行阈值检查与 checkpoint / truncate。建议将 64 MiB 的磁盘预算划分为主文件不超过 48 MiB、WAL 不超过 8 MiB，其余预留 sidecar / 临时空间；到达预算且无法回收时跳过新监控样本，保留丢弃计数，不能继续增长。删除行不等于文件缩小，回收和异常重启均须实测。

此规则只作用于新增监控数据；现有用量汇总、审计回执与记账证据沿用各自保留规则，不能为了监控清理误删账本。

## 用户故事

1. 我不配置策略时直接用 smart；根据额度重置和积分到期优先使用会损失的额度。
2. 我设置模型权重 3:1，观察请求均匀穿插；同一模型有多个账号也不会变成双倍成员权重。
3. 我使用 drain 时，前面的额度恢复不会抢回当前账号；休息恢复则可回到同一持久游标。
4. 我按同一模型比较不同源的可用率、延迟和质量，打开详情确认异常原因。
5. 我让监控一直运行；超过一天的数据滚动清掉，数据量激增也不会无限占存储。
