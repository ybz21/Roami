# 持久团队的每日运行与浏览器验收

先读项目 AGENTS、确认目标、原团队的当前成员/任务/轮次、群聊和记忆。将职责绑定到真实持久
成员ID，不用名称推断身份，不为下一天创建 r2/r3 替身。历史重复职责保留记录，迁移在职身份
要明确说明；不能因某次失败就认定当前实例永久不可恢复。

## 对话与派工

Main 的注册 CLI 必须作为一次完整、单独的 bash 调用，例如
`roami agent task status --input '{"taskId":"当前真实任务ID"}'`。先读 tool_list 或对应 help 的
schema，不加 `cd`、管道、重定向、env 或 `bash -c` 包装；直接读取结构化结果。宿主负责
turn/call 身份，不自行补造。原成员的后续工作走 task_steer 或受支持的 swarm say，
不直接往受管原生会话 session send；追加输入会改变原执行的可信范围。

Main 当前目录没有某个发布操作，不代表原成员机器没有 Chrome/ADB。分别检查当前角色的
受管操作与原成员实际已安装入口，沿用用户当前授权及冻结版本；不能用旧设备限制覆盖用户
后续明确授权。发布后先核对同一个平台对象，缓存未更新或回执字段矛盾时不换业务键重发。
时间从实际工具时钟或宿主事件取，不手填猜测时间。需要回看历史时指定范围；避免恢复整个
团队历史淹没当前上下文。原 Main 压缩期间保留原分支和历史，将一份有界交接排队，不连续
重复催办或新建 Main。

用 roami chrome 打开项目运行态，核对该项目 Main 的真实身份；从 Main 发送一项具体工作，
从群聊 @leader 验证进入同一负责人，再观察 Main 的实际转交、成员文件与群聊回复。
HTTP202/accepted/投递成功不是完成。Main 发进展应调用绑定身份的 swarm_post；
公共 CLI swarm say 是人的消息入口，会显示为 human 并唤醒 Main，不能用它给自己回报，
否则容易出现冒充用户与自我唤醒。成员任务的最新 revision/run 必须在真正启动后读取；
续派请求里的 expected revision 是前置版本，不等于下一轮的实际版本。不要将旧 r2 路径
硬编码进新轮次。发现目录与宿主身份不符时保留原件，记录偏差，以宿主身份验收。

原成员结束当前任务后仍需维持原 provider 会话。能力上下文属于具体活跃任务/修订；旧任务
结束后不能拿旧 context 操作账号。用户追加工作应由 Main 受管续派，领取新的活跃上下文。

## 成员问题与 Main 收件箱

先用实际宿主的工具发现/CLI help 确认是否支持 `swarm_inbox_read` 和 `swarm_post` 的
`kind`、`messageKey`、`replyTo` 字段。只有帮助或注册 schema 确认支持时才使用；仓库模板
和工具名称不能证明当前线上已经升级。不支持时保留原问题，让原 Main 在现有对话中处理。

成员用自己的当前 task/revision/run 身份提交 `question`、`blocker` 或 `handoff`，保留
同一业务 `messageKey` 和未知回执的原 commandKey；重试不换键，不改正文/收件人来冒充
同一消息。普通 `progress` 只记录进展，不进入 Main 待处理收件箱。同一问题跨轮次处理时
先读原回执，旧 run 的消息不能变成对当前任务的指令。

Main 从自己的绑定收件箱读取问题，用 `kind=reply` 和原 `postId` 作为 `replyTo` 答复；
原成员从自己的绑定收件箱取回回复。`sourceCurrent=false` 仅是历史证据，不能直接续派。
人的只读预览不代表 Main 已取到；read 回执不表示已理解或解决，只有实际关联的答复
才形成该收件人的答复凭据。另一个成员的答复也不能替 Main 核验或将任务改成成功。
Main 回合已停止或结束时，不用旧上下文追加新消息或标记已读；在原 Main 的真实活跃
回合继续处理。未知命令先用原 commandKey 对账已有回执，不改键重发，也不手填虚构回合。

宿主未接通受限自动协调时，需要用户在原 Main 发起处理；不要用人的 `swarm say`
把成员文本变成新授权。收件箱存在、Main 答过话及文件已生成，都不能当作每日自动循环
或任务验收已经完成。核对实际 Main turn、回复关联、当前任务状态与独立验收记录。

## 未知结果的恢复

WORKSPACE_OUTCOME_UNKNOWN 是当次尝试的历史结果，不能凭这条标签无限停住。重新读取
当前 writer 的真实执行结果、inputStopped/outcomeKnown、会话/工具状态及实际文件。缺少
停止证明就不重放；已有可信停止且已核对部分写入时，走支持的原任务续派，不删除锁文件、
不改数据库/busy、不新建成员绕过边界。恢复成功也不抹掉历史失败。

## 采集与复盘

由数据成员读取 Connector Skill，做一次有明确日期/窗口的采集，保留源响应、源身份、
时间与文件摘要，通过群聊交给 Main。Main 独立回读当前run字节后，调用受管项目操作确认
观测，并在浏览器重进数据看板核对。采集失败保留旧事实，缺数写unknown；重复同日快照
不等于跨日增长。发布后的真实曝光、点击、观看与制作数量分开，不能把草稿当发布。

## Main 的文本交付验收

在当前验收轮次完整读取本轮 artifact:// 引用，拿到结果后再调用注册 swarm verify。
宿主检查原 Main、当前 task/revision/run、文件 SHA 与完整读取记录；以前回合读过文件
不能替代本轮读取。只有验收事件与 task=succeeded 才表示宿主通过，不把 accepted 或
成员成功声明当完成。外部发布仍需用户/宿主核验，不能沿用文本验收路径替代平台回执。

日索引明确项目根相对路径、原素材批次和真实 producedAt；复盘保存、确认采集和发布
时间分别记录。旧记忆可以追加注明阶段更正，不覆盖原文；确认旧前缀和历史副本均保留。

## 记忆

先读全文和当前SHA，再追加已经验证的长期知识。不能用 content=probe/test 或缺字段请求
试探真实写接口；查帮助、工具schema或隔离fixture。全文编辑必须保留旧知识和历史版本，
误写只在停止相关写入后，通过原文、当前哈希和受支持CAS恢复。不可直接手改运行状态。

## 任务详情与失败诊断

群聊 accepted 只表示投递。核对这条共享消息实际关联的 Main turn、对话和最终状态，不能拿
Main 私聊的最新失败当作群聊失败，也不能因为没有最终回复就认定仍在执行。失败先进入原
Main 查看执行记录、产物和停止证明；保留草稿，不自动重发或另建负责人。

读取成员结果要指定真实 taskId。完整结果应保留当前修订的证据，不应隐式恢复整个 Main 的旧
执行日志；旧对话引用通过 conversation_history 单独读取，被遗忘内容仍排除。旧服务若把详情
读取扩大为完整历史，记录宿主缺陷及实际请求范围，不能靠截断交付内容或修改模型窗口掩盖。

模型错误按本轮 turn 检查，别把聚合旧轮次的调用数当成本轮。比较失败前后的输入范围和工具
回执；确需不执行工具的诊断重放时，先核对原请求哈希并沿用保存的路由和参数，不调用返回的
工具。诊断 HTTP200 只证明该请求此时可受理，原任务恢复仍要原 Main 转交、原成员执行和本轮
文件验收。没有修正证据不反复续派，也不新建实例绕过失败。

## 定时唤醒和催办

先查询本机插件/命令的实际能力。现有 cron 的 action=agent 每次会创建会话，不适合长期Main。
action=exec 执行 daily-operations Skill 的有界脚本：先核对 projectGoalDailyWake、原项目 Main
和仍有效的 delegationId，再通过 roami swarm daily 提交原目标的本地日期槽，不写新用户消息。
忙碌或等待用户回答时保留同一通知，不中断用户对话；日期槽和未开始的协调回合跨日后不补跑。
Main 读取本日计划、当前任务并续派原成员；不要定时启动替代 Agent。普通 reminder
只产生提醒，不证明模型已执行 Connector；autoCollect 也不是任意Skill的日更调度器。

启用前确认时间与时区、目标身份、命令、权限、下一次触发及运行者；使用已有插件调度，
不加个人 crontab。用一次受控触发验证原Main收到、实际执行和回执，再分别验收下一次定时。
插件启用或 plugind 存活不证明 cron.serve 已常驻。全局巡检可能同时触发现有其他日程；先核对
真实任务表和运行范围，不因登记本项目计划就启动所有已有任务。计划文件不等于注册或运行回执。
重复触发要复用同一项目/日期/时段的幂等键；结果未知不换键重投。不要为一个成员开启全局
keepalive；催办要针对真实当前任务与阻塞，无新信息时避免空转。

账号发布按用户为本项目选择的模式执行：人工模式先准备完整正文、图/ALT或视频/封面/标题简介，
再请求决定；已授权自动模式由原 Main 独立审核并冻结通过版本，不逐条重复报批。两种模式都要
核对实际账号/范围和平台回执；成员的话、任务成功或“等待审批”标签本身不能产生发布资格。

原生 agent notify 也只投递通知；唤醒需使用明确的 wake 能力，不回退普通 send 绕过空闲/身份检查。
cron.add 创建提案显式使用 enabled=false 和 IANA timezone；编辑不重置原启停与未指定的时区。

Use [durable team bindings](team-bindings.md) when reconciling current roles or an interrupted configuration save. Current/history presentation does not change old host task states.

## 已确认的运行态交互

团队页左侧选择 Main、群聊或原成员，中间保留该对话，右侧工作区切换协作与任务列表。
查看任务详情不等于给成员追加任务；派工、群聊投递、执行结果、Main 独立验收分别核对。
关闭右栏应释放宽度并保留草稿；手机工作区与详情逐层返回原聊天。浏览器缩窄/粗指针
模拟不能记为真机通过，验收命令须限定自己的 target，并将按钮限定到对应模块，避免
点到全局同名入口。

看板同一天的有效版本按宿主确认追加顺序取最后一条，不按 capturedAt 最大值排序。
跨日比较使用真实日期与当前 sourceKey；缺失/未知不是零。使用 Connector Skill 批次时，
Main 先阅读并核对当前轮原始字节，再 record；批次回执与群聊/任务验收保持独立。


## 原有成员聊天的隔离验收

聊天目录按群聊、Main、当前职责排列；查看成员复用其执行器的原会话与全局输入框，
不能用一条新建会话或另一个成员的历史冒充。注册较早的 CLI 成员可能没有 instance 字段；
先核对原 task、当前 revision/run、存活 session、执行器与项目归属，不能据缺字段另建成员。

不同 session 名和正确的发送目标不保证历史展示隔离。两个成员可共享 cwd；对受管
Codex/Claude，应核对宿主 lifecycle 的真实 providerConversationId 与唯一原转录文件，
再分别打开两名成员确认消息不同。缺失或冲突的绑定保持不可用，不回落同目录最新文件；
旧缓存 file 参数也不能覆盖当前绑定。这里只读验证，不手改 lifecycle 来制造通过。

迁移旧成员草稿时保留原文；全局原会话已有草稿优先。不确定投递继续使用原 commandKey
和前置任务 revision，不能在切换页面或恢复后改成新请求。请求晚回时不得清除后来输入。

## 采集与验收的角色证据

成员报告即使命名为 main-verification，仍是成员产物。核对实际作者和工具执行记录，
Main 必须独立读取当前轮原始响应与批次请求后再验收。批次已经提交时先对账现有回执，
不能为了补 Main 验收重复采集、换 key 或再 record。明确区分请求文件的原字节 SHA 与宿主
规范化请求摘要；二者不同不代表证据损坏。

## 长期循环中的边界

自动审核、发布和取数按[自动运行](automatic-loop.md)执行。Main已验收草稿交付仍可能留有改稿项，不能把task=succeeded直接作为发布许可。用户选择自动模式后不固定逐条人工报批；缺少发布通道则如实保留能力缺口。

续派text只包含该成员的职责，不转发整条总控请求；真实用户授权上下文另存。受管CLI逐条独立提交，宿主注入调用身份。任务完成回调可自动触发Main验收，普通群聊/日程的唤醒与恢复仍需分别证明。


## 交接收件人与下一步执行人

回复核验成员时，只确认该成员交付和待处理事项；不要把“由你投稿”等下游动作发给负责
只读核验的人。先核对收件人职责、原 member/task 和当前 revision/run，明确点名真正的
下游执行成员，再经受管续派提交。普通群聊回复不产生执行权限，也不替代 task_steer。

Main 说“接受证据”后仍须核对宿主验收回执：完整读取本轮要求的留存 artifact，再调用
swarm_verify。磁盘复算、群聊结论与正式任务验收分别留证；缺少读取时补实际读取，不能
清空产物列表绕过。只在旧任务已验收、当前执行已停止且结果已知后续派原实例。
