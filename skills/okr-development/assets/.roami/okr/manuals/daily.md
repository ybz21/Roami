# 日常运行与故障处理

## 一轮工作

Main 的受管命令按 tool_list/help 给出的 schema 单独调用，例如
`roami agent task status --input '{"taskId":"当前真实任务ID"}'`；不要加 cd、管道、重定向、
env 或 shell 包装，也不伪造 turn/call。续原成员用 task_steer 或支持的 swarm say，
不要直接 session send。普通进展投递不是任务执行或验收回执。

角色目录只说明当前角色可调用什么，不证明原成员缺少 Chrome/ADB。发布沿用最新用户授权、
准确账号与 Main 审核冻结版本；未知先对账同一平台对象，不换键重发。时间取真实时钟或宿主
事件，不猜时间；已公开回执的状态、uploaded/submitted/published 与公开 URL 应一致。
Main 历史压缩时保留原实例、原分支及全量记录，只排队一份精确交接，不用重复催办恢复全部历史。

1. Main 读取确认 O/KR、方法、团队记忆、今日索引、最近复盘和真实看板，确定当前实验。
2. 在原团队里安排有界任务与依赖。内容成员准备实际文案/素材，数据成员按 Connector Skill 取数；账号、同一文件和设备操作同一时刻只有一个负责方。
3. Main 按用户选择的模式独立审核当前交付；授权自动运行时，冻结通过版本后交原成员自动发布，不固定逐条人工报批。按[自动运行](automation.md)核对账号、版本和平台回执；制作任务验收不等于发布资格。
4. Main 确认真实指标入库并检查看板，不把活动数量直接解释为增长归因。比较已知结果和未知，写复盘与下一轮实验，再续派原成员。
5. 把有用事实和决定归入团队记忆；保留原始证据、轮次记录和失败原因。

## 文件组织

新物料写入项目根目录的 `materials/YYYY-MM-DD/<渠道或工作类型>/<简短主题>/`，目录名不使用任务或运行 UID。Main 维护当天 README.md 和 manifest.json；索引记录所有者、任务/修订/运行、来源、相对路径、字节数、哈希、产出时间和验收状态。跨天任务保留已约定目录，次日索引引用；旧素材迁移注明原日期与路径，不当新产出。

## 日更和唤醒

`schedules/daily.json` 是提案，文件存在不代表调度运行。先确认用户需要的时间和时区、当前宿主的定时/项目 Main 唤醒能力，再检查安装、nextDue 和真实运行回执。只唤醒绑定项目原 Main，不创建替代或回落首页。普通 send 不等于调度唤醒；一次手动取数不代表每日自动执行。

共享主机只运行本项目明确选择的日程，不能顺带激活别人的启用任务。缺少能力或时间时保留禁用提案并说明缺项，不臆造定时器。按宿主实际支持的 scoped tick/serve 协议配置，命令以本机帮助为准。

## 常见问题

| 现象 | 先查什么 | 收尾 |
| --- | --- | --- |
| 数字取到了但卡片为空 | [看板链路](dashboard.md) 与确认观测 | 实际卡片值与回执 |
| 同一内容反复派出 | 任务、运行、command/batch key 的既有结果 | 原请求对账，不换身份重放 |
| 成员失联或旧实例被引用 | 当前 work/task/revision/run/provider/会话状态 | 可信恢复原对话 |
| 保存冲突 | 新 revision 与他人变更，保留本地草稿 | 合并后重新确认 |
| 来源超时或字段缺失 | 当前来源绑定、原始响应及截至时间 | 保留旧值，缺失保持未知 |
| 看似定时却没有执行 | enabled、实际安装、nextDue、运行记录 | 不以配置文件当运行证据 |

## 定时任务的登记与验收顺序

1. 读取 `schedules/daily.json` 和 `skills/daily-operations/SKILL.md`（均位于 `.roami/okr/`），核对原项目/Main 与真实宿主能力。确认时间、IANA 时区、slot、输入 Skill、权限和补跑策略；未确定就保留禁用提案。
2. 在开发终端按该 Skill 的命令对原 Main 做 `--dry-run`；这只验证支持度与身份，不投递工作。通过当前插件 help 查询 cron 的真实 add/enable/list/run/tick/serve 参数，不猜命令。
3. 用 exec 调用该项目唤醒脚本，先显式登记禁用计划，保存调度任务 ID、命令绝对路径或明确 cwd、时区与执行者。核对后启用，回读 enabled 和下一次触发；不能用会新开会话的 agent action 替代原 Main。
4. 仅对本项目选定日程做受控触发，核对同一原 Main 的真实 turn、原成员本轮执行、证据、确认数据和实际看板。accepted 仅是接收；补记独立验收。结果未知先对账，不换 key 重投。
5. 核对持续运行的 scoped 调度进程及下一次真实触发记录；保存运行时间、使用的 Skill 版本、请求 key、结果/错误和下次触发。仅注册任务或进程存活不足以证明日更成功。
6. 改善时间或流程前检查正在执行的轮次并避免重叠；沿用原任务身份，保留旧回执。停用需要核对真实 disabled，不删除历史或强行改 busy。

## 定时推动的改进闭环

开工唤醒读取前一天/最近周期复盘，Main 选择一个可验证改进，写假设、基线、指标、窗口和停止条件。取数轮由原数据成员执行确认 Connector，失败保留旧值和未知。复盘唤醒比较真实结果，不重复计算累计快照或拿草稿数当公开发布数；Main 决定保留、调整或停止，并把有效结论写团队记忆、周期复盘，必要时提出 Skill 修改。

周/月/年按项目根 AGENTS.md 的路径组织复盘；可以根据实际需要另设经过确认的复盘 slot，不默认全部启用。下一轮使用修订后的 Skill 及原成员，保留版本、证据和回退条件，才能证明“记忆带来了改进”。

## 等待下一次已登记日程

当天工作完成后先处理所有待验收、未知结果及群聊 question/handoff。当前宿主若实际提供
`swarm_goal_wait`，协调 Main 可传真实 swarmId 和简短 reason 选择等待原计划。宿主
读取项目日程、原插件 job、实际 nextDue 与执行器，不采纳自报未来时间或本地证明文件。
该操作只保存等待决定，不创建任务、实例、第二条计划或发布权限。

登记阶段把实际 schedulerPlugin、schedulerJob、cron、runnerUnit 回执写入日程声明，
保留原 project/Main/Swarm/delegation 和时区/slot。当前读取实现支持原 cron 插件的
单日槽 exec，使用模板原 wake_main.py 和显式绝对 PATH，命令以 Python shlex.join
生成字面参数；Linux runner 须是只 tick 该 job 的每分钟 systemd timer。其他执行器
或自定义脚本未被核验时保持不可用，不能因为 enabled=true 就声称一定会唤醒。

等待不替代实际到期验收；继续原插件和 daily 去重，不另建并行计时器。没有计划或能力
时说明缺项，不派无意义的索引/预检维持忙碌。维护接续与人工消息单独标记，不能计为
自然触发。最终回告失败时，已保存的复盘和记忆仍保留；恢复先对账原回执，不重复写入。

## 保存复盘与失败恢复

先读取当前项目状态。工具目录提供 `project_okr_review` 时，项目 Main 使用该入口；协调回合使用 `swarm_project_review`。尚未提供时沿用 `project_okr_update` 或协调回合的 `swarm_project_update`，选择 `operation: "review"`，payload 使用真实整数 `revision`、非空 `summary` 和可选文本 `actions`。项目与团队身份保持宿主绑定，不能切到首页或其他项目。

summary 写本轮实际结果、证据、未完成事项；actions 写下一步。不要用占位复盘探测字段。字段错误先读返回的公开契约，不能把一次成功写入当作参数测试。同一请求重试沿用原业务键；改稿或刷新修订不应制造第二条复盘。若已误写，保留历史并用真实后续复盘明确更正，不算有效成果。

最终回复失败不代表此前写入回滚。先核对复盘回执、记忆当前内容及旧版本，再决定是否补做；已保存的复盘和记忆不重复提交。模型上游认证失败与浏览器登录失败分别排查，不改模型路由、密钥或费用配置来绕过。
